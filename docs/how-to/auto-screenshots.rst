******************************************
Auto-screenshot widgets for the docs
******************************************

Most widget images under ``docs/images/auto/`` are regenerated by
``tools/screenshot_widgets.py``, which drives Qt and grabs each ImControl
widget, either on its own or inside a running window built from a mock
setup.  This keeps the GUI documentation in sync with the code without
anyone having to remember to take fresh screenshots.

The full-window screenshots at the top of the module pages
(``docs/images/imcontrol-window.png`` and ``improcess-window.png``) show real
data on a real microscope, which no mock setup can produce.  They are taken
by hand and kept outside ``images/auto/``, so the script never touches
them.

Run it
======

Run the script from the repository root, in a full ImSwitch2 development
environment (napari included; the docs-only environment is not enough).
It imports whichever ``imswitch`` package Python finds, so if your
installed package is an editable install of a different checkout, put this
one first with ``PYTHONPATH=.``.

.. code-block:: bash

   # All widgets, each in isolation (default; see "Crash isolation" below)
   python tools/screenshot_widgets.py

   # Named widgets only (class names, space-separated)
   python tools/screenshot_widgets.py LaserWidget PositionerWidget

   # ALSO capture the ImControl window with a mock setup loaded:
   # docks are populated with mock detectors, positioners, lasers
   python tools/screenshot_widgets.py --mock-setup --show

   # Mock-setup pass only (skip the per-widget standalone captures)
   python tools/screenshot_widgets.py --mock-only --show

   # Use a different bundled mock setup
   python tools/screenshot_widgets.py --mock-only --show \
       --mock-setup mixed_hamamatsu_apd_mock_scan_setup.json

   # Faster but no crash isolation; one segfault stops the whole run
   python tools/screenshot_widgets.py --no-subprocess

   # Render on the real display (default is offscreen)
   python tools/screenshot_widgets.py --show

   # Write to another folder, to compare before replacing the committed images
   python tools/screenshot_widgets.py --out /tmp/shots

Options:

``WIDGET ...``
   Widget class names to capture.  Default: every widget found.
``--show``
   Render on the real display instead of Qt's ``offscreen`` platform.
   Windows appear briefly while they are captured.
``--mock-setup [SETUP_JSON]``
   Also run the mock-setup pass with this setup.  Without a value it uses
   ``example_no_hardware.json``.
``--mock-only``
   Run only the mock-setup pass (``example_no_hardware.json`` unless
   ``--mock-setup`` names another file).
``--no-subprocess``
   Capture every standalone widget in the script's own process.
``--light``
   Capture the standalone widgets in Qt's plain style instead of
   ImSwitch2's dark style sheet.
``--out DIR``
   Write the images to ``DIR`` instead of ``docs/images/auto/``.
``--single`` / ``--single-mock``
   Internal: used by the script to start its child processes.

Output goes to ``docs/images/auto/`` (or the ``--out`` folder):

* ``<WidgetClass>.png`` for each standalone capture, for example
  ``LaserWidget.png``.
* ``mock-main-window.png`` for the ImControl window of the mock-setup pass
  (the ImControl module only, not the multi-module application window).
* ``mock-<dock>.png`` for each dock of that window, where ``<dock>`` is the
  dock's key: a name from the setup's ``availableWidgets`` (``View``,
  ``Recording``, ``Scan``, …) or ``Image``.  A dock whose capture comes out
  empty, for example one hidden behind another dock's tab, is skipped.

The mock-setup pass runs first, then the standalone captures.  Every
skipped capture is reported, and the script exits with a non-zero status if
anything was skipped or the mock-setup pass failed.  With
``--no-subprocess`` the exit status reflects only the standalone captures.

Two capture modes
=================

**Standalone (default).**  Each ``Widget`` subclass is constructed in
isolation with the ``optionsBasic`` test fixture as its options.  Fast and
dependency-free but the layout is "empty": controllers haven't run, so
per-laser rows, per-positioner axes, and live plots are absent unless a
populator (below) fills them in.  The script applies the application's
dark style sheet (the one ``prepareApp`` installs), so the captures look
like the running program; ``--light`` leaves it off.  A widget that comes
out smaller than 32 pixels in either direction — an empty frame whose
content only its controller adds, such as ``WellPlateWidget`` — is skipped
rather than written.

**Mock-setup (``--mock-setup``).**  Builds the full ImControl main window
with a setup from ``imswitch/_data/user_defaults/imcontrol_setups/`` (the
setups shipped in the package, not the ones in your ``ImSwitchConfig``
folder).  Every widget is built by the real factory with its controller
attached, so the screenshots show actual mock laser rows, mock positioner
axes, the populated scan widget, the napari viewer, and so on.  Internally
this uses the same ``prepareUI`` helper as the UI test suite
(``imswitch.imcontrol._test.ui``), and the application's dark style sheet
applies.

The script accepts any file in that folder, including setups for real
hardware, so pick one of the hardware-free setups:
``example_no_hardware.json``, ``example_mock.json``,
``mock_scan_setup.json``, ``hamamatsu_mock_scan_setup.json``,
``mixed_hamamatsu_apd_mock_scan_setup.json`` or
``galvo_apd_mock_scan_setup.json`` (see :doc:`../mock-infrastructure`).

Run the mock-setup pass with ``--show``.  Qt's ``offscreen`` platform
provides no OpenGL context, and the pass builds napari's OpenGL image
viewer, so offscreen it crashes and is reported as
``mock setup: child killed by signal 11``.

The window is requested at 1920 × 1080 but cannot be larger than the
screen it is shown on, so the full-window capture is roomiest on a large
monitor; on a laptop screen the docks are as cramped as they would be in
use.  Once the window is up, the panels are re-sized for their content, as
**Tools → Reset panel layout** does.

The pass runs without anyone at the keyboard:

* On macOS and Linux it runs with a throwaway ``ImSwitchConfig`` (``HOME``
  points at a temporary folder that is deleted afterwards), so it neither
  restores nor saves the widget state of your own setup.  Windows finds the
  folder through *Documents*, so there the real one is used.
* Every dialog the pass would open — a restore warning at start-up, *Save
  the current widget state…?* on close — is answered **No**.
* Once the images are written, the child process exits without the napari
  teardown, which can crash at interpreter exit and would otherwise mark a
  good pass as failed.

The pass runs in a child process with a 120 s limit and is reported as
``mock setup: timeout after 120s`` if it takes longer, which makes the exit
status non-zero.

Crash isolation
---------------

By default each widget is rendered in its own short-lived Python
subprocess, stopped after 60 s.  Some widgets (anything OpenGL-backed via
vispy or napari) can crash hard on the headless ``offscreen`` Qt
platform — without isolation, a single ``SIGSEGV`` would end the whole
run.  In subprocess mode the parent reports the signal and moves on::

   skip EtSTEDWidget: child killed by signal 11

If you need to debug a particular widget interactively, run with
``--no-subprocess`` and ``IMSWITCH_SCREENSHOT_DEBUG=1`` to get a full
traceback in-process.

How it works
============

The script walks ``imswitch.imcontrol.view.widgets``, finds every
concrete subclass of ``imswitch.imcontrol.view.widgets.basewidgets.Widget``,
and tries to instantiate it with stub arguments.  Each widget is shown
briefly, ``QWidget.grab()`` is called, and the resulting ``QPixmap`` is
saved as PNG.  Widgets that are plain ``QWidget`` subclasses, such as
``ImageWidget``, are not found by this walk.

By default ``QT_QPA_PLATFORM=offscreen`` is set so the standalone captures
run without a display server.  Use ``--show`` if you need to capture a
tooltip, popup menu, or other transient UI element that only renders on a
real surface, and for the mock-setup pass.

Populators
==========

A *populator* is a small function that calls the same public methods
on a widget that its controller would normally call on init —
``addLaser(...)``, ``addPositioner(...)``, ``initControls(...)``, etc.
Without one, a standalone screenshot of e.g. ``ScanWidgetBase`` is just
an empty frame, because the scan-parameter grid is constructed
lazily from the positioner list.

Populators live in ``tools/screenshot_widgets.py`` next to a
``POPULATORS`` dict that maps widget class names to populator
functions.  Widgets without an entry (``SLMWidget``, for example) are
captured with their bare layout.  A few of the populators:

* ``_populate_laser`` — adds 405 / 488 / 561 (modulation-capable) /
  640 nm rows.
* ``_populate_positioner`` — adds X / Y / Z axes.
* ``_populate_scan`` — calls ``initControls`` with the same
  positioners + a few TTL devices; covers all four concrete scan
  widget variants.
* ``_populate_fft`` — pushes a synthetic FFT magnitude image
  (Gaussian DC + two rings) into the FFT widget so it shows a real
  picture, not a black square.
* ``_populate_flim_hist`` — feeds a bimodal lifetime distribution
  (~1.2 ns and ~3.5 ns populations) into the FLIM histogram widget.
* ``_populate_beadrec`` — drops a synthetic field of gaussian beads
  into ``BeadRecWidget`` so the reconstruction viewport renders.
* ``_populate_settings`` — adds a fake Hamamatsu camera with five
  representative ``DetectorNumberParameter`` /
  ``DetectorListParameter`` entries.
* ``_populate_leicastand`` — populates a cube turret with five
  filter cube choices.

To add a populator for another widget:

1. Open its controller in
   ``imswitch/imcontrol/controller/controllers/<Foo>Controller.py``
   and find what it calls on ``self._widget`` during ``__init__``.
2. Write a function ``_populate_foo(w)`` that calls those same
   methods with realistic-looking fake data.
3. Register it in the ``POPULATORS`` dict.

If a populator raises, the script prints
``populate(<WidgetClass>) skipped: …`` and captures whatever was rendered
up to that point — empty layout always beats no screenshot.

Adding a new widget
===================

If your new widget takes mandatory constructor arguments beyond
``options``, add its class name to the ``WIDGET_STUBS`` tuple near the
top of ``tools/screenshot_widgets.py`` and return the extra keyword
arguments from ``_widget_stub_kwargs()``:

.. code-block:: python

   def _widget_stub_kwargs(name: str) -> dict:
       if name == "ULensesWidget":
           return {"napariViewer": _stub_napari_viewer()}
       if name == "MyWidget":
           return {"someRequiredArg": <stub-value>}
       return {}


   WIDGET_STUBS = ("ULensesWidget", "MyWidget")

``ULensesWidget`` is the existing example: it gets a duck-typed
``MagicMock`` in place of a napari viewer, which is enough because
``addItemToViewer`` swallows ``AttributeError``.

Without a populator, the screenshot is a *layout-only* capture:
controllers populate runtime-driven elements (one row per laser, scan
plots, …) which are absent here.  The intent is to keep the *visual
structure* of each widget — its buttons, panels, labels — discoverable in
the docs.

For populated docks, use the mock-setup pass rather than a hand-taken
screenshot.  Only images that need interaction or a window the script does
not build (an open menu or dialog, the whole application window, the
ImProcess window) are taken by hand.  Images taken by hand belong in
``docs/images/``; the two whole-window images in ``auto/`` named at the top
of this page are the exception.

CI integration
==============

Nothing runs the script automatically.  Read the Docs builds from the
committed images: it installs only ``docs/requirements-readthedocs.txt``,
without napari and without installing the package, so it could not run the
script anyway.  Regenerate the images locally and commit them.

On a headless Linux machine, PyQt5 still needs the system libraries listed
under ``apt_packages`` in ``.readthedocs.yaml`` (``libgl1``, ``libegl1``,
``libxkbcommon0`` and others), even on the ``offscreen`` platform, and the
mock-setup pass needs a display.
