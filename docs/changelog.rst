Changelog
*********

Unreleased
==========

**New Features**

- **Scripting tutorials.** The scripts ImSwitch installs into ``~/ImSwitchConfig/scripts`` are now a step-by-step course in ``tutorial/basic`` (snapping, camera settings and the live view, recording and reading the file back, several cameras, stages, clean-up that survives Stop, ``importScript``) and ``tutorial/scanning`` (a scan triggering a camera, one frame per scan position, a camera and an APD in one scan, scan timelapses, a laser power series in one recording). Each script's header says what it teaches, which simulated setup file to load, what that setup simulates, and what your own microscope needs, so every step can be tried without a microscope; ``tutorial/README.md`` explains how to choose a setup and asks you to read each script and predict it before pressing **Run all**. ``imswitch/imscripting/_test/test_shipped_tutorials.py`` boots each tutorial's mock setup headless and runs it through ImScripting's own executor, so a change that breaks a tutorial fails the suite. See :doc:`scripting`.
- Scripts can set and read the recording file format: ``api.imcontrol.setRecFileFormat('HDF5'|'TIFF'|'ZARR')`` and ``getRecFileFormat()``. A script that reads back its own recording no longer depends on what the Recording widget last showed.
- Scripts can read detector parameters: ``api.imcontrol.getDetectorParameter(detector, name)`` returns the value the Settings widget shows, in the parameter's own units, and ``getDetectorParameters(detector)`` lists every parameter as ``{name: {'value', 'units', 'editable', 'options'}}``. The names differ per camera (``'exposure'`` in ms on the simulated camera, ``'Exposure'`` in µs on a Thorlabs camera, ``'Set exposure time'`` in s on a Hamamatsu), and an unknown name is refused with the names the detector does have. A script that changes the exposure can now put the user's value back instead of a value written into the script.
- ImProcess drop-in plugins can be reconstructors, not only processors. A ``.py`` file in the plugins folder that defines a ``Reconstructor`` subclass is discovered like a processor plugin, joins the reconstructor picker in the Parameters dock, the config editor's reconstructor list and headless workflows (``bootstrap_registry`` sees it), and is versioned by a digest of its file. The Plugins menu gains **Add plugin file…**, which copies a chosen ``.py`` into the folder and reloads in one step, so a reconstructor can be added to a running ImProcess from the menu bar. **Tools → Load reconstructor** lists every reconstructor ImProcess knows about but has not loaded — the built-ins the setup file did not name, plus discovered drop-ins — with a one-line description, and picking one registers it for the session, adds it to the Parameters-dock picker and makes it active; before, a setup that named only MoNaLISA never showed the others, and the only way to try one was to edit the setup file and restart. Reloading is exact about what changed: an edited reconstructor is swapped in at once (the active one gets its parameter widget rebuilt), an unchanged one keeps its instance and widget state, a removed active one hands over to the first registered reconstructor — and while a reconstruction is running the reconstructors are left alone and the status bar says so, so a job never straddles two versions of one plugin. ``examples/improcess_plugins/frame_average.py`` is a complete drop-in reconstructor.
- The config editor shows typed fields for every manager, not only the 20 with a hand-written template: each manager's ``managerProperties`` contract is extracted from its source into a checked-in JSON Schema (``imswitch/imcontrol/model/configeditor/schemas/``, regenerated with ``python tools/extract_manager_schemas.py --write`` and drift-checked in CI), and the schema is the type authority in the form. Templates remain presentation overlays. The editor also stops rewriting what nobody changed: an untouched field is written back as the very object it was loaded as, an optional key the file omitted is not added until it is edited, a key saved under an alias spelling is written back under that spelling, and numeric fields are plain line edits that neither clamp, round nor refuse a keystroke: a number is saved as the number typed, and anything else is saved as typed and named in the form. ``validate-setup`` validates every core manager against the same schemas and warns when a file gives a property under two spellings. The top-level keys of a device entry (``forAcquisition``, ``axes``, ``wavelength``, ``resetOnClose``, …) are typed from the ``SetupInfo`` dataclasses the same way (``schemas/kinds/``), so every one of them is a typed field for every manager, and ``validate-setup`` warns about a key of the wrong type. Properties read by a consumer other than the manager -- ``vel_max``/``acc_max`` by ``GalvoScanDesigner``, ``startConfig`` by the SLM controller -- are role rules (``schemas/roles/``): the validator reports a real scanning axis that lacks them with the designer's own message, and the editor offers them as optional fields on exactly those devices. The editor's templates are now presentation overlays (label, group, tooltip, options): a template can no longer describe a property the code does not read, nor mis-type one it does, and every device card in ``docs/devices`` is drift-tested against the schemas, so a manager cannot gain a property without the docs noticing. Device plugins get the same treatment: ``python tools/extract_manager_schemas.py --package <plugin> --write`` writes a plugin's schemas into its own package without importing it.
- The config editor gives back the kind of value it was handed. Every value without a dedicated widget is rendered as a line of text and was read back as a string, so a setup file that said ``"analogChannel": 3`` came back saying ``"3"`` — which ``SetupInfo.getAnalogChannel()`` returns verbatim instead of building ``Dev1/ao3``, silently breaking the line. The raw tab for untemplated properties had the mirror-image bug (a port ``"5"`` came back as ``5``), a select whose options were strings wrote ``"9600"`` over a baud rate every shipped setup stores as a number, and template bool defaults reached new devices as the string ``"False"``. Text that still reads as the value it was given *is* that value; edited text becomes the same kind if it can and a string only if it cannot; raw strings are never promoted; select options follow the saved value's type; and a default a template states as a value keeps its kind.
- **Tools → Edit hardware configuration…** opens the Config Studio from inside a running ImSwitch, on the setup file that session is running. It had only ever been reachable as a standalone script, which meant leaving the microscope to change anything about it — and, because ``utility_scripts/`` is not part of the installed package, was not reachable at all from an install or a frozen build. The editor now lives in ``imswitch.imcontrol.view.configeditor`` and ships with ImSwitch; ``python utility_scripts/imswitch_config_editor.py`` still launches it standalone. The window is not modal, so the microscope stays usable while a setup file is being edited, and a second trigger raises the window that is already open rather than putting two editors on one file. Saved device templates move from the install directory to ``~/ImSwitchConfig/config_editor_templates`` — site-packages is shared between users, may be read-only, and is replaced on upgrade — and templates already saved in the old place are copied across on first open.
- ImSwitch offers to restart when the editor closes, but only when the session actually needs it: the setup file it is running was saved, or the active config was pointed somewhere else. Editing a setup this session is not using changes nothing about it and asks nothing, because a prompt that appears every time is one that gets dismissed unread. Accepting runs the ordinary shutdown first — widget states saved, controller workers drained, hardware managers finalized — and re-execs only once it is done. **Tools → Pick hardware setup…** and **Pick modules…** now restart the same way; both used to replace the process image on the spot, so detectors, stages and lasers were never closed and the new process inherited whatever they had been doing. The command line is carried across the restart, so a session started with ``--debug`` or ``--scale`` comes back the same. A restart of a session that was itself started by a restart works on macOS and Linux too: the re-exec used to pass the interpreter path in literal double quotes (a Windows habit), which the restarted Python took as its own executable, so the second restart could not find it and ImSwitch neither restarted nor exited cleanly. A restart that cannot exec now logs why and exits normally.
- ImProcess results can be sent to installed **napari plugins**. ImProcess's viewer is a napari viewer, so a plugin's dock widget opens beside the result's layers in the same window, and a plugin's reader opens a file ImProcess exports for it (in the same viewer, or a detached one for plugins that insist on their own window). **Plugins → napari plugins** lists what accepts the current result; plugins that are not installed are shown disabled with the ``pip install`` line. Layers are built by result kind — localizations become a Points layer from the real table, in ``(z, y, x)`` order with the axial step from the file, never the histogram preview; tables and curves have no layer form and are not offered. The street is one-way by design: nothing is read back unless you choose **Import layer from napari as result…**, and then you pick both the layer and the result it came from; an imported image or mask gets a coordinate space of its own unless an adapter vouches for the plugin and the layer's transform is the identity. Adapters ship for napari-storm and napari-skimage, can be added in the setup file (``processing.napariEndpoints``) or as a ``NAPARI_ENDPOINTS`` list in a drop-in plugin file, and every send is a session that owns exactly what it added and cleans up after itself. See :doc:`improcess-napari-plugins`.
- Every ImProcess result now carries a **provenance graph**: the source file with a fingerprint, the reconstruction with its parameters, every processing step with its parameters, ordered input ports and ROI restriction, on every path that produces a result (the reconstruct button, the worker, live streams with their completion status, RAM recordings, the classic MoNaLISA path, consolidation). Parameters are written down losslessly or the step says it cannot be replayed and why. Saving goes through one staged protocol for all twenty result types — every file planned first, written beside the target, published by atomic rename with companions before the primary, and receipted — and the graph travels in the file (OME-TIFF description, HDF5/Zarr attributes, a listed ``.provenance.json`` companion for CSV). MoNaLISA keeps its ``(T, Z, C, Y, X)`` hyperstack layout, now as OME-TIFF with named channels; the classic ImageJ writer remains one release as ``imagej``. The multicolor-registration processor no longer writes an alignment file from inside the run; the alignment is part of its result. See :doc:`improcess`.
- **ImProcess workflows** reconstruct and process without the GUI: an ordered list of steps (sources, reconstructions, consolidations, processing steps, saves) referring to one another by id or ``id.port``, written as YAML/JSON, run through the same code paths the GUI uses so the results carry the same provenance. Parameters not given keep the plugin's widget defaults, which every built-in now declares and a test pins to the widget; MoNaLISA fills its scan geometry from the recording headlessly as the GUI does. ``python -m imswitch.improcess.workflows run WF.yaml --input *.h5 --out results/`` batches a folder with one summary row per file and no file overwritten unless asked; ``validate`` checks plugin ids, references, arity, parameters and ports (including data-dependent ones such as a channel split's) before anything runs; ``list`` prints every plugin with its version, ports and defaults. And because the record is in the file, ``replay FILE`` turns a saved result back into the workflow that made it — the Fiji macro recorder without a recorder — refusing with every reason when a step cannot be run again, and verifying in replay mode that the sources have not changed. **File → Export workflow of current result…** and **Run workflow…** do the same from the GUI, and **Run workflow on selected results…** / **Run workflow over files…** batch it: the workflow's reconstruction step stands in for each selected result (its source is not reopened, and the processing chains onto the result's own provenance), or its source is bound to each chosen recording; each run reports on its own, so one refused or failing input is one failed row and the rest still run; ``show-provenance FILE --json`` is what to hand an LLM, with the guide, for files that carry only a partial or legacy history. See :doc:`improcess-workflows`.
- ImProcess can open a saved time lapse as one stack. The new **Time lapse** reconstructor (``time-lapse``) takes a camera lapse or a scan lapse, recorded one file per timepoint or as ``scanN`` groups in a single HDF5/Zarr file. Open any one item and the whole lapse becomes the source. Until now each item was a separate multi-data entry: a lapse loaded in full once per timepoint, and in a single file every one of those loads re-listed every group. The lapse is found from recorded attributes (``recording:lapse_index``, ``recording:num_timepoints``, ``recording:single_lapse_file``). Each point is placed at its recorded index, so a missing point is a marked blank rather than a shift of everything after it. A second lapse recorded into the same file is told apart where the index starts again, since ``scanN`` numbers only the next free group. Only time is stacked: points recorded as ``tile`` or ``position``, and old tiling runs with a ``tiles.json``, are refused and left to **Tiling mosaic**. The stack is lazy. A header pass on the worker reads every point's shape, times and completion outcome without its pixels. The viewer then gets a dask array and reads the timepoint on screen, so a 2000-point lapse opens at once. T can follow the planned interval or the actual start times, and both are kept per point. Points that started late are listed in the Results table, as are incomplete ones. Scan lapses record no interval, so they always use the actual times. Incomplete points are marked in place or skipped at the end, and a point that changed shape is refused by name. The discovery and the lazy stack live in the data layer (``improcess.model.lapse_source``), so MoNaLISA or BeadRec can later process a lapse one timepoint at a time without redoing any of it. See :ref:`improcess-time-lapse`.
- ImProcess results that own their files are shown and saved without being read whole. A result whose array declares ``display_lazily`` -- the time-lapse stack does -- reaches napari as a dask array chunked by plane, so the viewer reads the plane on screen. A lazy view over a file it only borrows is still read once when shown, because that handle closes when another file is loaded. ``save_image_result`` streams any lazy array one leading index at a time into OME-TIFF (BigTIFF when large), HDF5 or OME-Zarr with plane-sized chunks, instead of reading it in full, and can write a per-plane OME ``DeltaT`` from one time per T index. The Denoise panel's applicability check no longer materializes the current result just to count its axes.
- **Tools → Session notes…** attaches free text to every recording and snapshot saved for the rest of the session. Plenty of what matters about an experiment never reaches a widget — the power measured in the back focal plane this morning, which coverslip batch is on the stage, that the 561 line was misbehaving after lunch — and until now there was nowhere to put it that travelled with the data. The editor is modeless, so it can stay open while an experiment runs, and every keystroke takes effect at once rather than on an Apply button somebody has to remember. Where the note lands depends on what the container can hold: HDF5 and Zarr get ``metadata/notes/session`` beside the rest of the recording's attributes, and OME-TIFF gets the OME ``Description`` — which is what Fiji shows under *Image ▸ Show Info* and what OMERO imports as the image description, and the note's only route into a TIFF, which carries no shared attributes at all. "Session" means until ImSwitch is closed: the note is deliberately not saved with the widget state, because a note about this morning's alignment would be a lie tomorrow. Scripts can set the same text with ``api.imcontrol.setSessionNote(...)``. See :doc:`gui`.
- The memory ImSwitch spends on buffering and on automatic work is settable per machine. A new ``memory`` group in ``imcontrol_options.json`` holds three limits, each named for the one thing it bounds, and **Tools → Memory limits…** in ImControl edits them and applies them as soon as they are saved (refused while a recording runs, since a smaller queue would fail it). The two queues default to what the code did before; the ImProcess working set defaults to 1 GiB, sized for a typical workstation rather than tied to the acquisition queues: ``writerQueueMB`` (512) is the backlog the recording writer may hold before the acquisition loop blocks, ``perDetectorQueueMB`` (256) is the backlog any one detector chunk queue may hold before that consumer's stream is declared incomplete, and ``processingWorkingSetMB`` (1024) is the working set ImProcess may spend on work nobody asked for — contrast sampling, whose sample size now follows the allowance rather than staying at two million values under a smaller nominal budget (and whose strides are now chosen from what each slice actually keeps — a singleton leading axis used to be charged a share of the reduction it could not deliver, so a ``(1, 100, 100, 100)`` stack came back with three times its allowance), and the mean preview computed on load. They are limits on what ImSwitch *chooses* to hold, not a process budget: camera drivers allocate their own ring buffers (the Hamamatsu interface about 4 GiB) and datasets are as large as the data, so no total is claimed. A value that is not a positive, finite whole number (``"lots"``, ``2.5``, ``NaN``, ``Infinity``) is reported by name and the default stands, since a typo in a preferences file must not take a rig down — the fields are deliberately untyped for the JSON loader, which would otherwise reject ``"lots"`` before any validation ran and silently round ``2.5`` to ``2``. Every message that quotes a limit — the chunk-queue overflow, the writer's backpressure line, the notices below — names the setting that moves it. See :ref:`improcess-memory-limits`.
- Recordings say what they can hold before they start, and say when they stop draining the moment it happens. At arm, one line estimates per detector how many frames the queue budget buys — or that one frame exceeds it on its own, as a scan-driven detector's volume can — together with the writer batch and the chunk in hand; a point detector logs its assembled volume's size when the scan is built, which is the first moment it is known. The acquisition loop now reports the *first* moment it blocks on a full writer queue (``PRODUCER_STALL_WARN_S`` waited a second first, and a 256 MiB chunk queue at 512 MiB/s fills in half that, so the overflow could arrive before the line that explained it), repeats every ``PRODUCER_STALL_REPEAT_S`` while it stays blocked, and still says when it resumes. These are estimates and diagnostics; none of them refuses an acquisition.
- ImProcess estimates automatic work before doing it, and never approximates a preview in plane. The mean shown on load needs a float64 accumulator, a float32 result and the input plane in its own dtype, which the existing plane-count bound says nothing about (the estimate was measured against the real peak, and a second float64 plane the division used to make is gone); above ``processingWorkingSetMB`` the current-data panel and the edit window open on the first plane instead and say so in the status bar — or on nothing, for a virtual source whose plane read decodes the whole series, as a TIFF without zarr support does, since there the first plane costs as much as the mean; the edit window reads its first plane through the lazy handle rather than loading the dataset, a plane read from such a TIFF no longer keeps its whole decoded series alive, and switching to a dataset with fewer frames no longer reads a plane because the slider was clamped — and the *Show mean* button computes the mean as asked after the same line — never at a spatial stride, because the MoNaLISA pattern finder and the SMLM detection preview take pixel-unit parameters from that image. The mean's meaning is unchanged either way (a lazy source has always averaged at most 256 planes at an even stride; a materialised one every plane). Ordinary *Open* still decodes the dataset whole, which is what was asked for, but a dataset larger than the working set is announced in the status bar and the log *before* decoding starts, with its decoded size (from shape and dtype, not the file size — a compressed HDF5 well under a gigabyte can decode to many) and whether *Open virtual* offers a genuine lazy path for that source (a TIFF without zarr support does not: its virtual array reads the whole series per plane).
- Single-axis scans work through the advanced scanning path: a Z-piezo-only axial profile — one scan axis, no galvo — designs, runs and records end to end, where it previously crashed in ``GalvoScanDesigner`` with an opaque ``zero-size array to reduction operation minimum`` (the smooth fast-axis signal was built as *(lines − 1)* tiled periods with the first and last half-sweeps sliced from that tiled middle, so one line tiled zero periods; the half-sweeps are now sliced from a single evaluated period, proven byte-identical for every multi-axis scan by golden baselines captured before the refactor). Which motion profile the fast axis gets is now a device property rather than a name heuristic: ``managerProperties.smoothScan`` selects the galvo profile (continuous constant-velocity sweep, spline turnarounds, ``vel_max``/``acc_max`` required) or the stepped profile (held at each centered absolute position for the dwell time — right for a piezo, no limits needed); absent the key, the historical 'mock'-name rule stands so no existing setup changes behavior. ``example_sted.json`` marks ``ND-PiezoZ`` stepped. Downstream, a 1-axis scan is one line of N pixels: loop dims ``[N, 1]``, buffers ``(1, N)``, chunks ``(frames, 1, N)`` — and the APD/PMT line insert actually writes them, where its squeeze-rank dispatch would have silently dropped every pixel; ``PointScanTTLCycleDesigner`` builds its cycle for a single line (it indexed a second axis unconditionally). The recording stays compatibility ``YX`` with ``SizeY=1`` and the scan step as ``PhysicalSizeX``, and the scanned physical device and axis (``scan_axis_devices``/``scan_axis_physical``, e.g. ``ND-PiezoZ``/``Z``) are written into every recording's shared attributes as deliberately write-only provenance — nothing in ImSwitch reads them back. Only axes that actually scan are claimed: an assigned axis that collapses to a single step emits no waveform and is excluded, by the same rule the designer uses. HDF5 and Zarr store the shared attributes natively; OME-TIFF now carries them too, as an OME ``MapAnnotation`` embedded in the OME-XML (``TiffStorer`` previously dropped its ``attrs`` entirely), with round-trip tests over all three containers — the rewritten OME-XML keeps the channel names (the stream finalize path had silently dropped them all along), with ``SizeC`` derived from the final axes/shape so a retained line-step recording (``TCYX``, one physical channel across ``SizeC = n_linesteps`` planes) gets its name replicated per plane rather than failing TIFF finalization or silently losing HDF5's ``ome_xml``; NumPy-valued attributes serialize at any nesting depth instead of failing the recording, and a snapshot whose metadata embed fails for any reason keeps the image with its native description. Advanced scans now also enforce voltage compliance before arming: ``_make_full_scan`` refuses a waveform outside a scanner's configured ``minVolt``/``maxVolt`` with an actionable error, where previously the only bound was the NI-DAQ task's generic ±10 V range — a Z scan centered at 0 µm on a 0–10 V piezo reached the hardware. In the config editor, ``smoothScan`` is a three-state field — *Automatic (not set)* / *On* / *Off* — whose Automatic state keeps the key absent from the saved file, so opening and applying a device that relies on the name-heuristic fallback can never silently switch its motion profile. A scan whose second axis collapses to a single step (an XZ with one Z plane) now degenerates to the same working single-line form instead of crashing. New tracked ``galvo_apd_mock_scan_setup.json`` runs the whole chain against the simulated NIDAQ. See :doc:`setupinfo-reference`.
- The pLS-RESOLFT and galvo-detection TriggerScope panels gained a **Camera used for detection** selector, as the multicolor panel already had. The firmware gates the camera on a fixed line in these modes, so the software never chose it — but a scan recording has to know *which* detector receives that pulse to tie frames to scan positions, and without the declaration the recording gate now refuses to arm. Select the camera wired to the firmware's camera line; older saved states and scan files simply leave it unset.
- Scripting: ``getWaitForSignal`` takes a ``timeout`` (raising ``TimeoutError``), polls every 50 ms instead of once a second, and stops immediately when the script is stopped. New global helpers ``callAndWaitForSignal(signal, func, ...)`` (creates the waiter *before* calling, so a signal emitted inside the call is not missed), ``runScanAndWait(timeout, source)``, ``sleep(seconds)`` and ``waitUntil(predicate, timeout)``. See :doc:`scripting`.
- ``api.imcontrol.runScan(source=None)`` now returns a completion handle bound to exactly that scan (``handle.wait(timeout)``, ``handle.done``, ``handle.successful``, ``handle.message``) and raises ``ScanRequestRejectedError`` when the start is refused, instead of returning ``None`` and logging. ``getScanSourceNames()`` lists the scan controllers ``source`` can pick on multi-scanner rigs; ``getScanRequestStatus(requestId)`` serves remote clients, which receive the handle as ``{requestId, source, state, message}``. ``signals()`` additionally exposes ``scanStarting``, ``scanStarted``, ``scanDone`` and ``scanRejected``.
- ``api.imcontrol.isRecording()``; ``stopRecording()`` is idempotent and returns whether a recording was active (so a script knows whether ``recordingEnded`` will follow).
- API calls made from scripts and from the REST/Pyro server are now synchronous: a ``runOnUIThread`` export returns its value and re-raises its exception in the caller, where it used to return ``None`` at once and swallow both. ``snapImage(output=True)``, ``getRecFolder()`` and friends therefore work from scripts and over REST for the first time.
- ImProcess can draw SMLM localization results as GPU point clouds through `napari-storm <https://pypi.org/project/napari-storm/>`_, now on PyPI and installed by the new ``storm`` extra. Set ``"napariStormViewer": true`` in the ``processing`` block and a ``LocalizationResult`` renders as summed Gaussians of each molecule's localization precision instead of the low-resolution histogram preview it carries by itself; without the package, or on a GL session without instancing, the flag does nothing and the preview stays. The viewer reads our nanometre table in place — columns are declared to napari-storm rather than renamed or converted — and the boundary is locked by contract tests that run headlessly against the released package. Point clouds are retained rather than rebuilt on every selection: opened once, updated in place, hidden while a non-localization result is on screen, and closed only when the result leaves the list, which is the churn napari-storm's architecture exists to avoid. A 3D result switches the canvas to 3D and frames the camera on the cloud rather than on the blank image layer. An optional render-controls panel (``"smlmRenderPanel": true``) exposes width mode (per-localization precision or a fixed sigma, with FWHM shown alongside), colour-by-depth, a per-axis render range and colormap/opacity; until a control is touched the renderer decides from the data. See :doc:`improcess`.
- Localization tables from other SMLM software open straight into the ImProcess reconstruction list, so data fitted in Picasso, ThunderSTORM or anything that writes a CSV can be filtered, drift-corrected, grouped, rendered and viewed here. **ThunderSTORM CSV** and **Picasso HDF5** are recognised by content — a Picasso file shares its suffix with image stacks — and need no interaction: units come from ThunderSTORM's ``name [unit]`` header rather than being assumed, its 1-based frames become 0-based, and Picasso's pixel size is read from its ``.yaml`` sidecar. Any other ``.csv``/``.tsv`` goes through a column-mapping dialog, pre-filled from the header names, with the position unit, camera pixel size and first frame number. A file declaring no pixel size gets an assumed 100 nm that is logged and recorded as ``pixel_size_assumed`` rather than passed off as measured. See :doc:`improcess`.
- The localization schema separates **localization precision** from **PSF width**. ``sigma_*_nm`` had been documented as the fitted width, but the Picasso reader mapped ``lpx``/``lpy`` — precision — onto it, so the column meant one thing for data localized here and another for imported data, and the napari-storm boundary was rendering our own results at the PSF width, which only reproduces a diffraction-limited image. New ``lp_x_nm``/``lp_y_nm``/``lp_z_nm`` columns carry precision; the Picasso reader and writer keep ``sx``/``sy`` and ``lpx``/``lpy`` apart; and the ``smlm-localizer`` fills precision from the Thompson/Larson/Webb closed form with Mortensen's correction, using the width, photons, background and pixel size it already computes. Rendering prefers precision and falls back to width for tables that have none. The estimate inherits the fitter's lack of camera-gain calibration, so it is correct in shape but scaled for cameras without unit gain — good for filtering, not for quoting an absolute nanometre precision.
- The config editor now opens the setup file ``imcontrol_options.json`` marks as active when it starts, instead of an empty form, and its ImProcess section exposes every ``processing`` flag the module reads, including the new ``napariStormViewer`` and ``smlmRenderPanel``.
- ImProcess operations can work across reconstruction objects. Processors now declare how many results one run consumes (``min_inputs``/``max_inputs``) and explain a refusal in words (``check_inputs`` returns ``(ok, reason)``), which replaces the undeclared ``params["results"]`` convention the combine-shaped processors had been smuggling their extra inputs through — a convention no panel could discover, which is why *Merge channels*, *Stack/Combine* and *Image calculator* raised on every run when opened from **Load tool**. Those panels now show a checkable, reorderable picker over every loaded result, because order is meaningful: it decides which channel is which, the order of a stack, and which image is A. The reconstruction list also publishes what is loaded and what is selected on the communication channel, so any panel can offer a multi-result operation instead of only the one controller that happened to hold a direct reference to the list. Two-image **FRC** takes the second image from another result rather than only another plane of the same one, so two reconstructions of the same field can finally be compared. In the other direction, a single-input processor can be swept over many results: processor panels gained an *Apply to* scope (current / selected / all results) and the parameterless toolbar ops (duplicate, max projection, split stack, split channels, make composite) run over the whole reconstruction-list selection, skipping inputs they do not apply to rather than cancelling the sweep, and reporting per-input failures without discarding the outputs that succeeded. See :ref:`improcess-multi-result-operations`.
- Tiling grids can be rectangular. ``N tiles`` becomes ``Tiles X x Y`` with a ``Square`` lock that ties the two spinboxes, and a ``Pattern`` chooser. **Spiral** keeps today's behaviour — it grows outward from the current position, so the mosaic is centred there and a run stopped part-way still leaves a filled, centred area; a rectangular spiral is the same walk with out-of-grid positions skipped. Skipping costs nothing in stops: the delta across a skipped position is folded into the next move, so the stage makes one longer move rather than an extra stop, and the number of settles and focus reacquisitions is exactly the tile count either way. It does cost travel, which grows with the aspect ratio — hence **Serpentine**, which rasters from the current position in +X and +Y with *no move longer than a single tile step* anywhere in the run, rows reversing direction rather than returning across. Total travel is then the theoretical minimum, and a settle tuned for one step is right for every move. The two anchor the grid differently on purpose: a spiral has a centre so the stage marks the middle, a raster has a corner so the stage marks where the area begins. The pattern is an explicit choice rather than inferred from whether the counts happen to be equal, so changing one spinbox by one can never silently move the start point or change what a stopped run leaves behind. New ``tiling.defaultTilesX``/``defaultTilesY``/``defaultPattern`` set the opening state; equal counts open with the square lock engaged.
- The ImProcess **Tiling mosaic** reconstructor gained an optional ``Correct vignetting``, which estimates the illumination profile from the run itself and divides it out of every tile. Shading is fixed to the detector — the same corner is dim in every tile — while the sample is not, since the spiral visits different specimen at each stop, so averaging the tiles in detector coordinates lets the specimen cancel and leaves the illumination envelope, which heavy smoothing separates from the residue. No shape is assumed, so one-sided falloff is handled as readily as a radial vignette. Each tile is divided by its own mean before being averaged in, so tiles contribute their shape rather than their brightness and one bright field cannot set the profile; the result is normalised to its median, so correcting flattens the falloff without rescaling the mosaic. Smoothing uses ``mode='nearest'`` — zero-padding would darken the borders, inventing vignetting exactly where real vignetting lives. The estimate is skipped with the reason logged rather than applied when it cannot be trusted: under four usable tiles, tiles of differing shape, or a profile spanning more than 0.2–5x its median, which is a specimen gradient rather than an illumination envelope. Off by default; costs one extra read pass over the tiles. Distinct from the acquisition widget's ``Intensity correction``, which scales whole tiles to their neighbours — that fixes tile-to-tile steps, this fixes the gradient within each tile, and the two compose.
- The ImProcess reconstructor picker can no longer strand you on the tiling reconstructor. Opening any file inside a tiling run resolves to that run's ``tiles.json`` — deliberate, so a tile can be dropped in and the mosaic comes back — but the picker also filtered itself to reconstructors accepting the *resolved* source, and only **Tiling mosaic** accepts a manifest. The two closed a loop: every file in that folder became a manifest, the picker collapsed to a single entry, and nothing in the folder could restore an image source, so **View only** was unreachable however it had been loaded before. The way out is the user's own selection, which is now remembered on the source. A reconstructor is offered when it accepts the loaded source *or* when the originally selected path would resolve to something it accepts, and choosing one reopens that path — so the offer is real rather than an entry that errors. Selecting a run folder or a ``tiles.json`` directly still offers only what can read it, since nothing else was asked for. Spec ids (``tiff``, ``hdf5``, ``zarr``) and source kinds (``image``, ``tiling-manifest``) are separate vocabularies; the mapping between them now lives beside the specs rather than being assumed at each comparison.
- Scans dispatched through the workflow service publish ``sigScanStarting``, and a timelapse publishes one for every timepoint rather than only the first. ``runScanExternal`` arms with ``sigScanStartingEmitted=True`` — it *asserts* the run-level start is already on the channel, and its terminal publishes ``sigScanEnded`` on the strength of that assertion. Neither ``run_scan_from`` nor the legacy broadcast transport made the assertion true — both land on ``runScanExternal`` — so every scan they dispatched ended without having begun; a ScanLapse additionally published one start for the whole run against one end per timepoint. The consumer that paid for this is the focus lock, which yields the focus axis on the start and takes it back on the end, depth-counted: an unpaired end drove the depth to zero and it resumed correcting into a live waveform. A tiling run of XYZ tiles therefore had the focus lock fighting the scan's own Z on every tile after the first — with **Pause during scans** checked, which is what made it look like the setting was being ignored. An XY scan hid the fault entirely, since a lock running alongside a scan that never touches Z is harmless. Starts are now emitted inside the dispatched action so they land on the UI thread ahead of the arm rather than queueing behind it, a refused or raising dispatch pairs the start nobody accepted, and callers that own the lifecycle themselves pass ``notify_starting=False`` so they cannot be doubled up. The pairing is deliberately narrow, matching the rule ``run_scan_prepared`` already applied: only a request a controller *reported on and refused* is paired here, since an accepted one already owes a terminal and an unreported one belongs to a legacy receiver that may have started and will publish its own end. The focus lock was not the only consumer left inconsistent — the autofocus scan interlock counts the same signals the same way, and was equally inactive from the second timepoint on.
- FLIM histogram widget gained a "Decay" mode that plots the aggregated TCSPC photon-arrival histogram with a red marker showing the global single-τ fit for the selected method; the original per-pixel lifetime distribution remains as "Lifetime dist." mode
- Added ``laser_rep_rate_mhz`` parameter to ``SwabianTimeTaggerManager`` so the phasor fit uses the true ω = 2π·f_rep instead of assuming the histogram window equals one laser period
- Added ``scripts/diagnostics/measure_laser_rep_rate.py`` — a TimeTagger.Countrate helper that prints the measured laser repetition rate for plugging into ``laser_rep_rate_mhz``
- Added opt-in time-resolved detector workflows for binned photon-arrival cubes, software gated-STED images, and tau-STED lifetime products. The first backend is ``SwabianTimeTaggerManager`` via a generic detector contract and ``api.imcontrol.buildWorkflowFacade(time_resolved_detector_name=...)``.
- Added stitched-overview cell target detection for tiling workflows. The GUI "Detect cells" action is passive and only overlays markers; automated/API cell targeting explicitly moves through detected targets and can invoke a per-cell workflow callback.
- Renamed the WFS polarisation-resolved acquisition workflow to ``WidefieldStarssWorkflow`` / ``WidefieldStarssParams``. The old ``RecordingWorkflow`` / ``RecordingParams`` names remain available as compatibility aliases.
- Added per-detector acquisition selection: the **Acquire with** control in the View widget chooses which detectors acquire. Free-running detectors are reseeded immediately; scan-driven changes take effect at the next scan iteration rather than disturbing one in flight. An active recording, workflow or event modality overrides deselection, and faulted detectors are always excluded. See :doc:`gui`.
- Point detectors (APD/PMT) now support multi-line-step scans driven by the Advanced scanning widget, where each line step gates a different set of lasers over the same physical line. APD frames keep the line step as its own axis and are saved as ``(T, C, Y, X)`` with correctly ordered OME axis metadata instead of collapsing to ``(T, Y, X)``. See :doc:`gui`.
- Detector acquisition is now lease-based, with a shared scan-execution coordinator owning the participant snapshot, the ``SCAN`` lease and an end-of-scan barrier. Two scans can no longer collide: a second entry point is refused with a clear "scan busy" error, including between repeat frames. The barrier waits for each point detector's final read before releasing hardware, so the last frame of a scan is no longer lost to teardown or to the next repeat frame. Developer reference: :doc:`scan-lifecycle`.
- Added ``LaserInfo.powerDevice`` so a laser entry that only owns a scan-gated TTL line can name the separate device that sets its emission power (an AOTF channel, for example); scans then switch that partner on for the scan's duration. See :doc:`setupinfo-reference`.
- Added the ``liveUpdateIntervalMs`` manager property for APD/PMT detectors to tune the live-preview redraw rate per rig (default 50 ms). See :doc:`devices/detectors`.
- Line-step scans emit ``[LineStepDiag]`` diagnostics from the scan controller, NI-DAQ manager and APD manager — expanded line count, sample budget, clock edges and read plan — for verifying line-step timing against the generated waveform on a real rig.
- ImProcess gained the two stack-axis operations ImageJ users reach for. The Projection panel now takes a *First slice* / *Last slice* range, completing the equivalent of *Z Project* — the statistic and axis were already there, but the whole axis was always collapsed, so projecting part of a stack meant cropping it first. And the Profile panel gained a *Z profile* mode: mean intensity over a drawn rectangle (or the whole frame, as in ImageJ) against the stack axis, plotted in that axis' own physical units and falling back to slice number. The axis is taken from the result's labels, and on a hyperstack the remaining axes stay where the viewer is, so profiling ``Z`` on a ``TZYX`` result profiles the timepoint on screen. Fits, Δx, push-to-table and push-to-graph work on it unchanged, which makes an exponential fit over a ``T`` profile a bleaching curve. See :doc:`improcess`.
- BeadRec fitting in both ImControl and the ImProcess reconstructor now includes an isotropic 2D exponential-decay model and a one-dimensional sine model with fitted wavelength, phase and arbitrary image-plane angle.
- Added an ImProcess **Metadata** panel that shows a measurement file's full metadata hierarchy as a tree. The reader is layout-agnostic — it descends whatever structure the container actually has (HDF5 groups/datasets, Zarr groups/arrays, TIFF series/pages/tag blocks) and reports every attribute it finds, so files from a future storer or another program display without code changes. Nested values, and string attributes carrying JSON or XML (OME-XML included), are expanded into subtrees. The panel follows the current data item and the selection in the reconstruction list — a result made in the session shows its identity, metadata and provenance in the same tree — can read any file without loading its pixels, filters by name/value/type, and copies or exports to JSON/CSV or the shared Results dock. Enable at startup with ``"metadataPanel": true``, or open it from the Tools toolbar. See :doc:`improcess`.

**New Features**

- The ImProcess **ROI manager** reads and writes ImageJ/Fiji ``.roi`` and ``RoiSet.zip`` files, saves and opens its own versioned ROI-set files, and keeps its sets between sessions. ImageJ interop needs the optional ``roifile`` package (``pip install imswitch[imagej]``); without it the menu entries are disabled with a tooltip saying so. Every conversion returns what it could not carry across — styles, arbitrary ROI properties, position axes outside C/Z/T, and the smaller parts of a disconnected region — because a silent lossy export is how a set is discovered to be incomplete long after the fact. Saved sets carry the schema version and the coordinate convention they were written under, and a file from a newer ImSwitch is refused rather than guessed at: reading it half-correctly would place ROIs at plausible-looking wrong coordinates. Sets normally live in the existing widget-state store; a set too large for it spills to a single ``improcess_roi_sets.json`` in the config root, with only a marker and a checksum left behind, so a file that has been edited or has gone missing is detected rather than half-restored. *Create Selection* turns a label image into ROIs and *Create Mask* publishes the ROI set as a label result.

- ROI edits in ImProcess are undoable. Every change already went through one audited path; that path now has ``Undo``/``Redo`` buttons that name what they would undo ("Undo Delete", not "Undo") and ``Ctrl+Z``/``Ctrl+Y`` bindings in the configurable shortcut catalog — ``Ctrl+Shift+Z``, the usual redo, was already **Channels**, and taking it would have left one of the two unreachable. An import is one step rather than one per ROI, and is all-or-nothing: a batch that fails part way leaves the set exactly as it was, because half an import is worse than none — the user cannot tell which of two hundred arrived. Name collisions on import resolve by renaming, skipping or replacing. Restyling many ROIs at once is a single step too, and cannot touch geometry, so it does not invalidate cached measurements. Sets are autosaved a few seconds after the last edit, into the same state store shutdown writes to, so a crash costs seconds rather than a session.

- The ImProcess ROI manager handles **points**. *Draw Points* places them on a layer of their own, and *Add Shape* captures the lot as one multipoint ROI rather than one ROI per point — a fiducial set is a thing, and splitting it would make counting the points, measuring their spacing or naming the set impossible. Twelve point measurements come with them: the count, the coordinates in pixels and calibrated units, nearest-neighbour distances (mean, min and max), and the ROI group ImageJ marks fiducial sets with. The intensity at a point is the value of the pixel it lands in rather than an interpolation between pixels, which would be a number in no pixel of the image. Points import from and export to ImageJ ``.roi``/``RoiSet.zip``, and everything a point does not have — area, perimeter, a fitted ellipse — reports as blank rather than zero.

- The ImProcess ROI manager gained the rest of ImageJ's ROI Manager: **Update** (replace the selected ROI's geometry with what is drawn, keeping its identity so earlier measurements still refer to it), **Specify…** (an ROI at exact coordinates, optionally centred), **Properties…** (name, group and the full style, over one ROI or a whole selection), **Sort**, **Deselect**, a name filter over the table and a right-click menu. Shortcuts follow ImageJ where they were free — ``T`` to add, ``Del`` to delete, ``F2`` to rename — and are rebindable like the rest. Properties deliberately has no geometry fields: it is the dialog most likely to be opened by someone meaning to nudge a region, and moving one is Specify's job. Editing several ROIs at once changes only the fields actually touched, and merges a style onto each ROI's own rather than replacing it, so setting the line width across a selection does not flatten five colours into one.

- ImProcess processors can run over a region instead of a whole image. Filtering, denoising, background subtraction, arithmetic and segmentation gained a *Region* chooser fed by the ROI manager's active set, with two behaviours: **crop** to the region, giving a smaller result, or **mask** outside it, keeping the frame so the output stays pixel-aligned with the input. The two are not interchangeable — a crop moves every pixel index, so a cropped result is given a pixel grid of its own rather than claiming its source's, which is what stops ROIs measured on it afterwards from reading the wrong pixels. Masked-out pixels become *not a number* rather than zero, since zero would claim they were measured and dark. Each result records which ROI set, at which revision, produced it. The restriction is applied around a processor rather than inside it, so a processor becomes region-aware by declaring one attribute and needs no other change. PSF resolution and colocalization are deliberately excluded: they already work per-ROI, and a second route in would be one more thing to disagree with the first.


- **Crop/Substack** can take its rectangle from an ROI. A *Crop from* chooser lists the area ROIs in the ROI manager beside the existing **Manual** entry; picking one fills the Y and X ranges from its bounding box, clipped to the image. The ranges stay the single source of truth — the ROI fills them in and they remain editable, and touching one returns the chooser to Manual — so what is applied is always what is on screen. The axes are matched by label, so an ROI drawn on a YX view cannot fill a YZ view's ranges. A crop made from an ROI records which one, so it is not merely a convenience that leaves no trace. Only ROIs with an extent are offered: a crop is rectangular, and a line or a point has no rectangle to crop to. A polygon or a mask crops to its bounding box, which is what a crop is — restrict a *processor* to an ROI if the shape itself should matter.

- The ImProcess **ROI manager draws every shape it can already capture**. It has always read back ellipses, polygons, lines and freehand strokes, but the only control said *Draw Rectangle*, so the rest were reachable only by changing napari's own drawing mode. It is now a chooser over all six, switching live when the tool is already held — picking a shape mid-draw means the next drag should be that shape. The rectangle stays the default, since changing what the panel opens on would change what a habit draws.

- **Crop/Substack offers the same thing from the toolbar and from the panel.** They were two implementations — a per-axis table in the toolbar's dialog, a ``Z=0:10,T=0:5:2`` text field in the processor panel — which is how only one of them came to offer cropping from an ROI. The table and the ROI chooser are now one widget that both host, so they cannot diverge again. The panel's copy retargets itself when the selected result changes, and drops ranges typed for the previous result rather than applying them to a different extent; any processor whose parameters depend on its input can do the same by declaring ``setResult``.

- The **Profile panel can plot a named ROI**, not only a shape drawn on its own scratch layer — chosen from a *Source* list beside *Drawn*, and re-plotted when the selected result changes, so one region can be compared across reconstructions. What each shape plots follows from what it is: a line has one answer, while a shape with an interior offers intensity round its outline or the mean along X or Y, taken over the ROI's own pixels rather than its bounding box. An ROI that misses the image is reported rather than sampled, since sampling outside the array returns zeros and a flat zero profile cannot be told from a real region with no signal.

- **Segmentation can work inside an ROI, and shows where its threshold landed.** A *Region* chooser restricts the run to an ROI from the manager; the threshold is then computed from that region's pixels alone, so a bright structure elsewhere cannot set the level for the region being looked at. Masked-out pixels become *not a number* rather than zero — zero would add a large dark population and drag every automatic threshold down. An intensity histogram of exactly the pixels the preview considered is drawn with a marker at the threshold found, which answers the question a single number cannot: whether the cut fell between two populations or through the middle of one. The preview is now a **button** rather than a checkbox: every spinbox nudge used to queue another segmentation, so a value was hard to type without the panel recomputing under it. Nothing recomputes until it is pressed — and a preview whose slice or layer has changed underneath it is removed with a note, because a labelling of one image left lying over another is worse than none.

- ImProcess results record how they were made, and saving keeps it. Every processor run now appends a step to the result's ``processing_history`` — what was applied, with which settings, to which input, and, for a run restricted to a region, which ROI set at which revision. The chain is inherited, so a reconstruction that was cropped and then filtered carries both steps in order, and two results derived from one source do not grow each other's history. It is recorded in the single place every processor's output already passes through, so a processor contributes its footprint without knowing the feature exists — the same reasoning as the spatial provenance attached alongside it. Settings that are not JSON are summarised rather than dropped (a kernel becomes ``<array shape=(512, 512) dtype=float64>``), because a key going missing reads as "there was no such setting".

- ImProcess results save as **OME-TIFF, HDF5 or OME-Zarr**, chosen by the filename, and every container carries the calibration and the footprint. The save dialog offers all three; previously it offered ``*.tiff`` only, though HDF5 had been supported all along for anyone who typed the suffix. There is now one writer for anything with an image array, describing it through the same ``OmeImageMeta`` ImControl records with — so a reconstruction and the raw data it came from state their axes and pixel sizes identically. OME-TIFF gets OME-XML in the ImageDescription tag, HDF5 gets Fiji's ``element_size_um`` alongside embedded OME-XML, and OME-Zarr gets NGFF 0.5 ``multiscales``. An uncalibrated result says so rather than claiming one micrometre per pixel. Result types with genuinely different content — a localization table, a curve, MoNaLISA's 6D ImageJ TIFF — keep their own writers.

**Bug Fixes**

- The error for a setup that names a manager from one of the bundled device plugins (``imswitch-device-tis``, ``imswitch-device-thorlabs``, ``imswitch-zhinst-devices``) no longer tells you to ``pip install`` it: none of them is on PyPI, so that command failed. It now says so and gives the install from a source checkout (``pip install "./examples/plugins/imswitch-device-tis[hardware]"``). The plugins' READMEs said the same and are corrected too, and the TIS plugin's missing-SDK error names the package to install, ``imagingcontrol4``.
- A tiling run's per-tile payload recordings no longer claim to be timepoints. Such a run is the Recording widget's scan lapse with tiling placing the stage before each point, and each item's acquisition layout was scoped with a ``time`` partition because the lapse only knew one kind of item — so every tile was recorded as timepoint *k* of *N*, the opposite of what the ImProcess reader already modelled (it adapts a tiling manifest as a ``tile`` partition). A positioned lapse now records its items as whatever its positioning provider says they are: ``tile`` for tiling, ``position`` for any other workflow, ``time`` only for a plain timed lapse. Each payload also carries its tile's ``Tiling:grid_x``/``grid_y``/``stage_x_um``/``stage_y_um`` as shared attributes, the same identity a snapshot tile already had, so a payload file says which tile it is without the manifest beside it — including when the recording session asked for its positioning before tiling handed the point over. The legacy ``recording:num_timepoints`` attribute still counts lapse items. See :doc:`tiling`.
- A recording's payload axis names come from its acquisition layout where the layout determines them. The writer named them by a frame-count guess — channels first, then Z, for a scan-driven detector — although it held the layout that declares the stored axes in array order; the tiling manifest copies these names for every payload, so a guess that happened to be wrong would have been written into the dataset twice, unchecked. Where every stored axis has one OME letter the declared order is used (and a disagreement with the guess is logged); where it does not — a camera frame stream over a raster, a RESOLFT cycle — the guess stands as before.
- BeadRec saves OME-TIFF with its pixel size. *Save* and *Save all* wrote bare TIFFs with no pixel size and no provenance, which is the one fact a bead fit needs. The reconstruction's pixel is one scan step, or the finer step on both axes when the image was rescaled to square pixels, and follows a 90° display rotation; it is written as the OME physical size, with what BeadRec knew about the image — scan dimensions and steps, orientation, rescaling, name, source — as an OME ``MapAnnotation``. Loading a file BeadRec saved keeps its pixel size, so saving it again does not drop it; an image whose pixel size is unknown is written without one rather than with an invented one. That includes the XZ/YZ images of an auto-axial run: BeadRec reads the scan steps once, from the XY scan, and has none for their Z rows.
- **Help → Documentation** opens ImSwitch2's documentation instead of upstream ImSwitch's. It opened ``imswitch.readthedocs.io`` at the installed version number, which is another project's manual; it now opens the ``docs`` folder on GitHub, until ImSwitch2 has a Read the Docs site of its own. **Help → Check for updates…** already asks ImSwitch2's GitHub releases and the ``imswitch2`` PyPI project (see *Behaviour Changes*), and ``test_help_menu_links.py`` now covers both menu entries, including the comparison of a ``v0.2.0``-style release tag with ``imswitch.__version__``.
- A scan-once recording, and a scan timelapse that runs to its last point, emit ``recordingEnded`` when the recording is finished and its files are written. They never did: the recording worker has held the signal back in the scan modes since 2022, when the recording controller still ended its own cycle on it, and the controller has since moved to an internal terminal, so nothing published it. A script waiting for ``recordingEnded`` around a scan recording hung, and on rigs with a joystick the positioner joystick, re-enabled on that signal, stayed disabled after every scan recording. It is emitted once per recording, not per timepoint; a failed recording still emits only ``recordingFailed``.
- ``api.imcontrol.setRecFilename(name)`` names the recording. It filled in the name but left *Specify file name* unticked, and the name is only used while that box is ticked, so every scripted recording kept its time-based name; ``setRecFilename(None)`` left the box ticked.
- ``api.imcontrol.setSnapModeSave()`` selects the snap format. It matched the name case-sensitively against 'HDF5'/'TIFF'/'ZARR', so its own default, ``'tiff'``, did nothing; unknown names now raise ``ValueError``.
- Loading scan parameters into the Base scan widget (``loadScanParamsFromFile``, setup-mode restores) no longer fails with ``'ScanControllerBase' object has no attribute 'plotSignalGraph'`` after the values were already applied.
- ``hamamatsu_mock_scan_setup.json`` and ``mixed_hamamatsu_apd_mock_scan_setup.json`` can record a scan. Their camera had no ``digitalLine``, so the Scan widget offered no trigger for it and every scan recording failed with "The scan declares no TTL pulse per position"; it now has a simulated line. ``galvo_apd_mock_scan_setup.json`` lists the Laser widget, so its lasers are reachable from scripts, and its 488 laser has a simulated analog power channel.
- A scan the scan manager refuses now says why, to a script as well as in the log. When a design broke a limit -- longer than the setup's ``scan.maxScanTimeMin``, or voltages outside a scanner's range -- ``makeFullScan`` logged the reason and returned None, and the Base, PointScan and MoNaLISA scan controllers unpacked the None: the refusal surfaced as a ``TypeError`` traceback after the run had already been reserved and announced, and ``runScanAndWait`` raised only *Scan controller failed before the requested run armed.* The Advanced controller did not crash but lost the reason the same way. The manager now raises ``ScanDesignRefusedError`` with the reason, and a new run is designed before anything about it is published, so the refusal is a refused start: one log line, the reason on ``scanRejected``, and ``runScan()`` / ``runScanAndWait()`` raise ``ScanRequestRejectedError`` carrying it (*Scan would take 20.8 min, above the 1 min cap (scan.maxScanTimeMin).*). A repeat frame or axial follow-up whose re-design is refused fails its run, with the reason as the failure message, and scan-mode recording, which designs the scan to learn its layout, reports the reason too. Scan designers give it through ``signalLengthRefusal``; a designer that implements only ``checkSignalLength`` still works and gets a generic reason.
- The ImProcess *Crop/Substack* preview rectangle sits on the region it will crop. It was drawn in pixel indices while the image is shown in its physical units (``axis_scales`` as the layer scale), so on a calibrated result it came out ``1 / pixel size`` times too large -- ten times the image on a 0.1 µm/px camera, and a speck in the corner of a result calibrated in nanometres. The preview layer now takes the result's Y and X scales, and its outline stays two screen pixels thick at any pixel size, as the ROI overlay's does.
- ImScripting loads after every other module, as the launcher intended. The launcher moved ``imscripting`` to the end of the module list, then imported the modules from a fresh, unsorted copy of that list. A ``modules.json`` that named ``imscripting`` before another module built the script scope before that module existed, so its ``api`` entry was missing from every script.
- Closing ImControl no longer logs ``ERROR Scan failed`` on setups whose scan widget never ran a scan. The scan controller's ``closeEvent`` aborts unconditionally, and ``abortScan`` treated "no iteration running" as a failure; the same happened to every idle scan controller that received a broadcast abort from a recording. An abort now fails only a run the controller still holds between iterations (a repeat gap, a non-final sequence part, a MoNaLISA axial follow-up) or a request still arming; aborting a running iteration is unchanged.
- RS232 devices set up in the config editor no longer time out on every query. Choosing ``\r`` (or ``\n``, ``\r\n``) as a *Send/Recv Termination* saved the two characters backslash + ``r`` instead of a carriage return, so pyvisa never sent the device a line ending and waited for a reply ending in that backslash pair: a device that answered in a terminal program timed out in ImSwitch. The template now offers the real line endings, the combo box shows them as readable escapes (and an escaped value an older editor saved as a distinct ``\\r`` entry), and ``RS232Driver`` decodes an escaped termination already in a setup file, with a warning naming the key. ``RS232Driver`` also maps ``even``/``odd``/``mark``/``space`` parity and 1.5 stop bits, which the editor offered but which silently fell back to a mock port.
- ``MPBLaserManager`` starts with units that report fractional power limits (``GETPOWERSETPTLIM`` answering ``199.9 3050.0``). The reply was parsed as integers, so startup failed and the laser fell back to mock mode. Limits are now rounded inward -- minimum up, maximum down -- so every setpoint and ramp step stays whole-mW and inside the reported range.
- An ``AAAOTFLaserManager`` whose controller does not answer at startup (a pyvisa timeout) no longer aborts ImSwitch. The failed exchange propagated out of the manager and took startup down with it; the RS232 manager's mock port only covers a port that cannot be opened at all. The channel now sends a best-effort OFF and continues in mock mode, sending nothing further, controlled by the new ``useMockOnFailure`` property (default ``true``, as for the Cobolt and MPB managers). Configuration errors still abort startup, and a channel that stops answering after startup still reports the failure.
- The config editor opened from ImSwitch (*Tools → Edit hardware configuration…*) drew white device cards with light text. It chose its card colours from the application palette, which ImSwitch leaves light -- ImSwitch darkens itself with a qdarkstyle style sheet instead. The editor now also asks a style-sheet-polished widget, and inside a dark host puts its own theme on its window so it looks as it does standalone, at ImSwitch's font size.
- A raw scan volume larger than the detector chunk-queue budget is recorded again. The byte budget that replaced the 16-frame raw cap counted a scan-driven detector's whole assembled volume — one frame, published once per completed scan — against ``MAX_QUEUED_CONSUMER_BYTES`` with no exception for an empty queue, so any Z-stack over 256 MiB (1024 × 1024 × 128 uint16 is one) was dropped at publish and the recording consumer told it had *"fallen far enough behind"* on a frame it was never handed; the frame count it replaced had admitted any single frame. The budget bounds a backlog, and a delivery arriving to an empty queue is not one: it is now admitted whatever its size — the rule the writer's ``enqueue_frames`` has always applied on its side — and everything behind it stays bounded, so the next delivery overflows until it is read, exactly as before. A *delivery* is what one drain hands a consumer: one volume for a scan-driven detector, or a burst of many frames for a camera polled late, so the exception admits one delivery, which may be more than one frame. An oversized admission is said once per consumer, naming the setting, because no further backlog fits behind it at that queue; the overflow message quotes what was held and what arrived. The four acquisition shapes — a large single volume, small rapid frames, a burst after a late poll, and two detectors with a consumer that stops polling — now run under a stalled disk in a test suite that asserts on per-queue occupancy, which is the gate for any later change to queue behaviour.
- The ImProcess *PSF resolution* processor failed on every real image under NumPy 2 with "Unable to avoid copy while creating an array as requested": it asked for a no-copy conversion to float64, which NumPy 2 refuses for a uint16 or float32 camera frame instead of copying. Its own tests passed because they fed it float64 synthetic beads.
- TriggerScope RESOLFT recordings no longer arm for the wrong frame count on a missing or unreadable scan counter. ``roSteps``, ``cycleSteps`` and ``timeLapsePoints`` were each read as ``1`` when absent or non-numeric — by the frame expectation *and* by the layout builder, from two copies of the same list — so a recording could arm for a fraction of the scan with a ``recorded``, ``certain`` layout to match. One table now drives both, a bad counter is refused with its name, and the legacy SNOUTY adapter attaches ``cycleStepSizeUm`` to the cycle loop and ``roStepSizeUm`` to the plane loop exactly as fresh recordings do. LS-XY-RESOLFT recordings now count their X/Y raster in the frame expectation (they armed for a single raster position before) and carry no acquisition layout until the firmware's loop order has been traced on a rig, rather than a guessed one.
- A scan-mode recording of a detector the scan does not gate is refused at arm time instead of being written as a clean scan. The layout producer and the recording gate both defaulted a detector missing from ``getNumCamTTL()`` to one pulse per position, so their cross-check compared a default with itself; a free-running or mis-triggered camera was then recorded with a certain layout and marked complete, its surplus frames clipped without a word. Pulses per position are now declared or refused (``DETECTOR_PULSES_UNDECLARED``; a gated detector with zero pulses is refused too), the gate says when it cannot run the pulse cross-check, and frames delivered beyond the plan are counted, warned about once per detector, and written to the file as ``recording:discarded_frames`` so a reader can tell the recording is not the scan its metadata describes.
- A recording with an event loop a reconstructor does not handle is now refused with a message naming the loop, instead of being folded into the wrong pixels. Every layout consumer used to pick the loop kinds it knew and let the rest fall through its index arithmetic: a two-pulse Advanced scan gave MoNaLISA two frames per position with the second silently overwriting the first, the live reader sized a stack as ``scan_x x scan_y`` and ignored line-step conditions and a Z axis, BeadRec folded a time lapse into one raster, and SNOUTY took cycle and plane counts without checking they were in the order its restacking assumes. All of them now go through one imcommon helper, ``select_loops``, which places the loops a consumer has a role for and raises for any other — a *declared* layout is refused, an *inferred* one is declined so the older path still runs. Whether each registered loop kind advances the scan position is pinned in one table that a test keeps complete, so a new kind can no longer count as a position by default.
- Advanced-scan line-step recordings whose fast axis is not the X stage — a Z-piezo-only scan, or a scan driven Y-first — now record the correct frame order. The layout builder placed the line-step ``condition`` loop next to whichever loop was *called* ``scan_x``, while the designers repeat each fast-axis *dimension* per condition regardless of which stage drives it; once the physical-axis override renamed a Z-only or Y-first dimension 0, the condition loop landed innermost or one level too far out, with every frame count still adding up. Placement and per-line mask arithmetic are now keyed on the ScanInfo dimension index. A test reads the analog positions at every camera TTL edge of both designers' waveforms and checks the layout against them.
- A scan axis configured with ``isPositiveDirection: false`` no longer reconstructs as a mirror image in one reconstructor and correctly in another. The acquisition layout carried the negative direction twice — as the loop's physical ``direction`` and, redundantly, as a ``reverse`` traversal — and consumers disagreed on how many times to apply it: MoNaLISA classic flipped twice, BeadRec and the scan dialog once. The rule is now settled in the contract: traversal is chronology only (a monotonically stepped axis is always ``forward``; ``reverse`` is a genuine retrace), ``direction`` is the orientation of a loop's index axis against the physical axis and is applied exactly once by one imcommon helper, and every consumer that places frames by metadata takes its coordinates from that helper. The seam test puts a negative-direction recording through MoNaLISA placement, BeadRec placement and the scan-dialog path and asserts every frame lands in the same pixel. The Fast Gauss and live paths orient from the data instead (their eight candidates already include every mirror) and now cross-check that detection against the layout, warning on disagreement and recording the orientation they actually used in the result instead of ``+`` placeholders. The scan-parameters dialog also stopped setting all three direction combos from the first axis, which silently turned a pre-filled negative Y back into positive on OK. No recorded file outside the test suite carries a layout yet, so nothing needs migrating.
- Fast Gauss MoNaLISA and the live MoNaLISA session reconstruct line-step scans correctly again, from the acquisition layout. Main's fix for the 648-frame 18x18x2 regression (``2463e9d6``) had not reached the layout branch, and the layout path itself *declined* any layout with line-step conditions and fell back to an attribute ladder that sized stacks as ``nx * ny`` — so every legacy line-step file still came out as two 324-frame time blocks, while the classic method, which places frames by their recorded coordinates, was right. Both fast paths now take the condition count from the layout — recorded or inferred by the legacy adapter, the two must agree — when conditions are interleaved per line, which is the order the Advanced scan records; a recording that declares one complete image per condition is still refused rather than reshaped. The MoNaLISA scan dialog fills ``n_linesteps`` and shows ``T = timepoints x conditions``, which is how the reconstruction reads it back.
- ImProcess starts again. The scan-parameters dialog keeps one direction combo per axis since the direction fix and reads three directions, while ``ScanParamsController``'s default dictionary still carried two -- an ``IndexError`` in a constructor, on every start, and the half-built main controller then failed a second time in ``closeEvent`` so the error on screen named the wrong thing. The default has three entries, the dialog fills missing axes from the first entry as it always did, and the main controller initialises its state adapters before anything that can fail.
- A FLIM recording saves the finished lifetime image, not the first preview. The Swabian TimeTagger manager declared itself scan-driven but inherited the camera defaults for the raw-frame contract, so a scan-once recording -- planned for exactly one frame -- was satisfied by the worker's first live preview one second into the scan, and closed as *complete* with the rest of the lines still zero and no log line anywhere. It now defers its raw frame like the APD and PMT do: the raw stream stays empty until the worker's final frame lands, yields it exactly once, and an aborted scan yields nothing. A mid-scan save request raises ``RawFrameUnavailableError`` instead of returning a half-filled image.
- The FLIM histogram window spans one laser period unless declared. ``n_bins`` defaulted to 64 while ``binwidth_ps`` defaulted to 32 and ``laser_rep_rate_mhz`` to 80 -- a 2.048 ns window against a 12.5 ns period, in the same constructor -- and a decay cut off at a sixth of its period reads as a short lifetime: the ``moment`` and ``phasor`` fits reported 0.84-0.95 ns for anything from 2 to 6 ns, plausibly, with the intensity image looking right. Undeclared, the window now covers the declared period (391 bins at 80 MHz / 32 ps); a declared window shorter than 80 % of it is warned about at startup and whenever the rate is changed at runtime.
- Real APD photon counts are no longer clipped to ``mockPhotonCountMax``. The synthetic generator's ceiling was applied to every pixel on the live NI-DAQ path too, so a bright feature at a long dwell -- 10 ms at 1 Mcps is 10 000 counts -- came back flat-topped at exactly 5000, indistinguishable from detector saturation and adjustable only through a key named for the mock. The ceiling now applies in simulation only.
- The HDF5 ``recording:completion_outcome`` attribute is as wide as its vocabulary. It was created as a literal ``S13`` -- the length of the longer of the two outcomes that existed -- and HDF5 cuts a longer value to the attribute's width without a word, so a future ``stopped_early_on_stall`` would have been stored as a valid, wrong ``stopped_early``. The width follows ``VALID_COMPLETION_OUTCOMES``, and a fixed-width string attribute too narrow for its value is recreated rather than truncated.
- Four camera managers whose drivers were never bundled are gone: ``BaslerManager``, ``GXPIPYManager``, ``ESP32CamManager`` and ``JetsonCamManager`` imported interface modules that do not exist in this tree (upstream deleted them in 2022), so every one of them could only ever construct the synthetic ``MockCameraTIS`` -- and two of them then returned a four-dimensional chunk that broke the ``(frames, Y, X)`` broker contract. ``AVManager``, which shares the same fate, stays as the shipped no-hardware camera and is now labelled as such in the catalog, its docstring, the docs and the README's minimal setup, rather than as a "generic video detector".
- ``PhotometricsManager`` has a mock of its own and one trigger table. Its fallback handed the manager a ``MockHamamatsu``, which answers none of the PVCAM surface it reads, so a rig without ``pyvcam`` failed one line after the "loading mocker" warning and took the whole imcontrol module down with it; ``"cameraListIndex": "mock"`` -- documented as supported -- was never honoured. ``MockPhotometrics`` answers that surface and is trigger-aware. The trigger source had a write map and a read-back map that disagreed on two of three values, so selecting a start-trigger displayed as a frame-trigger after the next exposure change; there is now one table of PVCAM extended-trigger codes with the read-back derived from it, and an unrecognised code is reported rather than guessed. **Behaviour change to confirm on a camera:** ``External "frame-trigger"`` now programs ``EXT_TRIG_EDGE_RISING`` (2304, one exposure per rising edge) where it used to program ``EXT_TRIG_LEVEL`` (2560, exposure lasts while the line is high).
- A Thorlabs TSI camera keeps its ring-buffer depth across trigger-mode changes. The re-arm read ``frames_per_trigger_zero_for_unlimited`` -- a different quantity that happens to be a small integer, set to 1 at open -- as the buffer depth, so the first Operation Mode change (which every startup makes while restoring the saved detector state) shrank the SDK ring from four frames to one for the rest of the session, and any latency spike longer than one frame interval dropped a frame silently. The depth armed with is remembered and re-used, and it is a manager property, ``frameBufferDepth`` (default 4).
- Point detectors take their sample clock from the NI-DAQ manager. The APD and PMT managers hardcoded ``ctr2InternalOutput`` and 1 MHz while the setup file chose which counter generates the timer pulse train, so a rig whose timer is any other counter clocked its detectors from a terminal nothing drove -- and with ``timerCounterChannel`` unset, which six of the seven shipped setups have, no pulse train existed at all while the detectors still waited for one. The manager derives the terminal (``/Dev1/Ctr2InternalOutput``) and its rate from the configured counter, both detectors read them from it, and a point-detector scan without a configured timer counter is refused at start with a message naming the setting. The galvo phase delay is converted from microseconds to detection samples at that rate rather than assumed equal to it.
- The NI-DAQ scan clock is stated once. Its 100 kHz was a literal at eight sites while ``scan.sampleRate`` was a required config field every designer, the simulator and the detectors honoured: a setup declaring another rate had its waveforms built at that rate and played out at 100 kHz, so the scan ran slower by the ratio with its metadata claiming the requested timing -- and a long enough scan was aborted by the recording watchdog as a detector stall. ``SCAN_CLOCK_RATE_HZ`` and ``TIMER_COUNTER_RATE_HZ`` are declared once, and on hardware a ``scan.sampleRate`` other than 100 000 is refused at construction.
- A point-detector read waits as long as the read needs. ``readInputTask`` inherited nidaqmx's 10 s timeout, so a fast-axis line longer than ten seconds -- an ordinary long dwell -- failed every read with a driver error naming neither the dwell nor the line, and the assembled volume was never published. The timeout is derived from the task's own sample clock: twice the read's expected duration plus the driver's default as a floor.
- The PMT's analog-input range reaches the driver. ``__createChanAITask`` accepted ``min_val``/``max_val`` and dropped them, so every PMT channel ran at nidaqmx's own +-5 V -- a preamp swinging further was clipped flat with no error. The range is passed through, defaults to that +-5 V so no rig changes silently, and a PMT declares its own with ``aiVoltageMin``/``aiVoltageMax``.
- TriggerScope firmware scans are checked against the axis's declared DAC range. The board ramps the DAC autonomously from wherever the axis is parked, and the excursion uploaded to it was compared with nothing, while the same axis jogged through the GUI is clamped to ``minVolt``/``maxVolt`` with a warning. Every ramp's far end and every fixed voltage in the raster, pLS-RESOLFT, galvo-detection, multicolor and LSXYR modes is now checked before upload, and a scan past the range is refused with the voltage, the axis and the range.
- The Beta stage designer's move and settle are declared, and bound the dwell. A 2 ms ramp and a 2 ms settle were literals inside the pixel loop, occupying the end of every dwell window: below a 4 ms dwell they folded back over the previous pixels (the panel's default dwell was 1 ms -- press Run and the stage visited the wrong places), and between 4 and 20 ms a camera exposing for the whole dwell integrated the move. They are now ``move_time``/``settle_time`` in ``scanDesignerParams``, a dwell not longer than their sum is refused, a dwell that is mostly motion is warned about, and the stage panels open at 10 ms. The ``maxScanTimeMin`` cap, read by the Galvo designer alone and declared only by setups using the Beta one, is now honoured by every scan manager.
- The point-scan delays are times in microseconds, seeded from the setup file and restored on load. The *D3 step delay* field said "(samples)" while the designer consumed it as microseconds (a tenth of the settling at 100 kHz), and the phase delay -- the galvo's response lag, a rig calibration -- was a widget literal that differed between the two panels (100 in Point Scan, 0 in Advanced) so the same galvo produced fast-axis-shifted images from the two panels; the Advanced panel never restored the value on load, so a calibrated delay came back as 0 after every restart and overwrote the saved one on the next scan; and a blank or comma-decimal entry became a silent 0. Both panels now label the fields in microseconds, open at 0, seed from ``scanDesignerParams.phase_delay``/``d3step_delay``, restore both values on load, and a garbled entry is an error.
- ``focusLock.updateFreq`` is documented as what it is: a rate in hertz. It was documented in milliseconds and consumed as hertz, so ``100`` meant 100 Hz rather than every 100 ms and anything above 1000 asked for a sub-millisecond timer. The setup refuses a non-positive rate, the timer is floored at 1 ms, and the reacquisition deadline is derived: ``reacquireTimeoutS`` (the settle allowance) plus the sample window ``reacquireSamples / updateFreq``, which the old deadline did not include -- at 5 Hz a five-sample window needs a second on its own, so the lock gave up on every tile of a tiling run.
- Autofocus reads a frame that started exposing after the move. It slept a hardcoded 150 ms and read the newest buffered frame, which with an exposure longer than that belonged to the previous Z position: every focus metric one sweep step off, the vertex fitted through them, success reported. The settle is ``autofocus.settleTimeMs`` (default 150), and the frame comes through the fresh-frame handshake tiling already used -- open a boundary, require two frames past it -- now shared between the two.
- A camera whose pixel size is assumed says so, and files can tell. ``cameraPixelSizeUm`` omitted from the setup file fell back to 0.15 µm silently, and the placeholder went into every recording's OME PhysicalSize, the scale bar and the napari layer scale looking exactly like a measured calibration; no shipped setup declares it. Startup now warns once per detector, and a ``Camera pixel size source`` parameter (``setup file`` / ``assumed default`` / ``user``) is recorded next to the value and flips to ``user`` when it is edited.
- ImProcess display reductions are bounded by what they would allocate. The Data panel's mean preview read every plane of a virtually loaded recording on the GUI thread; it now averages at most 256 planes at an even stride. The contrast gate counted elements (64 Mi) while the cost it gates is bytes -- a float64 copy, a finite mask and a compacted result per element -- so a 16-frame 2048x2048 uint16 stack, exactly at the threshold, paid a ~1 GiB transient for two numbers on the slider; the gate is now a working-set budget in bytes.
- Four smaller shapes of the same defect: BeadRec declares that the scan loops it measures with must be calibrated, so a layout without a physical step is refused rather than fitted at a pixel size of 0; an ImProcess processor without a stable ``id`` fails at class definition instead of loading as ``unnamed`` and defeating the duplicate-id guard; the live stall watchdog is opt-in per continuously streaming source rather than switched off by a flag each new source author had to remember; and a pulse generator's ``stop()`` raises ``TimeoutError`` when its worker outlives the join instead of returning as if it had stopped.
- Streaming HDF5 and Zarr recordings are chunked by size rather than by a frame count. The on-disk chunk was 32 frames deep because the writer batches 32 frames, and the two are different jobs: a chunk is what a reader must decompress to reach any one frame in it, so its *size* is what matters. Thirty-two frames is 100 kB for a small ROI, 256 MiB for a 2048x2048 camera — larger than any default chunk cache, so scrubbing the frame slider over a virtually loaded recording re-inflated the whole chunk for every frame, a ~30x read amplification — and thirty-two whole assembled volumes for a point detector, which the SWMR-compatible HDF5 file format refuses outright once a chunk reaches 4 GiB: a 512x512x256 uint16 scan could not be recorded at all, with an error naming an HDF5 file version rather than the scan. The depth is now derived from ``TARGET_CHUNK_BYTES`` (4 MiB) and the frame's own size, capped at the write batch: a small ROI still gets a full batch per chunk, a big camera one or two frames, a point detector's volume exactly one. Nothing has to be declared. ``WRITE_BATCH_FRAMES`` keeps its one meaning — how much the writer accumulates before a write — and no longer decides how the file is laid out.
- A live source's ``poll()`` hands back at most ``LIVE_POLL_MAX_BYTES`` (64 MiB) of frames per call. It used to return every unread frame in one call, and the lapse sources walked every timepoint in that same call, so switching live reconstruction on over a folder holding a finished recording materialised the whole recording before its first chunk was processed — in the streaming path, whose reason to exist is bounded memory. The cursor stays where the budget ran out and the next poll continues from there; it is the read-side twin of the detector queue's byte budget, and as there, the frame count follows from the frame.
- A point-scan recording refuses a camera pulse declaration the tiled TTL signal contradicts. ``getNumCamTTL()`` counts a detector's rising edges in one TTL cycle and calls that its pulses per scan position; for the point-scan designer one cycle is the decoded sequence, which spans several positions unless the sequence pulses on every step — ``h1,l1`` on the fast axis fires once per two positions, ``h2,l2`` once per four. The recording gate and the acquisition layout built from that number then expected frames the camera would never send, the recording sat waiting until the stall watchdog stopped it early, and the embedded layout described a scan that was not run. The Advanced scan path already cross-checked its layouts against the final tiled signal; the point-scan path now does the same, and the message names the detector, the planned frame count and the edges actually programmed.
- A scan waits long enough for its recording to open the file. The scan controller gave the recording 5 s to report armed, while the worker inside that wait gives the writer 30 s to create the file — so a file open that took longer than five seconds (a network share, a folder with a few hundred recordings for the name to number past) was reported as *"detectors did not report armed"*, the writer's own deadline could never be reached, and the abort that followed still blocked until the open it had given up on returned. The arm wait is now stated once, as the writer's open budget plus the detectors' own 5 s, and the failure message says which of the two was allowed how long.
- A slow camera is no longer declared stalled for being slow. The stall watchdog was a flat ten wall-clock seconds, sized for a camera that frames every few seconds, so a 30 s luminescence exposure — routine, and within what the Orca-Quest and Zelux will do — was killed at frame zero as stalled, its file deleted, and the failure blamed on scan TTL wiring in a mode that has no scan. The allowance is now the larger of that floor and three of the detector's *own declared* frame intervals, read from the same exposure or frame-interval parameter the OME metadata already uses. A detector that declares nothing keeps the floor exactly as before: the OME metadata substitutes one second when nothing is declared, and that placeholder is deliberately not used here, since it would have handed every undeclared detector an allowance it never earned. The message in a non-scan mode now points at the exposure rather than at ``numCamTTL``.

- Frames reach disk on time, not only on count. A write batch flushed only when it held 32 frames, so how stale the file on disk could be was 32 divided by the frame rate — 3 ms on a fast camera, 32 s at one frame per second — and a recording shorter than the batch had no dataset on disk at all until it finalized, so a live reader watched an empty file for the whole of a slow acquisition. A batch now also flushes once it has waited ``WRITE_FLUSH_MAX_LATENCY_S``. Count still decides how large a write is; time decides how late it may be.

- The mock Hamamatsu camera declares a frame interval of 0.1 s rather than 10 s. It hardcoded ``internal_frame_interval`` to the same number as its 10 fps rate, in a field DCAM reports in seconds, so anything that trusted the declared interval — the OME time axis, and now the stall watchdog — believed the mock framed once every ten seconds while it delivered ten a second.

- Shutting a recording down waits for a writer that is still writing, instead of for thirty seconds. The drain had a fixed deadline, which together with the queue budget asserted a disk throughput nobody declared — roughly 17 MiB/s — and missing it was not a warning: the caller raised, cleanup aborted, and the abort **deleted a recording whose frames had all been captured**. A NAS, a busy share or a spinning disk could lose a finished acquisition at the finish line. Progress is what is waited on now: while the writer is consuming queued chunks and writing batches it gets as long as it needs, and only a writer that does nothing at all for ``WRITER_STALL_TIMEOUT_S`` is declared stuck — with ``WRITER_FINALIZE_TIMEOUT_S`` covering the storer's single finalize call, which reports no progress of its own, and an abort keeping a fixed bound since it discards the output anyway.

- A chunk consumer that has fallen behind stops costing the consumers that have not. Bounding the queue by memory made it hold tens of thousands of small frames, and the over-budget trim removed them one at a time — each removal shifting the whole remaining queue — on that drain and every drain after it, inside the lock every other consumer needs to read its own frames. Once a consumer is over budget its stream is incomplete however much is kept, and nothing retained for it can ever be returned to it, so the queue is released in one go and skipped until the consumer is restarted or released. Its next read still fails rather than accepting a gap.

- Deriving the size of one time point no longer walks a whole gated acquisition. The branch taken when a detector is gated — which is the configuration the recorded-span machinery exists for — still tallied every recorded frame, on the live reader's ``open()`` before a single frame is read: 1.4 seconds on a two-million-event scan. Time is outermost by then, so one time point's frames are consecutive; counting the first and checking it divides the total gives the same answer in about a millisecond, and an uneven gated selection is still refused.

- The recording writer's buffer is bounded by memory too, so it holds what its size implies. ``WRITER_QUEUE_MAXSIZE`` bounded the queue at 64 *items*, and an item is whatever one poll returned — at the 0.1 ms poll interval that is about one frame, so the buffer meant to absorb a disk or compression hiccup was 64 frames: seven milliseconds on a fast camera rather than the seconds the number suggests, and *shorter* than the detector-side budget downstream of it, so a recording could not use its own buffer. It is now ``WRITER_QUEUE_MAX_BYTES``, applied by the producer against the bytes actually in flight. A single chunk larger than the whole budget is admitted rather than waiting for room that can never appear, and the queue no longer has to be an item-bounded container at all, so the shutdown sentinel cannot be blocked by a full queue and never has to displace queued frames to get in.

- The live view no longer hands a stalled recording its whole backlog at once. Every drain of the hardware queue fans out to every registered consumer, so a 300 ms live-view tick on a fast camera pushed hundreds or thousands of frames into a recorder's queue in one go — while the recorder was blocked on its writer and could not take them. The frames are the recorder's to have, but they can wait in the driver's buffer instead of being counted against a budget the recorder cannot currently spend. A display read now reuses the latched frame when another consumer has drained since it last looked, and drains for itself when nothing else is draining, so a blocked recorder cannot freeze the view. The save path is unchanged: a snap still forces a drain, because it wants the newest data rather than the freshest available one.

- A detector's chunk queue is bounded by memory rather than by a frame count, so no detector has to declare which category it belongs to. The two hand-picked counts — 1000 frames for a display consumer, 16 for a raw one — bounded nothing: the same number is 3 MB for a 76x20 crop and 8 GB for a full sensor, which is why 16 frames was a 1.7 ms deadline on a camera running at 9338 fps and a gigabyte-and-a-half allowance on a point detector's assembled volume. Choosing between them per detector fixed the number but kept the trap, since every new detector then had to remember to categorize itself correctly. The queue now holds ``MAX_QUEUED_CONSUMER_BYTES`` worth of frames, counting each frame's pixels plus its object overhead, and the number of frames that buys follows from the frames themselves: tens of thousands for a fast camera on a small ROI, tens for a full sensor, a handful for a large volume. ``rawFrameIsDeferred`` keeps its one honest job — telling "the scan has not finished" apart from "go and fetch it" on the save path — and no longer decides a memory budget. The overflow message quotes the budget in MiB and how many frames that was for the detector that tripped it.

- Camera scan recordings no longer abort after a sixteen-frame hiccup. The recording worker registers its chunk consumer as ``ChunkKind.RAW`` for every detector it records, and the raw queue cap ``MAX_QUEUED_RAW_FRAMES = 16`` — sized for point detectors, whose raw frame is a whole ``S x Nz`` volume published once per completed scan — was selected by that kind alone. A camera's raw frame *is* its display frame, one per exposure, so every camera scan recording since the raw chunk contract landed had sixteen frames of slack: one writer or disk stall longer than that, with the live-view poller filling the queue meanwhile, aborted the run with *"fell behind by more than 1000 frames; its stream is incomplete"* — the message quoted the display cap whatever the kind, which is why the one field report of this (a Snouty pLS-RESOLFT multicolor scan) read as a catastrophic backlog rather than a two-second stall. The cap is now chosen by ``rawFrameIsDeferred``, the property that actually says "one fat frame per completed scan" and is true only for the APD and PMT, so cameras keep the ordinary 1000-frame budget and point detectors keep 16. The exception quotes the cap that tripped and names the detector. ``enqueue_frames`` warns when the acquisition loop has been blocked on a full writer queue for longer than ``PRODUCER_STALL_WARN_S`` (1 s), and again when it resumes, so a stall is reported as itself rather than only through its consequence. The tests now model a camera-shaped raw consumer beside the scan-driven one, and one test binds the recording worker's consumer key to the cap it is subject to — the seam the defect lived in, which neither test file had referenced.
- The ImProcess contrast widget and every tool built on the "active image layer" accessor no longer raise on a layer whose ``data`` is not an array. A point-cloud layer has ``contrast_limits`` and a ``data`` holding a tuple of geometry arrays, so attribute presence alone let it through to code that then took the tuple's min and max straight out of a button handler. Non-image layers are skipped; the check is now whether the data really is an array.
- Clearing an embedded napari viewer's layer list no longer hangs the process. ``EmbeddedNapari`` protects the base image layer by having deletion quietly skip it, but ``layers.clear()`` is a ``pop()`` loop that stops only when the list raises ``IndexError`` — which a list that keeps its protected layer never does, so the call spun forever at full CPU. Nothing in ImSwitch called it until the point-cloud viewer's tests did, and the hazard was there for any caller. ``clear()`` now removes every unprotected layer and returns.
- A second napari viewer could not be built in a process that had already made one. The guard against re-registering the ``grayclip`` colormap used ``hasattr`` on a dict, asking whether it had an *attribute* of that name, which was always false — so registration ran every time and raised on the second.
- Saving an ImProcess result as TIFF no longer discards everything except the pixels. It was ``tifffile.imwrite(path, data)``: no pixel size, no axis labels, no metadata of any kind. A cropped reconstruction reopened as an anonymous array, and the calibration — known at every point up to the moment of writing — was lost at the one place it cannot be recovered from. Two related faults are fixed with it: the toolbar's own operations (crop, projection, split, merge, calculator) passed neither source nor processor when normalising their output, so results made from the toolbar carried no provenance at all where the same operation run from a panel did; and the writer let ``tifffile`` infer what the samples were, which reads a trailing axis of size 3 or 4 as RGB — so a crop four pixels wide was written as a colour image, and with OME metadata attached the write failed outright.

- A mask made in the ROI manager can be applied to the image it was drawn on. Two separate refusals stood in the way. The **Image calculator** accepted only ``image`` results, and a mask is published as ``labels``, so it was never offered — but the kind gate is there to keep a metrics table away from an image processor, not to stop a mask reaching its own image, and a label image is numbers on the same grid. Once offered, the calculator refused the pair anyway: it reused the *stacking* compatibility check, which demands identical shapes, so a ``(1, 233, 233)`` result and a ``(233, 233)`` mask — the same picture — were called incompatible. Stacking has to be that strict, since it builds one array; arithmetic only needs the operands to line up. Element-wise operations now use numpy's own rule, with one restriction: the result must be one of the two inputs, so a 233x1 column and a 1x233 row are still refused rather than broadcast into a 233x233 image neither of them contains. Axis labels and pixel scales are compared only on the axes both inputs actually have, and a ``px`` result still combines with a calibrated one while µm against nm does not. The same check now decides both whether the operation is offered and whether it runs, so the two can no longer disagree.

- ROI outlines are drawn two screen pixels thick on every image, instead of two pixels times the pixel size. napari measures a shape's edge width in *data* units and multiplies it by the layer's scale and the camera zoom; the overlay divided by the zoom alone, so the two zoom terms cancelled and the on-screen thickness came out as ``2 x pixel size`` at every zoom level. That is right by accident on uncalibrated data, invisible on a 0.1 µm/px camera, and two hundred screen pixels of outline on a 100 nm/px result calibrated in nanometres — which is most super-resolution data. An ROI's own ``stroke_width`` is now honoured as the screen pixels it was documented to be, rather than as a data-unit width meaning something different on every calibration, and zooming rescales each ROI's width separately instead of collapsing them onto one. The width is set from *Sets > Default appearance…* for a whole set or *Properties…* for a selection; napari's own layer controls cannot change it, because the overlay is a managed read-only layer re-rendered from the ROI records — the same property that stops a dragged vertex from silently desynchronising them.

**Behaviour Changes**

- A positioner no longer moves to 0 when ImSwitch2 closes unless its setup entry says ``"resetOnClose": true``. The default was ``true``, so every stage whose entry did not mention the key drove itself back to zero on exit, where it could meet an objective, a sample or a limit nobody expected; every shipped mock setup already set it to ``false`` by hand. A setup that relies on the reset now has to ask for it.
- The scripts folder is reorganised: ``tutorial/basic`` and ``tutorial/scanning`` replace ``example_import.py``, ``example_imported.py``, ``example_record.py`` and ``example_scan_power_series.py`` (each is now a tutorial step that runs on a mock setup), and the rig workflows moved to ``workflows/wfs`` and ``workflows/timeresolved``. An existing scripts folder is brought in line at the next start: untouched copies of the removed scripts go to the trash (see the next entry), edited ones stay.
- The default files ImSwitch copies into ``~/ImSwitchConfig`` (example and mock setups, scripts and tutorials, ``config/modules.json``) are brought up to date at every start. They were copied once and never touched again, so an update never reached them: a reviewer's old ``hamamatsu_mock_scan_setup.json`` lacked the camera trigger line the scanning tutorials need. ImSwitch now ships the hash of every version it has ever shipped of each default (``imswitch/_data/user_defaults_history.json``, regenerated with ``tools/update_user_defaults_history.py``; a test fails when it is stale). A copy that matches an older shipped version was never edited and is replaced by the current one; a copy with any other content -- edited by you, or saved by ImSwitch -- is kept, and the log lists the ones that differ from the current version. An untouched copy of a script ImSwitch no longer ships is moved to the trash; setup and SLM files are never deleted, since a rig's options may name one. Line endings are ignored, so a CRLF copy of a version still counts as untouched.
- A fresh install loads ImProcess and ImScripting beside ImControl. The ``modules.json`` shipped in ``_data/user_defaults`` listed only ``imcontrol``, and because it is copied into ``~/ImSwitchConfig/config`` before the code-level default is consulted, that default (``imcontrol`` + ``imscripting``) never applied: a new user saw one tab and no sign of the other two. Both now list ``imcontrol``, ``improcess`` and ``imscripting``. An existing ``modules.json`` that was never changed is updated to the new default at the next start (see the next entry); one that was changed is kept, and **Preferences → Set active modules…** adds the others.
- Imswitch2 is published on PyPI as ``imswitch2``: ``pip install imswitch2``. ``ImSwitch`` on PyPI is the upstream project, and both install the same ``imswitch`` package, so every install hint that named ``imswitch`` — the NI-DAQ, Thorlabs TSI, OpenCV and napari-storm messages, the update dialog's upgrade command — would have fetched upstream's 2.0.0 and overwritten this one; so would the example device plugins, which required ``ImSwitch>=0.1`` and now require ``imswitch2``. The command (``imswitch``) and the import package are unchanged. The update check asks PyPI about ``imswitch2`` and GitHub about ``Imswitch2/Imswitch2``, and the About and update dialogs link there instead of upstream's repository. ``test_distribution_identity.py`` fails if setup.cfg and ``imswitch.__distname__`` disagree, or if an install hint or example plugin names the old distribution. Releases are uploaded by ``.github/workflows/imswitch-pypi.yml`` through PyPI Trusted Publishing, with no API token; the file's header lists the one-time PyPI setup and the release steps.
- A fresh install loads ImProcess and ImScripting beside ImControl. The ``modules.json`` shipped in ``_data/user_defaults`` listed only ``imcontrol``, and because it is copied into ``~/ImSwitchConfig/config`` before the code-level default is consulted, that default (``imcontrol`` + ``imscripting``) never applied: a new user saw one tab and no sign of the other two. Both now list ``imcontrol``, ``improcess`` and ``imscripting``. An existing ``modules.json`` is left alone, so an older config folder keeps the modules it names; **Preferences → Set active modules…** adds the others.
- ImProcess *Projection* now requires a stack, as ImageJ's *Z Project* does. It used to accept a 2D image and collapse one of its two displayed axes, leaving a one-axis profile that the viewer could not draw (napari raised on every cursor move afterwards) and the TIFF writer could not store. A workflow whose projections resolve ``Auto`` on a result with fewer stack axes than the one it was recorded on is now refused at that step, with the offered result's axes and shape in the message, and the other rows of a batch run on. The viewer, its napari widget, the napari endpoints and the TIFF writer also refuse a result with fewer than two axes outright, whatever produced it, so no path can leave napari's image layer holding data it cannot draw.
- **ROI standard deviation is now the sample standard deviation** (``ddof = 1``), matching ImageJ, and a single-pixel ROI reports ``NaN`` rather than ``0``. It was the population form (``ddof = 0``), so every ROI standard deviation ImSwitch has reported was smaller than the figure ImageJ gives for the same region — by ~12% for a 5-pixel ROI (1.118 becoming 1.291), and by less as the region grows. Nothing else about the numbers changes. This affects the ROI manager, the ROI statistics panel, and anything reading ``ROIStats.std``; there is one definition now, in the measurement registry, which the legacy helper is a view onto.

**Bug Fixes**

- A MoNaLISA reconstruction keeps the contrast you set on it. Selecting a result ended by applying its whole-result ``display_levels`` to the viewer -- unconditionally, after the render had already put the right levels on screen. For a result whose contrast lives on the result itself that is a no-op; for one that renders display layers and keeps its contrast per component it overwrote what had just been restored. MoNaLISA's reconstructor measures the 1st and 99.9th percentile at construction and stores it there, so every fast-Gauss reconstruction came back at that measurement each time it was clicked, however many times its contrast had been adjusted -- and the viewer then recorded the overwrite as the result's contrast, so the setting was not merely ignored but lost. The render is now the only thing that applies levels. A producer's own ``display_levels`` still seeds the first layer the first time the result is shown, which is what it is for; once that layer has a contrast of its own, that wins.
- ImProcess scales a result and a duplicate of it to the same contrast. A MoNaLISA reconstruction renders through the display-layer path, which clips the outermost 1% at each end; a duplicate of it renders through the plain-image path, which spanned the full data range. On a fast-Gauss reconstruction with a few hot pixels those are not subtle variations of each other, so clicking between the two looked like the viewer was re-contrasting on every switch even when both were showing their correct defaults. Automatic scaling now follows the same 1%-per-tail rule whichever path renders it, with the slider still spanning the full range so it can be dragged past the clip.
- ImProcess remembers the contrast each result was last shown with, so two reconstructions of the same field can be compared. Setting a contrast on one, a contrast on the other and clicking back rescaled the first to its own data again, which is precisely the comparison it was set up for. Two faults, both of them a question of *when* the contrast was read back. It was read when the selection moved, so anything that re-rendered without the selection moving -- re-running a reconstruction, switching view, any toolbar operation -- overwrote a setting that had never been saved; the levels are now recorded on the change itself, from the layer that changed, whether that was our own toolbar or napari's slider. And for a result rendering several layers (a MoNaLISA reconstruction renders one per base) only the *active* layer's levels were kept, while every layer's colormap and visibility were -- so a layer adjusted after selecting it in napari's layer list came back at its own 1-99 percentile range every time. Two smaller things fall out: the previously-shown result is now held by reference rather than by list index, so removing a result can no longer file one result's contrast under another's; and a result shown for the first time is scaled to its own data instead of inheriting the previous result's levels, which was at its worst exactly when the two were being compared because their ranges differ.
- The ImControl window no longer opens taller than the screen, cropped at the bottom until it is maximized, restored and maximized again. Docks stack vertically and a splitter's minimum size is the sum of its children's, so a panel pinning its own minimum height added that figure to the smallest size the *whole window* could take -- and rearranging docks recomputed the sum, because two panels stacked in one column add their heights where side by side they did not. A laser column (320 px), a scan panel and a TriggerScope panel (200 px each) in one column were already most of a screen. Every one of those panels scrolls its own contents, so the minimum was doing nothing for the panel and everything to the window; it is gone from Laser, ScanWidgetBase, Console and the six TriggerScope / light-sheet panels, which takes the example STED profile's window minimum from 999x649 to 1105x383. Dock insertion is unchanged -- a dock-level scroll wrapper was tried before and rejected for perturbing dock proportions -- so existing layouts open exactly as they did. A contract test keeps new panels from reintroducing one.
- The recording output folder is no longer remembered between sessions. It is built from ``recording.outputFolder`` plus today's date, so saving it into the widget state pinned every later session to the day the state was written — reopening ImSwitch on Tuesday put Tuesday's recordings into Monday's folder, which is exactly the filing the dated default exists to avoid. Restoring it also warned that the folder no longer existed, a warning that was never actionable: snapping and recording both create the folder on demand, so a missing dated folder is the normal case rather than a fault. The folder is session-scoped now, and a ``recFolder`` left in an older state file is ignored without comment.
- Stopping a script no longer freezes ImSwitch. ``ScriptExecutor.cancel()`` joined the script thread with no timeout on the GUI thread while the script had no way to notice the request, so a script stuck in ``getWaitForSignal`` (or any wait) plus Stop, Run or closing the window greyed out the whole application until it was killed. Cancellation is now cooperative and delivered exactly once: every ImSwitch-provided wait raises ``OperationCancelled``, ``finally`` blocks then get a 30 s cleanup window in which waits and API calls work normally (so a recording can still be stopped), and a script that never reaches a cooperative point is interrupted with an injected exception after 2 s. Stop returns immediately and shows *Stopping…*; Run while a script is stopping starts the new one only after the old has ended.
- A script could hang forever waiting for ``scanEnded`` when the scan start had been silently refused (a scan still running or still finishing): ``_beginScanRun`` and the TriggerScope start gate returned with only a log line. Every refusal is now published on ``sigScanRequestRejected`` and ``runScan()`` raises.
- ``changeScanPower`` (and ``loadSetupMode``) ran on the script thread and updated Qt widgets from there, undefined behaviour that can freeze or crash intermittently. Both are UI-thread exports now; a static tripwire test catches any other off-thread export that reaches a widget.
- A ``runScan`` request during a running scan on the workflow dispatch path could publish a ``scanEnded`` for the *running* scan; the API dispatches through the pre-flighted path, which refuses before any lifecycle signal.
- Closing ImSwitch while a script runs no longer tears hardware down underneath it. ``launchApp`` runs a ``prepareShutdown`` phase before any module's ``closeEvent`` (imscripting first: it closes the API gate and drains the script thread with a 10 s cap); if the script cannot be stopped, imcontrol skips hardware-manager finalization exactly as it already does for undrained controller workers, and the process exits without finalizers.
- Six TriggerScope/LightSheet scan controllers overrode ``runScan`` without re-applying ``@APIExport``, which silently dropped the export on those setups; the scan API is now owned once by ``WorkflowFacadeController`` and a discovery test guards every inherited export against undecorated overrides.
- Stopping a long recording no longer freezes the GUI for 30 seconds and then deletes the file. Unchecking REC waited on the GUI thread for the recording worker, and the worker gave the writer a fixed 30 s to drain its queue (up to 64 chunks of full-size camera frames, gigabytes on a slow disk) before aborting and discarding the partial output. REC-off now returns immediately and the worker's own ``recordingEnded`` resets the controller; the writer drain is bounded by *progress* (30 s without a written batch counts as a stall; the storer's finalize step gets 300 s), and a slow drain logs its backlog instead of failing. Checking REC again while the previous recording is still finalizing is refused with a log line.
- While a script ran, every other thread's ``print`` output vanished into the script's output buffer: the executor used ``contextlib.redirect_stdout``, which swaps the process-global stream. Output is now routed per thread, so only the script's own writes are captured.
- ``framework.Thread.wait(timeoutMs)`` is bounded; ``FrameworkUtils.processPendingEventsCurrThread`` tolerates threads without a Qt dispatcher.
- The API docs generator's embedded setup lacked ``scanWidgetType`` and crashed before writing anything.
- A galvo scan whose configured first axis collapses to a single step no longer routes waveforms to the wrong devices. ``GalvoScanDesigner`` filters axes with one step out of the scan (an axis whose ``round(length/step)`` is 1 does not scan), but the emitted signal dict, the reported ``pixel_sizes`` and the voltage-compliance indexing all kept using the *unfiltered* device order — so with d1 collapsed and d2/d3 active, d2's sweep was keyed under d1's device name and driven onto d1's AO channel, the recorded pixel sizes belonged to other axes, and ``checkSignalComp`` compared each waveform against another device's voltage rails. All three are now bound to the active axes in signal order, and the compliance check reads the aligned ``axis_names``/``minmaxes`` pairs the designer emits rather than re-deriving the mapping.
- Stage (Beta) scans convert each axis with the *target device's own* conversion factor. ``BetaScanDesigner`` indexed conversion factors by position over the setup file's positioner list while the target list is scan-dim-ordered, so assigning scan dims in any other order converted lengths, steps and centers with another device's factor — under the STED example a Z-piezo scan placed on the first scan dim was divided by the galvo's 17.44 instead of the piezo's 1.0, silently shrinking a 10 µm request to 0.57 µm of actual travel. A target device that is not a scanning positioner is now a clear error instead of an off-by-position lookup. The designer also finally checks its waveforms against each scanning positioner's ``minVolt``/``maxVolt`` — ``checkSignalComp`` had been a ``return True`` stub since it was written — so an unrepresentable scan (a Z scan centered at 0 µm on a 0–10 V piezo, say) is refused with the existing "signal voltages outside scanner ranges" error instead of reaching the DAQ. Every *emitted* waveform is checked, parked axes included: Beta drives a parked axis to its center for the whole scan, so an out-of-range center is a real out-of-range output (the galvo designer can exempt parked axes only because it emits no signal for them). Positioners that configure no voltage limits are skipped rather than rejected.
- ImProcess analyses that fit something now report the fit, not just draw it. A result renders through three channels — napari layers, graph payloads, table rows — but the router only ever published rows for ``kind == "table"``, so a ``curve`` result's ``table_records()`` were dropped even when present, and consequently no curve result implemented them. The numbers were computed and then stranded: ``frc`` put its resolution in the log and the plot title, and the photophysics drop-in put its fitted amplitudes, time constants and R² into ``metadata``, which nothing renders. Curve results can now opt into publishing rows (``publishes_table_rows``, kept opt-in because a localization table runs to six figures of rows), and both FRC and photophysics do. The Graph panel's *Push to table* was mislabelled to match: it pushed only the manual Δx marker record and returned silently when no markers were on screen, so pressing it on a plot of fitted data put nothing in the table — it now pushes the payload's parameters and a per-curve summary, with the Δx row added when markers are shown. Separately, the photophysics fatigue mode drew a bleaching curve and fitted nothing at all, though the module's own exponential fitter was already there for off-switching; it now fits the decay under the existing *Fit* toggle, reporting time constants in cycles rather than the fitter's default milliseconds, which are not this axis' unit.
- ImProcess measurement panels now answer for the result on screen. Profile, ROI statistics and the ROI manager read their pixels from the viewer, which selecting another reconstruction changes underneath them — but nothing told them a result had changed, so they kept displaying a curve or statistics measured on the previous one, which on screen is indistinguishable from a fresh measurement. They re-measure on every result change; the ROI itself is deliberately kept, since measuring the same region across reconstructions is the point. Two related gaps close with it: a profile could be pushed to the Results table but not to the Graph, and the Graph re-rendered itself from the current result on every switch, so two profiles could be measured but never compared — profiles can now be pushed to the Graph, pushed plots are pinned against that re-render, and an *Overlay* button draws everything the panel holds in one set of axes. Rows pushed to the accumulating Results table also name the result they came from, which they previously did not, leaving two pushes distinguishable only by their values.
- ImProcess **Merge channels** no longer looks like it works within a single reconstruction only. It had two ways in and both were broken: from *Tools > Load tool* it opened the generic single-input panel, which passes no inputs, so it raised "Merging channels requires at least two results" on every run — as did *Stack/Combine* and *Image calculator* by the same route; from the toolbar it merged the reconstruction-list multi-selection, which nothing on screen advertised, gated by an all-or-nothing check that greyed the button out with no reason whenever the results differed in shape, axis labels or pixel scales. Both paths now open a picker over every loaded result and report incompatibility as text naming the input and the property that disagrees. Two further quiet faults are fixed with them: merge ignored ``scale_unit`` where Stack/Combine rejects a mismatch, so a µm result merged with an nm one silently took the first one's unit; and merging inputs that already carried a ``C`` axis produced an output with two identically-labelled axes, which every label-driven axis lookup resolves to the first match. Channel order was also whatever order the results happened to be ctrl-clicked in — ``selectedItems()`` returns selection order, not list order — and is now explicit and reorderable in the dialog. Merging offers *Create composite*, so the result arrives as coloured channels rather than a greyscale stack needing a second **Make composite** step.
- The focus lock no longer fights a hardware Z scan that drives the same physical piezo. Suspension now happens on ``sigScanStarting`` — before the scan writes to any positioner — instead of ``sigScanStarted``, which fires only after the NI-DAQ tasks are already running. It is released on ``sigScanEnded``, the one terminal published on every path: bound to ``sigScanDone`` as before, a failed or aborted scan left the lock silently suspended for the rest of the session while the button still read "Unlock". Whether a scan conflicts is decided automatically, and the ``ND-PiezoZ``/``PiezoZ`` case in the STED example is detected with no configuration change; see :ref:`focuslock-scan-arbitration`. The **Scan Block** checkbox is now **Pause during scans** and is enabled by default — it was previously an unchecked, unpersisted opt-in, so a fresh session allowed the conflict by default.
- Resuming the focus lock after a scan now rebuilds the PI controller instead of re-enabling the old one. The retained integrator output was re-applied as a relative move and the stale error turned the whole scan-induced spot excursion into one derivative kick on the first tick. The lock also no longer resumes the instant the scan ends: it waits for the signal to settle *and* return within ``reacquireTolerancePx`` of the setpoint it was holding, giving up after ``reacquireTimeoutS`` rather than correcting against a signal that never came back. A pending "about to lock" is now cleared on scan start, so it can no longer re-engage mid-waveform.
- The focus-lock widget shows its lifecycle state (Locked / Suspended / Reacquiring / Lock lost after scan). The lock button alone could not distinguish "locked" from "a scan has suspended the lock".
- Positioners marked ``returnToCenterAfterScan`` are now parked on every scan terminal, not only on successful completion by two of the scan controllers. A run that failed to build or was aborted before an iteration went live released its actuator wherever the waveform left it — and then released the focus lock onto it. Multi-part and repeat sequences still park per part, with no additional hardware write.
- Focus calibration and autofocus no longer drive the Z axis against a running scan. Neither had any scan interlock: calibration issues ~20 absolute moves from a worker thread, and ``AutofocusController`` had no scan awareness at all. Both now refuse to start while a scan owns the axis and cancel if one begins; a calibration cancelled this way is discarded without its usual restore-to-start move, which would itself have fought the scan.
- Removed the non-functional focus-lock "Z-stack" path. Its checkbox had been commented out of the layout, and the control path read a ``stepDistance`` attribute that no longer had any assignment, so enabling it would have raised ``AttributeError``. The visible "Min z-stack step (nm)" field, which configured only that path, is gone with it; the scan-arbitration reacquisition barrier covers what it was for.
- The focus-lock control loop no longer double-integrates. ``PI.update`` computes a running command, which the caller then applied as a *relative* move — so the positioner integrated an already-integrated signal. Simulated against a rig calibration of 586 nm/px with 0.4 px measurement noise, that loop diverges at the shipped gains; applying the increment instead settles to ~6 nm residual RMS at those same gains. Corrections below the smallest worthwhile move are now carried forward instead of discarded, so the integral term is no longer thrown away by the threshold. **Existing gains should be kept**: in simulation ``kp=25, ki=0.1`` outperforms higher values.
- The focus-spot centroid is background-subtracted before the centre of mass. A plain centroid over raw intensities lets the background pedestal drag the result toward the window centre by an amount that scales with spot brightness, so any fluctuation in optical power reads as defocus. RMS error now stays ~9 nm from 0% to 50% frame-to-frame intensity jitter, where the unsubtracted centroid degraded from 4 nm to 32 nm — a little worse in the perfectly stable case, several times better in a realistic one.
- The focus lock's **Two foci** option no longer hangs the GUI. ``gaussian_filter`` preserves its input dtype, so a uint16 camera frame stayed uint16 and integer truncation collapsed it into broad flat plateaus — 117k distinct values down to 683 on a representative frame. Plateaus produce many near-coincident peak candidates, and enforcing the minimum spacing between them cost 574 ms per frame against 2.4 ms for the same scene in float32; ``scipy.ndimage`` holds the GIL and the estimator worker is asked for a new frame every 100 ms by default, so the interface was starved for as long as the option stayed ticked. Filtering now happens in float32, which also removes the quantization from the centre-of-mass both paths depend on. The peak search is additionally bounded, and selecting between the two foci is vectorized — the previous hand-rolled version raised ``IndexError`` whenever fewer than two peaks were found, logging a traceback on every tick. A genuinely saturated spot is still slow to search, but it carries no centroid information either; reduce the exposure.
- The focus signal now reports the spot's real position. The window-local centroid was re-referenced to the frame by adding the peak coordinate rather than the window's start, which differ by the half-window, so the reported position sat a constant 50 px from the spot — visible as the marker line never lining up with the maximum. Within half a window of the frame's low edge it stopped being cosmetic: the error became signal-dependent and the reported movement per real pixel rose from 1.00 to 1.83, so the control loop's gain depended on where the spot happened to sit.
- The ImProcess **Tiling mosaic** reconstructor now solves the whole layout at once instead of chaining each tile to one neighbour. Refinement previously visited tiles in acquisition order and aligned each against the first already-placed tile it sufficiently overlapped — in a spiral, almost always its predecessor. That is one constraint per tile where the geometry offers two to four, it accumulates error along the acquisition order, and because nothing scored the correlation, a single false match displaced every tile measured after it: the mosaic came apart into two internally consistent halves. Every overlapping pair is now correlated and scored by the cross-correlation at the shift it claims, links that contradict the consensus are rejected on their residual, and the over-determined system is solved by weighted least squares, anchored per connected group at its earliest-acquired tile. On simulated spiral runs with 2.5 px stage jitter, placement error stops growing with tile count — 49 tiles of sparse filament-like structure went from 2.7 px RMS (5.1 px worst) to 0.35 px (1.5 px worst) — at a cost of ~15 s for 100 tiles of 2048 px. A tile nothing could be measured against keeps its recorded stage position rather than being guessed at. Every stage now logs as it goes — tiles read, pairs correlated, links dropped per solve round, and the mosaic's dimensions and memory cost before that memory is asked for — because reconstruction runs on the calling thread and a working run was otherwise indistinguishable from a hung one. Measured on 100 tiles of 2000x2000 px: 15 s end to end, 0.4 s of it reading, 11 s correlating 342 pairs, 2 s assembling.
- A tiling run that saves tiles now records a full payload at each position, and stops dispatching its own scans. A triggered run opens **one recording session** for the whole run — a lapse whose points differ by where the stage is rather than by when a timer fires, which is what a tiling run already was — and the session dispatches every scan. Two dispatchers would command the same firmware for one tile, and whichever arrived second would be scanning a stage the first had already moved. The handover is a **positioning request**, not a call: tiling resolves one from its own worker once the stage is there and settled, and the session arms only on ``RESOLVED`` — a cancelled, failed or timed-out request ends the session with the reason it carries. While a move is in flight the session re-schedules itself and returns to the event loop rather than blocking it, which is what keeps the focus-lock timers running through a hundred moves. Each tile's manifest entry then points at where its recording actually finalised, read from the terminal rather than guessed at dispatch. Free-running runs are unchanged: there is no scan for a session to run, so their snapshot remains the payload.
- Recording failures are typed, so a caller running many recordings in one go can tell what it would be continuing past. ``FailureKind`` distinguishes ``WRITER`` — the measurement happened, the file did not — from ``ACQUISITION``, ``SCAN`` and ``HARDWARE``, and only the first is recoverable. An unclassified failure is ``UNKNOWN`` and deliberately **not** recoverable, since the alternative is carrying on past something nobody understood. The kind rides on a new ``sigRecordingFailedTyped`` alongside the existing signals, and is a prerequisite rather than a nicety: classifying by matching message text would look like a policy while silently misclassifying anything reworded.
- A recording session reports where its data actually landed. ``PayloadLocator`` carries the path, the group within a container, the detector, the axes and the generation — a filename alone does not find the data again, because grouped HDF5/Zarr needs the group and separate files may have been de-duplicated against existing ones. Locators are published by the writer once ``getSaveFilePath`` has resolved them, and report ``complete`` only after finalisation: a caller writing them into a manifest must wait for the terminal, since pointing a manifest at a file whose writer never drained is the same mistake as guessing its name.
- Recordings ask detectors for the measurement rather than the picture of it. Streaming recording reads ``getChunk()``, which for a point detector returns ``_image_display`` — and what that holds is decided by ``_linestep_view_mode``, a *display* setting. The APD never assigns it, so its line steps survived by luck; the PMT sets ``"sum"`` in its constructor for ``_compute_display_frame``, so every PMT recording of a line-step scan had its channels added together before anything could see them, irreversibly. A chunk's contents were a per-detector display preference no consumer could ask about or override. Detectors now answer ``drainChunk()`` with both representations from one destructive drain, consumers declare ``ChunkKind.DISPLAY`` (the default, so every existing caller is unchanged) or ``ChunkKind.RAW``, and only the recording worker asks for the latter. Every camera is unchanged and needs no override: a camera's chunk *is* its frames, so both kinds are the same object. ``getLatestFrameShared(is_save=True)`` also stops lying — it took the chunk branch before ever consulting the flag, so merely having a recording open silently downgraded every other reader on that detector, and the two representations are now cached separately.
- The raw chunk of a scan-driven detector is published once, when the scan ends, and never half-written. ``_onFrameBoundary`` fires at every higher-dimensional step — once per Z plane — so the raw buffer is a volume still being filled, while a recording asks for exactly *one* frame from a scan-driven detector: it would have kept the first partial volume, planes unwritten, with no error anywhere. The raw side is therefore latched on its scan's generation and released only when that generation reaches a terminal state, which happens during teardown after the last boundary and so cannot be driven off a frame event. Polling again yields nothing rather than a second copy, and an aborted scan publishes nothing at all — the veto is set before teardown, since teardown is what would otherwise publish it. Raw consumer queues are capped far lower than display ones, because a raw frame is a volume and the same frame count is not the same memory.
- A tiling run can save several detectors at each tile position, while still aligning on one. The detectors come from the Recording widget's own selection rather than a second setting inside tiling — the same place the output folder already comes from — and the **Detector** combo is now **Align on**, since it names the detector the mosaic is built from rather than the only one saved. Saving is the easy half: the capture contract is what makes it correct. The save set is pinned at run start so the manifest describes one set of detectors for the whole dataset; every selected camera is leased for the run, not just the aligned-on one; each gets the same post-move fresh-frame proof, so a second camera cannot contribute a frame left from the previous tile or exposed mid-move; and no tile is written until the slowest camera has produced its image, which is what sets the per-tile cost. A detector is dropped only when it *cannot produce a tile here* — no such detector, or scan-driven in a free-running run — and the reason is logged. How its pixels relate to the aligned-on one is a separate question, declared via the new ``tiling.detectorTransforms`` and recorded per payload: ``identity`` is an assertion about the rig that whoever configured it owns, and ``unknown`` is the absence of one. Equal pixel sizes prove nothing about sensor origin, ROI, orientation or optical-path offset, so that relationship is never inferred here — but not knowing it is a reason to write it down as unknown, not to throw the data away, since the run only passes this sample once and the question can be answered offline. A declared ``identity`` that contradicts the detector's own pixel size or frame shape warns and saves. Offline, an undeclared transform still resolves to identity so the pixels come out, and the assembly reports it as *assumed* rather than as something the manifest stated. Offline, the reconstructor gained a **Detector** picker; every detector shares one solved layout, because they were all captured at the same stage positions.
- A tiling manifest now records what each tile file actually contains, and mosaics assemble with any number of leading axes. A line-step scan's leading axis is *channels*, but the manifest could only call it ``tile_shape_px.depth`` and give it a ``z_step_um`` — so a channel was recorded as a distance, and every reader downstream inherited that. Each tile entry now carries ``axes`` (what a reader should end up with), ``stored_axes`` (what is on disk, taken from what was written rather than assumed) and ``shape``. The acquisition side distinguishes channels from planes by whether the detector publishes a Z spacing, and leaves the entry undescribed rather than guessing when it cannot tell. On the reading side, ``assemble()`` previously supported exactly one optional leading axis, so ``CZYX`` could not be assembled at all, and the loader squeezed leading singleton axes — silently destroying a single-channel axis. Both are fixed: the mosaic keeps whatever leading axes the tiles have, a squeeze happens only where the descriptor asks for one and only on a length-1 axis, and it raises rather than discarding data. Tiles of differing rank still compose, with a plain image among stacks contributing to every plane where a genuine length-1 axis covers one position. Manifests without descriptors read exactly as before.
- Live tile alignment now uses the offline reconstructor's global solve. It previously correlated each tile once, against the region of the canvas its commanded position pointed at, and applied whatever came back — so a false match placed that tile and every tile placed relative to it afterwards, and that layout was what got saved. Each tile is now correlated against *every* already-placed neighbour it overlaps (a spiral usually offers two to four) and placed at the confidence-weighted consensus; when the run ends the whole layout is solved again by weighted least squares, with measurements that contradict the consensus rejected on their residual. The solved layout is what reaches the overview, the saved mosaic and the sidecar files, so a run no longer records the live pass's mistakes. On simulated 25–49 tile spirals this removed the placement error entirely on textured samples (3.6 px RMS / 23 px worst → 0.0); on very sparse ones it is a wash, since there is often only one usable neighbour anyway. It is also **faster** — the old pass rebuilt and copied the whole growing mosaic once per tile, where this correlates against the two to four small tiles that actually border the new one, measured at 0.41–0.49x the time on 100-tile spirals at 273–1024 px tiles. The single-neighbour path has been removed rather than kept as an option: there was no regime in which it won.
- The tiling widget is laid out in labelled blocks — **Scan**, **Acquisition**, **Alignment**, **Stitching** — instead of one flat grid of controls in acquisition-order rows, and the stitched overview now spans the full width and takes all the space the controls do not need. It previously spanned four of the layout's six columns, so it could never reach the right-hand edge.
- The **Tiling mosaic** reconstructor lays tiles out from the stage coordinates the run commanded, instead of the pixel positions it saved. ``tiles.json`` records ``pixel_xy`` *after* the live "Align tiles" pass, so any correction that pass made is baked into it — and offline refinement cannot undo one, because it crops its correlation windows from those same positions: a tile displaced far enough is measured against the wrong part of its neighbour, or is no longer seen to overlap it at all. On a real 100-tile point-scan run this was decisive. Tiles were 273 px on a 227 px step, so they overlapped by 46 px, yet the live pass had moved 85 of the 100 tiles, 23 of them by more than that entire overlap and one by 111 px. Reassembling from the saved positions found 288 candidate pairs, kept 263, rejected 14 as inconsistent and left the mosaic in five pieces; from the stage coordinates it found 342, kept 337, rejected 4, and tied every tile into one group, with the solve's own corrections a median 7.8 px from the commanded layout. A **Start from stage positions** checkbox (on by default) reverts to the saved layout. Manifests without usable stage coordinates — older writers put the same one on every tile — fall back automatically. The orientation flags are applied exactly as the acquisition side applies them, swap before flips.
- Tile correlation is band-passed, so uneven illumination no longer costs the mosaic its links. Where two tiles meet they show the same vignetting curve at different points on it — the falloff at one tile's right edge against the rise toward the other's centre — and those ramp in opposite directions. Scoring the raw overlap therefore returned a normalized cross-correlation near **-1** on pairs whose sample structure had in fact aligned to a third of a pixel, and the score gate discarded them. Lost links fragment the layout into groups that each fall back to raw stage coordinates, which is the "one region is fine, another region is fine, the join between them is nonsense" failure. Removing a coarse local mean before correlating and scoring restores them: on simulated 16-tile runs with vignetting, usable links went from 11 to 26 and the layout from five disconnected groups to one, with no change on evenly illuminated data. The score threshold is deliberately left permissive — raising it made placement worse in every case measured, because losing a link costs more than admitting a weak one the global solve can outvote.
- Assembling a tiling mosaic no longer allocates three full-size copies of it. The averaging step built a separate quotient array and a separate divide-safe copy of the weights, on top of the accumulator and the weights themselves; the division is now done in place and the weights, which are overlap counts, are held as ``uint16``. Output is bit-identical in 2D and 3D and with blending on or off. On a 100-tile run of 2000x2000 px tiles — a 15522x15520 mosaic — peak allocation drops from 3.85 GB to 1.45 GB.
- The tiling detector can be chosen at runtime from a **Detector** combo in the widget, instead of only from ``tiling.camera``. The setup file remains the default; the combo overrides it for the session and is not persisted, so a saved selection can never silently outrank the configuration. Only detectors with ``forAcquisition`` are offered, and the combo is hidden on rigs with a single one. Changing it discards the current overview — a different detector means a different pixel size, so the existing mosaic no longer maps to stage coordinates for click-to-navigate.
- Triggered tiling now waits for the focus lock to reacquire before starting the next tile's scan. A scan's completion resolves as soon as its terminal is published, while reacquisition is only just beginning — so the loop moved the stage and fired the next scan straight through the barrier, cancelling it. At the default 10 Hz estimate rate a five-sample window needs ~0.5 s against a 0.15 s tile settle, so every tile cancelled the previous one's reacquisition and the lock stayed inactive for the whole run, silently.
- Cancelling autofocus or focus calibration for an incoming scan is now an acknowledged handoff. Both previously set a cancel flag and let the scan start immediately, so a sweep could still be mid-move — and autofocus' cleanup restores its starting Z, meaning cancellation could itself drive the axis into a running waveform. The scan now waits (bounded) for the worker to leave, and a worker cancelled this way abandons the axis instead of restoring it.
- The focus-lock reacquisition timeout now expires even when the focus camera stops delivering estimates — previously the deadline was only checked when a new sample arrived, so a stalled camera left the controller in "Reacquiring" indefinitely with callers blocked. An expired deadline also can no longer be overridden by a sample window that completed after it.
- A scan that failed before arming no longer issues a return-to-center move. The "already parked" flag was only created when an iteration armed, and a missing flag counted as pending, so a first run failing in ``getParameters`` or signal construction wrote to the stage from a possibly half-rebuilt parameter dict.
- ``returnToCenterAfterScan`` without an explicit ``returnToCenterAfterScanAxis`` now parks under the positioner's own first axis name instead of the integer ``0``. Managers key tracked position by axis name, so the old default wrote the voltage but recorded it under a new ``0`` key, leaving ``position["Z"]`` stale for any later relative move. ``example_sted.json`` ships exactly this configuration.
- New ``physicalActuator`` field on positioners declares that two entries drive one physical device. Setup validation warns (``xref.focuslock.shared-actuator``) when the focus-lock positioner shares an axis with a scanned positioner and neither declares it.
- The focus lock's safety unlock no longer issues the oversized correction it exists to prevent. When the computed step exceeded the 3 µm threshold, the loop dropped the lock but still reported that step to its caller, which applied it — so tripping the guard drove the piezo by more than 3 µm in a single tick instead of stopping it. The guard now reports no motion, and a correction is never applied to a lock that was dropped mid-tick. Most likely to be hit on the first tick after a Z scan, where the accumulated spot excursion is largest.
- FLIM lifetimes from the three fit methods (moment, phasor, exp1) no longer diverge when the IRF peak is offset from t=0. The worker now auto-detects the IRF peak bin from the aggregated decay each frame and compensates each fitter: moment subtracts ``t_peak`` from the mean, exp1 restricts the fit to bins ≥ peak with a shifted time axis, phasor rotates the measured (g, s) by −ω·t_peak. On known dyes the three methods now converge toward the true lifetime.
- Phasor fit previously assumed the laser repetition period equalled ``n_bins * binwidth_ps``, which silently scaled τ by an arbitrary factor whenever the histogram window did not happen to span exactly one laser period
- The tiling GUI cell-detection path no longer iterates the stage through every detected target. Stage iteration is reserved for explicit automated/API cell targeting calls or manual click-to-navigate.
- Recording a scan with a point detector (APD/PMT/TimeTagger) no longer fails with a false ``Detector '<name>' stalled: no frames received for 10.0s`` whenever the scan itself ran longer than the watchdog timeout. These detectors integrate the whole scan and publish a single frame at the end, so the watchdog now starts counting at the scan's expected or observed completion instead of at recording start. Line-step scans, which multiply scan duration by the number of steps, were the common way to trip this.
- Enabling **Repeat** on an NI-DAQ scan no longer crashes the GUI. ``scanDone`` re-armed the next frame synchronously from the finished scan's task-completion slot, recreating NI-DAQ tasks, wait threads and per-detector scan threads while the previous ones were still shutting down (a ``QThread`` destroyed while running). The re-arm is now deferred to the next event-loop turn, and aborting or un-checking Repeat in that gap cancels cleanly. Only reproducible on real hardware — simulation mode never created the wait threads.
- Point-detector live preview is no longer choppy on slow scans and no longer floods the GUI on fast ones. Redraws were gated on image *shape* with a random draw per scan line; they are now limited deterministically by wall clock (default 20 Hz, see ``liveUpdateIntervalMs``).
- Detector settings restored at startup now reach the hardware. State is applied to the detector first and the widget refreshed from the resulting state, so ROI, binning and editable parameters land on the correct detector instead of being shown but never applied.
- A ``cameraPixelSizeUm`` set in the setup file is no longer overridden at startup by the value saved in ``imcontrol_widget_states``. The camera pixel size is instrument calibration, so when the setup file declares it the config wins: the value is neither snapshotted nor restored, and a stale snapshot from before the config was edited no longer silently reinstates the old calibration into every recording's metadata (OME ``PhysicalSize``, Fiji ``element_size_um``, ``Detector:<name>:Param:Camera pixel size``). Cameras without the key keep the previous behaviour, where the pixel size is an ordinary editable setting that persists. See :doc:`devices/detectors`.
- A failure while refreshing the detector settings display after a state restore is now reported as a warning instead of silently leaving the widget showing pre-restore values while the detector runs with the restored ones.
- The Hamamatsu settings tree now reflects the camera's actual trigger source. ``_updatePropertiesFromCamera`` compared ``getPropertyValue('trigger_source')`` — which returns ``(value, type)`` — against an integer, so every branch was dead and **Trigger source** was never refreshed from the camera; it kept showing whatever ImSwitch had last written. The read-back no longer routes back through the hardware write either, so changing the exposure no longer re-pokes the trigger configuration.
- The IC4 (Imaging Source) camera now reports the ROI, exposure and gain the sensor actually took rather than what was requested. Width/Height/Offset are rounded down to the sensor's increment (commonly 4 or 8 px) and exposure/gain are clamped to their legal ranges, so an arbitrary ROI from the GUI's selector left ``frameStart``/``shape`` — and with them the settings display, the viewer scale, the recording shape and the OME metadata — describing frames the camera was not producing. Matches the read-back ``HamamatsuManager.crop`` already did.
- Lasers no longer perform hardware writes from the scan-signal path, which could drive TTL lines incorrectly during a scan; resolving scan devices now only updates which laser controls are editable. Scan arming reapplies the intended amplitude per scan, disarms only the lasers that scan armed, and leaves power setpoints editable while a scan runs (only the on/off control locks).
- Scan-driven detectors (APD/PMT/TimeTagger) are now counted as producing one frame per scan when computing expected frame totals, preventing hung or truncated scan recordings.
- The TIS (Imaging Source) camera no longer crashes focus lock or chunk capture when the driver buffer is briefly empty. A missing frame is treated as a transient condition, and the last valid frame is preserved for polling callers instead of being duplicated into the stream.
- TriggerScope scans now use the shared scan-execution lifecycle across raster, RESOLFT, galvo and multicolor controllers. Laser membership is resolved before the firmware starts so selected laser controls lock and their gates are armed; board-wide start/done signals are handled only by the owning controller; scan-driven detector leases and their finish barrier are retained through completion. A stop still lets the autonomous iteration and its final detector read finish, while reliably preventing repeat or sequence continuation even when recording teardown arrives during completion publication.
- Scan recordings on setups with several scan widgets are now bound to the scan that actually runs. A scan-once recording is armed and then picks up the frame count, camera-TTL map and scan dimensions from whichever scan widget the operator starts, instead of from whichever controller happened to expose those accessors — previously a rig with both a TriggerScope raster and a TriggerScope RESOLFT widget always recorded with the raster's pixel grid and the scan failed. A recording that cannot be armed now stops the scan rather than letting it run unrecorded. All TriggerScope controllers report their geometry (``roSteps x cycleSteps x timeLapsePoints`` for the RESOLFT-family modes). Timelapse scans, which the recording starts itself, take their scanner from a new **Scan source** control in the Recording widget, shown only when the setup offers a choice and refused while no choice has been made rather than defaulting to one. Scan dimensions and step sizes are omitted rather than borrowed from another scanner when the chosen one does not report them. See :doc:`scan-lifecycle`.
- Live View, focus and other latest-frame readers now follow frames drained first by BeadRec or a recording. The shared frame broker latches the newest hardware frame regardless of which consumer performed the drain, preventing a TriggerScope raster reconstruction from leaving Live View frozen on its pre-scan image.

- A scan lapse recorded as a single file can be opened again. Choosing *single file* storage writes one group per timepoint — ``scan0/Camera/data``, ``scan1/Camera/data`` — but dataset discovery only ever looked at the container root, found neither an array nor a detector group there, and reported ``File does not contain any datasets``. Every such recording was unopenable, in both HDF5 and Zarr, by any dataset name; the other lapse mode, one file per timepoint, was unaffected, which is why the shape survived. Discovery now names each timepoint (``scan0/Camera``), so each opens on its own and carries its own ``time`` partition — which is what tells a reader *which* timepoint it is holding. It descends exactly one level, and only through a group that holds detector groups, so an ordinary recording is discovered exactly as before. The gap was structural rather than accidental: the storer's tests assert the groups are written, the live-streaming reader always knew about ``scan{N}`` groups and has its own tests, and the metadata resolver was tested on attribute dictionaries lifted straight out of a dataset. Every layer was tested against its own idea of the next one, and no test opened a written lapse file the way a user does.

- ``tools/inspect_acquisition_layout.py`` reports how *its own* checkout reads a recording. Python puts a script's own directory on ``sys.path`` and never the working directory, so on a machine with ImSwitch installed from somewhere else — a release install beside the branch under test, which is the normal case on an instrument computer — the tool imported that other copy and reported how *it* would read the file. On an install predating the acquisition layout the failure was an ``AttributeError`` naming an attribute of ImSwitch's own model class, which reads as a broken recording rather than the wrong code being asked. The tool now binds to the repository it ships with, prints which ImSwitch interpreted the file, and says so plainly when that ImSwitch is too old to answer. It also inspects *every* dataset in a container rather than refusing files with more than one, so a single-file lapse prints one block per timepoint instead of ``File contains multiple datasets``.

- The **Camera used for detection** selector on the TriggerScope RESOLFT panels lists detectors only, and a scan armed without one says which control to use. The selector was filled from every device with a digital line, which is lasers as well as detectors, so a laser could be chosen for a role only a detector can fill; that read back as "no camera declared", which since this release refuses the recording. The generic refusal then told the operator to gate the detector in the scan's TTL cycle — advice that cannot be followed in these modes, because the firmware owns the camera line and the software's only say is *which* detector is wired to it. The message now names the panel control and says whether nothing was selected or the selection is not a detector. A saved state pointing at a laser comes back as an empty selection rather than an invalid one, and is refused at arm with that message instead of being recorded as a certain scan.

- Old recordings open again, and are described honestly. Three faults in the legacy adapters, each of which made a pre-branch file *worse* than it was before the acquisition layout existed. The TriggerScope adapter claimed any file carrying a sequence time with no line steps and no ``Nx`` — which is what every point-scan and MoNaLISA controller publishes for every recording on those rigs, scan or not — so a plain timelapse whose frame count happened to match the configured stage area was reported as a raster at *high* confidence, and a galvo point scan was attributed to TriggerScope. It now reads only files that name TriggerScope, and skips a recording that declares several timepoints, the same guard the stage adapter already had. The 2D assembled-image path it owned moves to the modality-neutral adapter, since a point detector's assembled image follows from the payload rather than from one firmware. Second, two positioners whose names guess the same axis — ``ND-PiezoZ`` beside ``PiezoZ``, ``Mock Kinesis XY`` beside ``Mock X``, both shipped in this repository's own example configurations — produced duplicate loop ids and an invalid layout. A spare stage that stood still is now left out of the geometry, and two axes that both moved and share a name are declined rather than guessed. Third, and worst: those failures escaped into the *display* path, where ``getattr(..., None)`` swallows only ``AttributeError``, so opening an ordinary readable file produced no image at all. Naming axes is a decision with a fallback; view-only now falls back to ``Frame, Y, X`` and reports the failure through its source inspection instead of refusing the pixels.

- A single-file lapse reads its timepoints back in time order, and one unreadable neighbour no longer empties a container. Discovery ordered the per-timepoint groups as text, so a twelve-point lapse came back 0, 1, 10, 11, 2, … in the dataset picker and in the multi-data list, while the live readers sorted the same groups numerically — two layers disagreeing about one file. It also dereferenced every child of every root group without a guard, which is new: this is the first code in the open path that follows nodes it did not write, so a dangling link in an unrelated group failed the whole file. Unreadable children are skipped; discovery answers what *can* be opened.

- A scan-driven detector recorded as OME-TIFF can be read back. One assembled frame is stored as the plane itself rather than a one-element stack, so the container has one axis fewer than the layout declared — and an explicit layout that disagrees with its container is refused outright by design, never fallen back from, which made these recordings unreadable rather than merely unannotated. The embedded layout now drops the same axis the storer drops. Note that OME-TIFF still cannot express a line-step axis: it projects onto ``T``, which the resolver reports as a lossy projection. Record scan-driven detectors as HDF5 or Zarr when the line steps matter.

- ``tools/inspect_acquisition_layout.py`` reports the recording's lifecycle and stops inventing frames. It printed the whole planned frame table for a recording that stopped early, so frames that were never acquired appeared under the heading *stored frames* — in the one output a rig session is told to trust, three lines below the resolver's own warning that the file holds fewer frames than the layout selects. The table is now bounded by what the container holds and names the planned frames that are missing, and a lifecycle line reports the writer state, the completion outcome and the actual against planned counts, so a file still being written no longer reads as a finished one. A dataset name that does not exist in the file is refused rather than silently answered with the file's only dataset.

- A scan lapse saved with **Save on disk and keep in memory** no longer destroys itself. Each finished file is reopened read-only and the live handle is handed to the app, which keeps it; for a lapse written as a single file that is the same path the next timepoint opens for append, and HDF5 refuses that while any read handle is open. Timepoint 1 failed to open, the recording aborted, and the abort removed the file — so a ten-point lapse produced no file at all, having already acquired the first timepoint. The hand-off for a single-file lapse is now a detached in-memory copy, which is what the memory-only mode gives consumers anyway, and the abort path no longer deletes a file it did not create: the timepoints already in it are complete recordings and are not the aborting session's to discard.

- Running the same scan lapse twice no longer appends the second run into the first run's file. The exemption that lets timepoints 1..N-1 append to the file timepoint 0 created was expressed as "this path may always be overwritten", which is equally true of the first timepoint of the next run. The second run continued the first one's group numbering while every recorded time-partition index restarted at 0, so one file held two groups each claiming to be timepoint 0 of the same lapse. A lapse now resolves its destination once, at its first timepoint, and every later timepoint writes to what that resolved to; a fresh run de-duplicates like every other recording.

- A lapse recorded to memory reaches ImProcess as openable timepoints. The memory hand-off enumerated the container's root keys, which for a single-file lapse are the per-timepoint group names rather than datasets, so every timepoint arrived as a row that failed when opened. It now uses the same dataset discovery as the on-disk path — the half of that fix this path had been missing.

- A de-duplicated OME-TIFF is named ``rec_Camera_1.ome.tiff`` rather than ``rec_Camera.ome_1.tiff``. The counter was inserted with ``os.path.splitext``, which splits on the last dot only, so it landed inside the two-part suffix and the file sorted away from its siblings and matched no ``*.ome.tiff`` pattern. HDF5 and Zarr were never affected.

- What a source inspection found is written to the log when no widget can show it. Only one parameter widget in the tree implements the display hook, and the default view-only reconstructor's does not, so the inspection was assembled and then discarded: a scan that stopped at four of six positions opened as an ordinary four-frame stack with nothing anywhere saying so. Until a widget shows it, the incompleteness is at least stated. The layout inspector reports the same thing directly, from the file.

- An interrupted recording no longer looks like a complete one. The acquisition layout is exactly what makes the difference detectable — it says how many positions were planned, the container says how many frames it holds — and every place that could have said so was dropping it. The Parameters dock now shows what the source inspection found, for every reconstructor rather than for the single plugin whose own widget implemented a display hook; previously the inspection that knew a scan had stopped at four of six positions was assembled and discarded, and the recording opened as an ordinary four-frame stack. The SMLM loop selection range-checked against the layout rather than the stored frames, so a selection its own validator accepted indexed past the end of the array and surfaced as a bare NumPy message about an axis; it now names the positions the acquisition never reached. And a recording stopped before its first frame — which still leaves a file, because datasets are created lazily — now carries its detector, its outcome and its planned count on the container itself, instead of being an anonymous stub indistinguishable from a corrupt file.

- A page-less OME-TIFF reports that it holds no image, rather than offering a dataset and then refusing it. The reader invented the name ``default`` for a file with no pages and then failed with *Dataset "default" was not found in TIFF series ['default']*, naming the dataset in the list it claimed not to contain. It now gives the same accurate refusal HDF5 and Zarr already gave.

- Live reconstruction of a lapse that was stopped mid-timepoint terminates on the recording's own marker instead of on a timeout. ``Hdf5LapseSource`` waited for timepoints that an interrupted acquisition will never write, and the only way out was the stall timeout, whose message called a deliberate stop a crashed writer. A timepoint finalized as ``stopped_early`` is now recognised as the last one. A lapse stopped cleanly *between* timepoints still cannot be told from one that is merely slow, which is what the timeout is for — but it no longer asserts a crash it cannot know about.

- Legacy line-step recordings report what is actually wrong with them. The geometry helper's "do not cross-check against the frame count" mode raised *ambiguous geometry* whenever the size and endpoint conventions disagreed, which every real file makes them do, so its only caller — the detector-gating retry that exists to explain a line-step file — could never be reached. It now assumes the size convention and says so. The same adapter also recognises the ``(T, C, Y, X)`` shape the writer actually produces for a scan-driven detector, not only the ``(C, Y, X)`` a reader might construct, which is why the two-line-step point-detector recordings it exists for were falling through to the frame-stream path.

- A point detector's assembled scan can have more than two axes. The legacy adapter recognised a ``(condition, Z, Y, X)`` recording and then described it as ``condition, scan_y, scan_x`` — one axis short — and an explicit layout that disagrees with its container is refused outright by design, so the file could not be resolved at all. The stored axes after the condition are now taken from the scan's own loops, slowest first, with configured axes that never moved left out.

- An *inferred* raster no longer overrules the Scan X/Y you typed. Refusing a manual entry is only a declared layout's prerogative; a reading of legacy metadata that happens to say 4×3 was rejecting a valid manual 6×2 on the same twelve frames, which is the opposite of the rule that inference must never refuse data that used to be usable. A recorded layout still refuses, as it should.

- A recording that threw frames away no longer reads as a clean one. A detector can meet its planned count exactly and still have produced a surplus the writer dropped — a free-running camera, or one pulsed more often than the scan declared — and the completion vocabulary has no word for that, so the file said ``complete`` and nothing consulted the count. The lifecycle now reports the discarded frames and raises a warning on them, and OME-TIFF carries the field at all, which it previously filtered out.

- Opening a file cannot be made to allocate hundreds of megabytes by a few hundred bytes of metadata. Two spans claiming three hundred thousand repetitions each of a six-event scan built one run per repetition before anything checked that they addressed events the scan does not have. Spans are now range-checked first, and the overlap sweep runs only on spans that could be valid.

- The size of one time point is counted, not guessed from where the time loop sits. Counting frames until the time coordinate first changed assumed the time loop was outermost and ran forward; a layout with time nested inside a spatial axis returned half the stack, and a reversed traversal returned nothing, in both cases leaving a live reader waiting for a number it would never reach. Frames are tallied against their own time coordinate, and a gated selection whose time points differ in size says so instead of picking one.

- A persisted layout override is found again when the file is reopened. The sidecar was keyed on the detector the *layout* declares, while resolution keys on what the *container* calls its data — ``Camera`` against a TIFF series named ``Image0`` — so the override was rejected as targeting a different detector and the metadata it was written to correct came back.

- Two polarization stacks are paired only if their whole event structure matches. Comparing loop *names* accepted a ``time=2, condition=6`` acquisition as the counterpart of a ``time=3, condition=4`` one: same names, same frame count, different states compared pixel by pixel. Counts, traversal order and any gated selection are compared too.

- SMLM refuses an anisotropically calibrated recording instead of reporting Y in X's units. It read the X pitch and applied it to both axes, so a stack calibrated 65 nm along Y and 100 nm along X had every Y coordinate and every Y sigma scaled as though the pixel were square — silently, since the number looked ordinary. Which axis is right is a question about the microscope, so a pixel size entered by hand settles it and nothing else does.

- Validating a gated selection no longer costs a second and seventy megabytes. A span is a grid — ``start + i*period + j*stride`` over ``repeats`` by ``count`` — and comparing two of them cut each one per repetition, so two spans of three frames per position over a hundred-thousand-position scan built six hundred thousand arithmetic runs to answer a question about six. Each span is now cut along its shorter edge, which describes exactly the same events and bounds the work by ``min(repeats, count)``.

- A recording whose time points are not consecutive is refused rather than given a stack size that cannot describe it. Counting frames until the time coordinate first changed assumed time was the outermost loop; counting them properly, as the previous release did, still returns a number a reader slices with — and when the time loop is nested inside a spatial axis the first N frames hold several time points, not one. That shape has no stack size, and the live reader declines it with the reason instead of reading mixed frames into one stack. Where a stack size does exist it is now derived from the loop counts: deriving it by walking the acquisition took nearly three seconds on a scan of two million frames.

- The SMLM panel asks where the pixel size should come from. It always sent the spinbox's default, so the recording's own calibration was never consulted and the refusal of an anisotropic one could not fire — the localizer had no way to tell a default from a decision. *Pixel size* now chooses between **From the recording** and **Enter below**, and only the second sends a number.

- Pairing two polarization stacks compares their condition labels as well as their counts. ``("signal", "background")`` and ``("background", "signal")`` are the same shape and the opposite pairing, and comparing counts alone accepted them as counterparts.

- The discarded-frame count goes through the same strict parser as every other count in a recording, and survives a round trip through OME-TIFF. It had a lenient parser of its own that turned ``1.9`` into ``1`` and a negative into silence, so a corrupt marker looked like an absent one; and it was missing from the set of annotation keys read back as numbers, so in OME-TIFF it returned as text that the strict parser then rejected.

- An old line-step recording whose detector was gated onto only part of the scan resolves again. ``ScanTTL:linestep_enable`` — which detector ran on which line step — is a structured value, so it is stored as JSON behind a sentinel, and only ``SharedAttributes`` knew how to decode it. Every reader that went to the file directly saw the raw string, so the legacy adapter's per-detector gating retry could never find a mask and the file failed to resolve at all: a recording that used to open, made unopenable by this release. The resolver now decodes the sentinel wherever it appears, which reaches every structured legacy attribute rather than this one.

- The multicolor pLS-RESOLFT panel offers only cameras the firmware can be told about. Unlike the other RESOLFT panels, that mode *programs* the camera's line into the firmware, and it can only do so for a detector whose setup entry names a ``Triggerscope/TTL<n>``. Offering every detector there moved the failure from arm time to five parameters into the scan, as a bare ``KeyError``. A device without a line is now named, with the setup key that fixes it, wherever a TriggerScope scan needs one.

**Developer / Internal**

- The acquisition-layout contract is now tested at the seam, not only per layer. ``test_acquisition_layout_recording_seam.py`` records three scans through every real stage — the Galvo and Advanced-TTL signal designers generate the scan, the producer builders describe it (through the controller-level accessor, so device mapping, directions and physical-axis overrides are exercised as the rig will use them), ``startRecording`` gates it, the real recording worker and HDF5 storer write it under the simulated NI-DAQ with the repository's own mock camera and APD managers, and the ImProcess resolver reads the layout back. A camera point scan checks the planned frame count against the rising edges of the TTL that actually ran; two point detectors on a two-line-step scan check the assembled payload and its ``condition`` storage axis, and the gate's refusal of a frame-stream layout for an assembling detector; a two-item single-file scan lapse checks that both items land in one file as ``scan0``/``scan1`` and each resolves to its own ``time`` partition. Nothing between the stages is faked, which is the property the per-layer tests could not have: each of them agreed with its own idea of the neighbour, and that is how a queue cap sized for point detectors came to be applied to cameras without a failing test.
