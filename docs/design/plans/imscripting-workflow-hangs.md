Stable identifiers, never renumbered:

* **`D-nn`** — defects found in the current code (§2.1). Each states where, why it matters, how it was verified, and since when.
* **`C-nn`** — constraints: verified facts about the codebase, not choices (§2.2).

## 1. The failure chain

Two independent bugs combine into the reported symptom; a third bug can produce it on its own.

```
script thread                                   GUI thread
─────────────                                   ──────────
api.imcontrol.runScan()
  └─ _UIThreadExecWrapper: lock, emit, RETURN ─▶ (event queued)
waitForScanningToEnd = getWaitForSignal(scanEnded)
  └─ connect(slot)  ← listening starts HERE     runScan → runScanAdvanced → _beginScanRun
waitForScanningToEnd()                             ├─ armed:   ... later sigScanEnded ✔ (slot queued to script thread)
  while not emitted:                               └─ REJECTED: log warning, return None   ✘ no signal, ever
      processEvents(); sleep(1.0)
      …forever…                                  user clicks Stop / Run / closes window
                                                 ScriptExecutor.cancel()
                                                   ├─ requestStop()   (flag nobody reads)
                                                   ├─ thread.quit()   (no-op: exec() owns the loop)
                                                   └─ thread.wait()   ◀── UNBOUNDED JOIN → GUI frozen
```

1. **The script gets stuck** — either because `scanEnded` fired before the waiter existed (`runScan()` is fire-and-forget, so the ordering in the script is a race, **D-02**), or because the scan start was *rejected* and no terminal signal is ever published (**D-03**). Both reproduce headlessly (§2.1).
2. **The GUI then freezes** the moment anything calls `ScriptExecutor.cancel()` — the Stop button, "Run" while a script is running, or closing the window — because `cancel()` joins the script thread with no timeout on the GUI thread, and the script thread has no way to notice the cancel (**D-04**). On Windows this is the greyed-out "Not Responding" window; only killing the process helps.
3. Independently, **`changeScanPower` mutates Qt widgets from the script thread** (**D-01**). That is undefined behaviour in Qt and a known source of random freezes and crashes; it cannot be ruled out as a contributor to "sometimes".

Everything else in this plan is either a consequence of fixing these properly, or a sibling bug found on the way.

### 2.2 Constraints (verified facts the design must respect)

* **C-01** Scripts run in a dedicated `QThread` (`ExecutionThread` worker moved to a framework `Thread`); `exec(code)` blocks that thread's event loop for the whole run. API functions *without* `runOnUIThread` execute on the script thread.
* **C-02** PyQt creates the slot proxy for a plain Python callable in the thread that called `connect()`. `getWaitForSignal` therefore receives `scanEnded` as a **queued event on the script thread**, delivered only inside `FrameworkUtils.processPendingEventsCurrThread()` in its polling loop. Verified experimentally (offscreen Qt): slot ran on the worker thread, delivered by the worker's `processEvents`. Consequence: once the connection exists, an emission is *never* lost even if the script thread is busy — it waits in the queue. Only emissions *before* `connect()` are lost.
* **C-03** `runOnUIThread` wrappers post one event per call; Qt delivers events from one sender thread to the GUI thread in FIFO order, so `changeScanPower` → `runScan` ordering is preserved whether the calls are asynchronous or synchronous.
* **C-04** The same API objects are called from three places: scripts (script thread), the imscripting console (`pyqtgraph.console.ConsoleWidget`, **GUI thread**), and `ImSwitchServer` (FastAPI/uvicorn thread + Pyro). A blocking hand-off to the GUI thread must detect "already on the GUI thread" and call directly, or the console deadlocks.
* **C-05** `framework.base.Thread.wait()` has no timeout overload; `NidaqManager._joinThreadBounded` already works around this with a `TypeError` fallback, so adding an optional `timeoutMs` is backward compatible.
* **C-06** `sigScanEnded` is published exactly once per run on every terminal path *that published `sigScanStarting`*. Pre-reservation rejections publish nothing, deliberately: a duplicate start "must never … call `scanFailed()` on the original still-running scan". Emitting `sigScanEnded` on rejection would tell FocusLock/Recording that the *running* scan ended. Any rejection signal must be a new, distinct one.
* **C-07** The rig runs Windows (COM ports in the setup file); a greyed window = "Not Responding" = GUI thread blocked ≥ 5 s.
* **C-08** Test conventions: pytest + pytest-qt (`qtbot`), scripting tests in `imswitch/imscripting/_test/unit/test_script_execution.py`; `docs/api/_actions.rst` and `docs/api/api.imcontrol.rst` are generated by `tools/generateapidocs.py`; user-facing docs are Sphinx `.rst`; `.md` plan docs under `docs/design/plans/` are work-in-progress only.
* **C-09** Python's `exec()` cannot be interrupted from outside except cooperatively or via `ctypes.pythonapi.PyThreadState_SetAsyncExc` (public C-API, delivered at the next bytecode boundary; blocking C calls such as `time.sleep` or a serial read finish first).
* **C-10 (r2)** Module lifecycle: `imscripting` is moved to the end of the enabled-module list so it is created last; `launchApp` shows the window, runs `app.exec_()`, then calls `closeEvent()` on each module controller in that same order, catching and logging exceptions. There is no pre-close phase.
* **C-11 (r2)** The workflow layer already implements ordering-proof scan completion: `WorkflowServices.run_scan(...)` marshals dispatch onto the UI thread, runs the side-effect-free `_externalScanStartRefusal` pre-flight (completion still publishing / active iteration / active run → refusal *before* any lifecycle signal), publishes `sigScanStarting`, and pairs a refused-after-start request with `sigScanEnded` itself. An accepted request yields a `ScanRequestCompletion` bound to the exact run token, with `wait(timeout) -> bool`, `successful`, `message`, `add_done_callback`. `ScanWorkflowFacade.run_once(wait=True, timeout_s=…)` wraps it, refuses to block on the UI thread, and requires an exact-capable (coordinated) scan source.
* **C-12 (r2; corrected r3 after R-11)** `stopRecording()` only sets the REC button unchecked; Qt emits `toggled` solely on a state change, so when nothing is recording the controller and manager are never called and **no `recordingEnded` follows**. `RecordingManager.endRecording()` itself emits the terminal only for a live generation that has not already ended (`_signalRecordingEnded` returns early for generation ≤ 0 or an already-emitted end). An unconditional "stop and wait for `recordingEnded`" therefore times out when idle, after a failed start, or after a completed run. There is no `isRecording()` API today.
* **C-13 (r2)** `_scanCompletionPublishing` is set at the top of `_publishScanDone` (before `sigScanDone`) and in `scanFailed`, and cleared only in `completeRequest`/`completeFailure` after the run release has been finalized. It therefore covers the whole deferred-release window for the owning controller.
* **C-14 (r2.1)** There are **two scan-controller families** on the one shared coordinator. (a) The `SuperScanController` family (Scan widget: `ScanControllerBase`, `ScanControllerAdvanced`, `ScanControllerMoNaLISA`, `ScanControllerPointScan`): `_beginScanRun`, `runScanExternal` reports acceptance and binds a `ScanRequestCompletion`, `_externalScanStartRefusal` pre-flight, `supportsExactScanRequestCompletion = True`. (b) The `TriggerScopeScanLifecycleMixin` family (Raster, LSXYR, PLSR, PLSRMulticolor, GalvoDetection, the unified `TriggerScopeScanController`, `LightSheetMulticolorController`): reserves/arms/resolves on the same coordinator, has its own duplicate/busy gates that `return False` **silently** (log only — the same D-03 shape), already treats `ScanBusyError` as contention rather than failure, but does **not** report on requests and binds no completion — so the dispatch path sees `handled=False`, treats it as a legacy receiver, and `ScanWorkflowFacade.run_once(wait=True)` refuses it. Both families derive from `ScanLifecycleMixin` ([basecontrollers.py:241](../../../imswitch/imcontrol/controller/basecontrollers.py)), which today provides only `isRunning` and actuator publication. Event-triggered controllers (EtSTED, EtMonalisa, EtSnouty) and `RotationScanController` are *consumers* that start scans through signals; they expose no scan-start API of their own.
* **C-15 (r2.1)** Scan-source resolution (`CommunicationChannel.getRecordingScanSource(preferredKey)`): an explicit key → the canonical `Scan` controller → a lone capable controller → otherwise a `RuntimeError` naming the candidates (ambiguity fails closed). The workflow dispatch onto the UI thread is bounded (30 s) and cancellable while still queued.

## 4. Decisions

### A-01 — API calls from non-GUI threads become synchronous, with return values, exceptions, and Stop-synchronous cancellation of pending calls **(r2, R-01; r3, R-08, R-10)**

`_UIThreadExecWrapper.__call__` executes the API function on the GUI thread and **waits for it**, returning its value and re-raising any exception in the caller's thread. Script statements then behave the way every script author already assumes: in order, and `x = api.imcontrol.snapImage(output=True)` actually yields an array. The REST/Pyro server gets real return values for free.

Mechanism (no `BlockingQueuedConnection`, which cannot carry a result and deadlocks on same-thread use):

```python
class _Invocation:                       # one per call; plain object, no Qt
    PENDING, RUNNING, DONE, CANCELLED = range(4)
    # args, kwargs, result, exception, state, epoch, done = threading.Event()

class _UIThreadExecWrapper(SignalInterface):
    _sigInvoke = Signal(object)          # AutoConnection: queued from other threads

    def __call__(self, *args, **kwargs):
        apiGate.checkOpen()                                # A-08: raises during shutdown
        if QtCore.QThread.currentThread() is self.thread():
            return self._apiFunc(*args, **kwargs)          # console / GUI callers: direct (C-04)
        token = currentCancelToken()                       # may be None outside a script run
        inv = token.openInvocation(args, kwargs) if token else _Invocation(args, kwargs)
        #   openInvocation(): under the token lock — REQUESTED → deliver now (raise
        #   OperationCancelled, nothing dispatched); EXPIRED → raise; IDLE → epoch 0;
        #   DELIVERED → epoch 1 (authorised cleanup call); registers inv as in-flight.
        self._sigInvoke.emit(inv)
        inv.waitDone(token)                                # 50 ms poll; token-aware (A-02)
        if inv.exception is not None: raise inv.exception
        return inv.result

    def _invoke(self, inv):              # GUI thread
        if not inv.start():              # decided under the token lock (see below)
            inv.finish(skipped=True); return
        try: inv.result = self._apiFunc(*inv.args, **inv.kwargs)
        except BaseException as e: inv.exception = e
        finally: inv.finish()
```

* **Stop is decided on the GUI thread, synchronously (R-08).** `CancelToken.requestStop()` runs on the GUI thread (Stop button, run-while-running, shutdown). Under the token lock it moves `IDLE → REQUESTED` **and cancels the registered in-flight invocation if it is still `PENDING` with epoch 0**. `inv.start()` on the GUI thread also takes the token lock and admits only `PENDING` invocations whose epoch matches the token state (`IDLE` → epoch 0; `DELIVERED` → epoch 1; anything else → skip). Because `requestStop()` and `_invoke` both execute on the GUI thread, their order is total: an invocation dispatched (in GUI-thread order) after Stop never runs, whatever the worker's poll timing. A cleanup call issued after delivery carries epoch 1 and runs; once `EXPIRED`, `openInvocation` refuses before dispatch and `start()` skips whatever is left.
* **A running invocation cannot be aborted** (it is Python code on the GUI thread); the caller keeps waiting for it to finish — this cannot deadlock because the GUI thread is by definition executing it — and then `OperationCancelled` is raised in the caller's thread per A-02. Only one invocation per script thread can ever be pending or running, because the script blocks on it.
* **The gate covers every export, not just UI ones (R-10).** `generateAPI` wraps non-UI exports in a thin `_GatedExport` callable that checks `apiGate` and then calls the raw method on the caller's thread (as today); it preserves `__name__`, `__doc__`, `__signature__` and `__wrapped__`, which `tools/generateapidocs.py` and `ImSwitchServer` read. The gate is a fail-fast line for API calls during the drain; it is *not* the isolation guarantee — that is the thread drain of A-08.
* The per-call object replaces the cross-thread `QMutex` (D-05's undefined unlock). `currentCancelToken()` is a thread-local accessor in a new tiny module `imswitch/imcommon/model/cancellation.py` (`OperationCancelled(BaseException)`, `CancelToken`, `setCurrentCancelToken`, `currentCancelToken`). `imcommon` must not import `imscripting`; imscripting sets the token at run start. Timeout: none by default — API calls such as `snapImage` legitimately take seconds — but cancellable.

Rejected: (a) keep fire-and-forget and add a `waitForUIThread()` action — leaves D-05 unfixed and keeps the ordering trap; (b) `QMetaObject.invokeMethod` with `BlockingQueuedConnection` — no return value, deadlocks from the console; (c) run the API function on the script thread with a global GUI lock — Qt widgets are GUI-thread-only, full stop; (d) executing already-queued calls after cancel "because they were requested" — a `runScan` landing after Stop is exactly what an operator pressing Stop wants to prevent (R-01); (e) letting the worker cancel its own pending call on its next poll (r2) — loses the race to the GUI thread (R-08).

### A-02 — Cooperative cancellation with a bounded cleanup window, then escalation **(r2, R-02)**

* `ExecutionThread` owns one `CancelToken` per run and publishes it thread-locally (A-01). The token is a small state machine, all transitions under a lock:

| State | Entered when | Cooperative waits (`getWaitForSignal`, `sleep`, `waitUntil`, `_Invocation.waitDone`) | API invocations |
| --- | --- | --- | --- |
| `IDLE` | run start | wait normally | run normally |
| `REQUESTED` | Stop clicked / `shutdown()` / run-while-running (t₀) | the **first** wait reached cancels its pending invocation (if any) and raises `OperationCancelled` → token becomes `DELIVERED` | a pending call is skipped (A-01); a running call completes |
| `DELIVERED` | first delivery (cooperative or injected) | wait normally, bounded by their own timeouts — this is the **cleanup window**; `finally` blocks can stop recording, park stages, close files | run normally |
| `EXPIRED` | t₀ + `CLEANUP_BUDGET_S` (default 30 s, **Q-09**) with the thread still alive | raise `OperationCancelled` immediately, every time | refused (`OperationCancelled` before dispatch) |

* `OperationCancelled` derives from `BaseException` (like `KeyboardInterrupt`) so a user script's `except Exception:` cannot swallow it. `ExecutionThread.execute` catches it and marks the result `CANCELLED`; if the token expired before the thread ended, the result additionally records `cleanupTimedOut=True` and a warning is logged.
* Escalation, two stages: (1) if `REQUESTED` has not become `DELIVERED` within `ESCALATE_AFTER_MS` (default 2000 — the script is not at any cooperative point, e.g. `while True: pass`), `ExecutionThread.interrupt()` injects `OperationCancelled` once via `ctypes.pythonapi.PyThreadState_SetAsyncExc(threadIdent, OperationCancelled)`; the token then becomes `DELIVERED` and the cleanup window starts. (2) once `EXPIRED`, `interrupt()` is repeated every second until the thread ends. A script blocked inside a C call (`time.sleep(600)`, a serial read) ends when that call returns (C-09). Documented; the `sleep()` action is the cancellable replacement.
* Interaction with `finally` (R-02): because delivery happens once, a cleanup block written as `callAndWaitForSignal(recordingEnded, stopRecording, timeout=60)` runs to completion (or to its own timeout) inside the window. A cleanup that itself needs more than the budget is cut off — deliberately bounded, and reported.

Rejected: `QThread.terminate()` (the unsafe approach the June commit removed — leaves Qt/serial state corrupt); `sys.settrace`-based cancellation (10× slowdown of every script); delivering `OperationCancelled` at every wait after Stop (r1 — makes cleanup impossible, R-02); an unbounded cleanup window (re-creates the "only killing helps" case with extra steps).

### A-03 — `cancel()` never blocks the GUI thread; `shutdown()` is bounded **(r2, R-02, R-03)**

* `framework.Thread.wait(timeoutMs=None) -> bool` (both `base` and `qt`); no-arg behaviour unchanged (C-05).
* `ScriptExecutor.cancel() -> None` is **non-blocking**: it moves the token to `REQUESTED`, arms the escalation timer (a `QTimer` on the executor's thread), and returns. `isExecuting()` stays true until the thread really ends; `sigExecutionFinished` is emitted then, as today. `execute()` while a run is winding down does **not** start: it stores the pending `(path, code)` and starts it from the `sigExecutionFinished` handler, so a replacement script can never overlap the previous script's cleanup window (R-02). If cleanup expired and the thread still has not ended, `execute()` refuses with a logged, user-visible message ("previous script is still stopping") instead of starting.
* `ScriptExecutor.shutdown(timeoutMs=3000) -> bool` (used only by A-08): `cancel()` with the cleanup budget clamped to the bound, bounded `wait`, escalation, one more bounded wait; returns whether the thread ended. It never blocks longer than ~2 × `timeoutMs`. It does **not** `terminate()` — the process is exiting anyway and a leaked thread is harmless at that point, while `terminate()` during `finally` blocks could corrupt files being closed.
* `EditorController.stopExecution`: confirm dialog as today, then `cancel()`, disable Stop and show "Stopping…" until `sigExecutionFinished`. `runCurrentCode` while running: the existing Yes/No dialog, then `cancel()` + deferred start (above). `EditorController` gains `closeEvent()` → `scriptExecutor.shutdown()` as the module-level fallback; the authoritative shutdown ordering is A-08.
* `__del__` calls `shutdown()`, never a bare join.

### A-04 — `getWaitForSignal` contract and new wait helpers **(r2 note, R-04)**

```python
getWaitForSignal(signal, pollIntervalSeconds=0.05, timeout=None) -> Callable[[], None]
```

* The returned `wait()` raises `TimeoutError` after `timeout` seconds (None = wait forever, unchanged default; **Q-02**), raises `OperationCancelled` per the A-02 token state, and always disconnects in `finally`.
* Default poll interval 1 s → 50 ms (D-07). `processPendingEventsCurrThread()` stays: it is what delivers the queued slot (C-02).
* Contract documented on the function, in `docs/scripting.rst`, and in `example_record.py`: **create the waiter before triggering the action**.
* New actions in `_Actions`:
  * `sleep(seconds)` — cancellable sleep (50 ms slices, polls the token).
  * `waitUntil(predicate, timeout=None, pollIntervalSeconds=0.05)` — cancellable condition wait.
  * `callAndWaitForSignal(signal, func, *args, timeout=None, **kwargs)` — creates the waiter, calls `func(*args, **kwargs)`, waits; returns `func`'s result. Catches an emission that happens synchronously inside `func` (the D-02 r2 case).
* **What this does not fix (R-04):** a script that keeps the original "call, then create the waiter" order and passes no timeout can still miss a terminal that fires inside the call, and will then wait until Stop. The guarantee for such a script is A-02/A-03 — Stop ends it within the bound and the GUI never freezes — not completion. Completion for any ordering is what A-05's completion handle provides.
* `docs/api/_actions.rst` regenerated.

Rejected: making `wait()` return a bool on timeout — silent by default is how this bug survived; scripts must fail loudly. A sticky "already emitted" flag on the channel signals — it would need a per-consumer reset protocol; the exact completion handle already exists and is identity-scoped.

### A-05 — One request contract for every scan-controller family; the scan API exported once, dispatched through the pre-flighted path, returning a cooperative, serializable completion **(r2, R-04, R-06; r2.1; r3, R-07, R-09, R-12, R-13)**

Two controller families share the coordinator but not the request contract (C-14). The contract moves to the shared base, `ScanLifecycleMixin`, so every present and future scan controller inherits it — but the *API* is exported exactly once, by an object that is not a scanner.

* **Single owner of the scan API (R-13).** `runScan(source=None)`, `getScanSourceNames()` and `getScanRequestStatus(requestId)` are `@APIExport(runOnUIThread=True)` methods of the existing API-only `WorkflowFacadeController` (already in `apiObjs`, no widget; **Q-13** on naming). No scan controller exports `runScan`: the decorator is removed from `SuperScanController.runScan` and `TriggerScopeLSXYRController.runScan`; every family keeps `runScan` as the GUI slot for `sigRunScanClicked`. `generateAPI` over any number of scanners therefore builds without a name collision.
* **Pre-flight before any lifecycle signal (R-07).** The dispatcher calls `WorkflowServices.run_scan_prepared(recalculate_signals=True, is_non_final_part_of_sequence=False, notify_starting=True, preferred_source=source)` — the one dispatch path that checks ownership (active source, retained run, `_externalScanStartRefusal`) *before* setting `startingPublished` and emitting `sigScanStarting`. `run_scan_prepared` gains the `preferred_source` argument (a widget key handed to `getRecordingScanSource(preferredKey)`, C-15); `run_scan_from` is left as is. A refusal (`result.handled and not result.accepted`) raises `ScanRequestRejectedError(result.rejectionMessage)` with **no** global start or end having been published, so FocusLock and Recording never see a phantom terminal for a scan that is still running. Several capable controllers and no `source` → the existing fail-closed `RuntimeError` naming the candidates.
* **Request contract on the mixin (r2.1).** Three pieces the Scan family already has become mixin-level, with one hook per family: (1) `_externalScanStartRefusal()` — side-effect-free pre-flight over the coordinator's `activeToken`/`activeRunToken`, plus a family hook for private flags (`_scanCompletionPublishing` for the Scan family; `_scanStopRequested` / `releaseRequested` for TriggerScope); (2) acceptance reporting (`report_scan_request_result`) and `ScanRequestCompletion` binding immediately after `reserveRun`, resolved from each family's own terminals (`_publishScanDone`/`scanFailed` vs `_completeTriggerScopeIteration`/`_failTriggerScopeScan`); (3) `supportsExactScanRequestCompletion = True` on the mixin. Reporting is a no-op outside an active request envelope, so the GUI Scan-button paths are behaviour-preserving. The TriggerScope family's existing `except ScanBusyError` ("contention, not failure") becomes the shared rule: `_beginScanRun` gets the same `try/except` (the cross-owner case of D-10).
* **Every silent refusal becomes observable.** All `return None` / `return False` refusal branches in `_beginScanRun` **and** `_startTriggerScopeScan` record a reason and emit a new `CommunicationChannel.sigScanRequestRejected(str)`. `signals()` additionally exposes `scanStarting`, `scanStarted`, `scanDone`, `scanRejected`; its docstring is updated.
* **The handle (R-09, R-12).** An accepted request returns a `ScanRunHandle` (in-process object) with `requestId`, `source`, `state` (`pending | succeeded | failed`), `message`, `done`, `add_done_callback`, `to_dict()`, and `wait(timeout=None) -> bool`. `wait` is a **token-aware polling wait**: 50 ms slices on the completion event, a monotonic deadline, and the A-02 token rules (raises `OperationCancelled` on the first delivery and again after the cleanup deadline); it raises `RuntimeError` when called on the GUI thread, pointing console users at `done`/`wait(timeout=0)`/`add_done_callback`. Exception injection is therefore no longer needed to wake it. The dispatcher keeps a bounded registry of recent handles (last 64 by `requestId`); `getScanRequestStatus(requestId)` returns `to_dict()`. **Transport:** `ImSwitchServer.createAPI` wraps every result in `_serialize_api_result`, which turns objects exposing `to_dict()` into plain dicts (numpy already has its `Serializer`); the same `Serializer` registry in `server/_serialize.py` gets a `ScanRunHandle` entry for Pyro. REST/Pyro callers therefore receive `{"requestId", "source", "state", "message"}` from `runScan` and poll `getScanRequestStatus`. **Q-08** covers the in-process return-type change (was `None`).
* New action `runScanAndWait(timeout=None, source=None) -> None`: `handle = api.imcontrol.runScan(source); if not handle.wait(timeout): raise TimeoutError; if not handle.successful: raise ScanFailedError(handle.message)`. It is the script-level equivalent of `ScanWorkflowFacade.run_once(wait=True)`; with the contract on the mixin, `run_once(wait=True)` also starts working for the TriggerScope family.
* **Scope boundary.** Nothing in this decision changes how a scan is built, armed, finished or recorded: the designers, the NI-DAQ and TriggerScope managers, the coordinator, detectors and the recording manager are untouched. What changes: the API entry point (defined once on an API-only owner, dispatched through the existing pre-flighted path, Repeat consequence in **Q-10**), one new optional argument on `run_scan_prepared`, the request contract moving from one family to the shared mixin (**Q-11**), instrumentation on refusal branches, one `try/except`, and a result adapter in the server. The GUI Scan buttons keep calling `runScanAdvanced` directly.

Rejected: `run_scan_from` as the dispatch path (r2 — publishes a start before the refusal check, R-07); a decorated `runScan` on the mixin (r2.1 — duplicate exports on multi-scanner rigs, R-13); a plain `Event.wait` handle (r2.1 — not cancellable, R-09); returning the live handle over REST (r2.1 — not serializable, R-12); emitting `sigScanEnded` on rejection (C-06); returning `False` from `runScan()` (silent by default, see A-04's rationale).

### A-06 — Widget-touching API exports run on the GUI thread, enforced by explicit tests **(r2, R-05)**

Same shape for `loadSetupMode` with a fake registry recording the applying thread.

### A-07 — Per-thread stdout routing (optional, P-6)

Replace `redirect_stdout/err` with one process-wide `_ThreadRoutingStream` installed at `ScriptExecutor` construction: `write()` routes to the active run's `SignaledStringIO` when called from the run's thread, else to the original stream. Restore on shutdown only if `sys.stdout` is still ours (the pyqtgraph console swaps `sys.stdout` around its own `runCmd`, so never clobber a foreign replacement). ### A-08 — Application-level shutdown phase: a *drain barrier* for scripting, reusing imcontrol's existing fail-closed policy **(r2, R-03; r3, R-10)**

What isolates hardware from a script at shutdown is not a gate but the absence of any thread that can still call into it. The threads that can are: the script thread, the REST/Pyro server threads (already drained with a bounded join by `ImConMainController.closeEvent`), and the GUI thread itself (which runs no user code once the event loop has exited, except queued invocations delivered while the controller barrier pumps events — which the gate now skips). Retained workflow facades and raw non-UI exports are reachable only from those threads, so draining them is the isolation guarantee.

* `launchApp` gains a phase between `app.exec_()` returning and the `closeEvent()` loop: for each module controller in **reverse** creation order (imscripting first, C-10), call `prepareShutdown()` if present, guarded like `closeEvent`. Results are recorded in a process-wide `ShutdownState` (new, `imswitch/imcommon/model/shutdown.py`: `begin()`, `scriptingDrained: bool | None`, `reasons`).
* `ImScrMainController.prepareShutdown()`: `apiGate.close()` (every export, A-01), then `scriptExecutor.shutdown(timeoutMs)`: cooperative request → 2 s → `interrupt()` → repeated injection every 1 s → hard cap `SHUTDOWN_DRAIN_CAP_S` (default 10 s, **Q-12**). Returns whether the thread ended; the result goes into `ShutdownState.scriptingDrained`.
* **Failure policy = the existing one.** `ImConMainController.closeEvent` already refuses to finalize hardware managers when its controller barrier or the server drain times out ("Skipping hardware-manager finalization because … did not drain within the shutdown deadline", returns `False`). It gains one more condition: `ShutdownState.scriptingDrained is False` → same log line naming the script, same `return False`, managers not finalized. The process still exits (the leaked thread is a daemon-equivalent at that point); the operator sees an error naming the script, and no manager `finalize()` runs under a live worker. No `terminate()` anywhere: terminating a thread that may hold the GIL or a serial handle is worse than not finalizing.
* `MultiModuleWindow.closeEvent` is unchanged (`QApplication.quit()`).
* Integration tests (P-9): three fake module controllers recording call order (`prepareShutdown` reverse, then `closeEvent` forward); a script blocked in a cooperative wait ends within the bound and `scriptingDrained` is `True`; a script that swallows `BaseException` in a loop trips the cap, `scriptingDrained` is `False`, and a fake `ImConMainController.closeEvent` skips `masterController.closeEvent()`; **event delivery during teardown**: an invocation queued before `prepareShutdown` is skipped even when a fake controller barrier loop calls `processPendingEventsCurrThread()`; a non-UI export raises after the gate closes.

Rejected: relying on `EditorController.closeEvent` (r1 — runs last by construction, C-10); reordering module creation (imscripting is created last because its API scope needs every other module's API to exist); treating the wrapper gate as isolation (r2 — R-10); `terminate()` as a last resort (r2 draft — GIL/serial-handle corruption); blocking teardown indefinitely on the script thread (re-creates the original bug at exit).

### A-09 — Idempotent recording stop contract: `isRecording()` and `stopRecording() -> bool` **(r2, R-02; r3, R-11)**

* `RecordingController.isRecording() -> bool` (`runOnUIThread=True`): the controller's `recording` flag.
* `stopRecording() -> bool` (`runOnUIThread=True`): returns `True` if a recording was active and its stop was requested (the REC button was checked and is now unchecked, so `recordingEnded` — or `recordingFailed` — **will** follow), `False` if nothing was recording (no signal will follow). Idempotent.
* Cleanup guidance (docs, examples, Appendix A): `if api.imcontrol.stopRecording(): waitForRecordingToEnd()` with the waiter created first, or the equivalent `if api.imcontrol.isRecording(): callAndWaitForSignal(signals.recordingEnded, api.imcontrol.stopRecording, timeout=60)`. The r2 claim that an unconditional stop-and-wait is safe is withdrawn (C-12).
* Tests through the public API (P-5): never started, failed start (manager arm failure → `recordingFailed`), already ended — `stopRecording()` returns `False` and no terminal is emitted; active → `True` and `recordingEnded` follows.

### A-10 — Scan-source contract test: discovered, not enumerated **(r2.1, new)**

The guarantee "solid for every scan type, including ones not written yet" has to be a test that finds new controllers by itself, not a list someone must remember to extend.

* `imswitch/imcontrol/_test/unit/test_scan_source_contract.py` imports `imswitch.imcontrol.controller.controllers`, collects every concrete class that defines `runScanExternal`, and parametrizes over them with the headless doubles the existing ownership tests already use (`test_scan_run_ownership.py`, `test_scan_once_recording_sources.py`). For each class it asserts:

## 9. Risks and rollback

* **A-01 timing change** is the only behavioural change visible to *working* scripts. Rollback is a one-line switch back to the queued path; keep the old class under a private name for one release? — No: two code paths is how D-05 survived four years. Rely on Q-01 sign-off and the rig run instead.
* **Async exception injection** (A-02) can, in theory, interrupt a script between two hardware commands. It is only used ≥ 2 s after a *user-requested* stop when the script has not reached any cooperative point, and again only after the cleanup budget expired — both cases today mean a frozen GUI.
* **`PyThreadState_SetAsyncExc` on the wrong thread id** would be catastrophic; the id is taken with `threading.get_ident()` *inside* the run and the call is guarded by `isExecuting()`.
* **Cleanup window vs. Stop expectations (r2):** after Stop, a script may keep issuing API calls for up to 30 s (its cleanup). The editor shows "Stopping…" for that time; the escalation after expiry is the backstop. If this feels wrong on the rig, the budget is one constant.
* **A-05 depends on the workflow dispatch path (r2):** `run_scan_from` requires a resolvable scan source; on a setup where `getRecordingScanSource()` cannot resolve one, `runScan()` raises instead of silently broadcasting — the same fail-closed rule the recording controller already follows.
* **P-5 touches the scan-ownership core.** Changes are confined to `_beginScanRun`'s exit branches, one `try/except` around `reserveRun`, and the API entry point; the R9–R12 lifecycle tests and the facade tests are the safety net and must stay green untouched.
* **r3 touches `WorkflowServices.run_scan_prepared`** (one optional argument threaded to the existing resolver) and `ImConMainController.closeEvent` (one more fail-closed condition of the same shape as the two it already has). Both are covered by their existing test files plus the new ones; neither changes a code path that runs when no script or workflow is involved.
* **r2.1 touches the TriggerScope lifecycle mixin** (completion binding + reporting + rejection signal). All three are additive: reporting is a no-op without an active request envelope, the completion is unobserved unless someone holds it, and the signal has no listeners in the GUI. The existing TriggerScope geometry/lifecycle tests plus the A-10 discovery test are the net. If Q-11 is answered "later", P-5 shrinks by 1 d and A-10 gets a temporary allow-list naming that family — which is exactly the kind of list this plan argues against.

* **`execute()` while stopping defers instead of refusing (A-03).** The new run starts from the `sigExecutionFinished` handler; a second `execute()` replaces the pending one (its result is marked cancelled). No click is lost and no overlap is possible.
* **A run that caught `OperationCancelled` and returned normally is reported CANCELLED**, not SUCCEEDED (the stop was requested).
* **Leaked script threads (A-08 failure policy).** Destroying a running `QThread` makes Qt abort the process, so `ScriptExecutor.shutdown()` keeps an undrained thread referenced for the process lifetime and `launchApp` exits with `os._exit` (after `logging.shutdown()`) when `ShutdownState` says scripting did not drain — no finalizers, no abort, error logged with the script's name.

* **`_recordScanStartRejection` and the TriggerScope bookkeeping use `self.__dict__.get`**, not `getattr(..., default)`: on a QObject shell built with `__new__` (the boundary-test pattern) sip raises from `getattr` even with a default.

## Appendix A — the trigger script, written to the new contract **(r2, R-02)**

```python
import numpy as np

mainWindow.setCurrentModule('imcontrol')
signals = api.imcontrol.signals()
laser = api.imcontrol.getLaserNames()[0]   # check this really is the 405 on your setup
powers = np.array([0, 0, 0, 0, 0, 0, 3, 5, 10, 25, 50, 100, 200])

api.imcontrol.setRecModeUntilStop()
try:
    # Startup is inside the cleanup scope: a timeout or a Stop during arming
    # still reaches the finally block (R-02).
    callAndWaitForSignal(signals.recordingStarted, api.imcontrol.startRecording, timeout=30)
    for p in powers:
        api.imcontrol.changeScanPower(laser, float(p))     # synchronous (A-01)
        runScanAndWait(timeout=600)                         # exact completion, any ordering (A-05);
                                                            # Stop interrupts it immediately (R-09)
        getLogger().info(f'scan at {p} mW done')
finally:
    # Runs inside the cleanup window after Stop (A-02). stopRecording() is
    # idempotent and reports whether a terminal will follow (A-09, R-11):
    # only wait for recordingEnded when one is actually coming.
    waitForRecordingToEnd = getWaitForSignal(signals.recordingEnded, timeout=60)
    if api.imcontrol.stopRecording():
        waitForRecordingToEnd()
```

### R-01 [P1] — Cancel queued commands before they reach hardware

**Applies to:** A-01, P-4.

A-01 explicitly allows a queued invocation to execute after its script has been
cancelled. A pending `runScan`, `startRecording`, or laser change can therefore
take effect after Stop or after a replacement script starts. Discarding the
return value does not prevent the hardware side effect.

**Requested resolution:** Give each invocation a synchronized
pending/running/cancelled state. Skip cancelled pending calls on the GUI thread,
and define separately what cancellation means once a call has started. Add a
test that cancels before dispatch and verifies that the API function is never
executed.

### R-02 [P1] — Define how cleanup runs under cancellation

**Applies to:** A-02, A-03, A-04, Appendix A.

The cancel token remains set while the script unwinds through `finally`. In
Appendix A, `stopRecording` is queued, but its API wait or the subsequent
`recordingEnded` wait raises `OperationCancelled` again. The executor can report
completion and start a replacement script before recording finishes. Also,
recording startup is outside the `try`, so a startup timeout bypasses cleanup
entirely even if the asynchronous start later succeeds.

**Requested resolution:** Define a bounded cleanup mechanism that can await
shutdown despite cancellation, including how escalation interacts with cleanup.
Place recording startup inside the cleanup scope and define cleanup for a
partially completed start. Test Stop followed immediately by Run, cancellation
during startup, and startup timeout; verify recording cleanup completes or
reports a bounded failure before a replacement run begins.

### R-03 [P1] — Stop scripting before hardware teardown begins

**Applies to:** A-03, P-1, P-8.

An `EditorController.closeEvent` hook alone does not establish safe shutdown
order. In [applaunch.py](../../../imswitch/imcommon/applaunch.py), `launchApp`
calls module close hooks in creation order after `app.exec_()` returns.
`imcontrol` can therefore close its controllers and hardware before `imscripting`
requests cancellation. Controller shutdown polling also processes queued GUI
events, allowing pending script commands to execute during teardown.

**Requested resolution:** Add an application-level shutdown phase that cancels
scripting and rejects pending/new API work before hardware closure. Specify
what happens if a script cannot finish within the bound, rather than assuming
the editor close hook runs first. Add an integration test covering shutdown
order and queued API commands, not only the executor's bounded wait.

### R-04 [P2] — The unchanged script can still wait forever

**Applies to:** A-01, A-04, P-8 checklist item 1.

The original script creates its waiter after `runScan` and supplies no timeout.
Synchronous dispatch does not prevent `scanEnded` from firing before `runScan`
returns, and A-04 retains `timeout=None`. Such an emission remains lost and
cannot produce the promised `TimeoutError`. Rejection propagation fixes a
different path; it does not eliminate this ordering problem.

**Requested resolution:** Revise the unchanged-script acceptance criterion to
require bounded cancellation when an event is missed, or introduce a completion
mechanism that supports the original ordering. Keep successful completion and
explicit timeouts as acceptance criteria for the corrected script. Include a
test where the terminal signal is emitted before the API call returns.

### R-05 [P2] — The proposed audit misses both motivating regressions

**Applies to:** §2.3, A-06, P-3.

The current laser path is `changeScanPower` → `setLaserValue` → `_setLaserValue`
→ `_widget`, beyond the proposed one-hop check. `loadSetupMode` reaches widgets
through `registry.applyComponentState`, which that check also cannot follow.
The audit could stay green with both original defects present.

**Requested resolution:** Add explicit regression checks for these exports and
runtime thread-affinity coverage, or expand the analysis and document its
limits. Verify that removing `runOnUIThread=True` from either repaired export
actually causes its regression test to fail. Correct the one-hop audit claims
in the evidence section accordingly.

### R-06 [P2] — Revalidate D-10 against the current completion guard

**Applies to:** D-10, A-05, P-5.

The described path does not match the current normal completion flow in
[basecontrollers.py](../../../imswitch/imcontrol/controller/basecontrollers.py).
`_publishScanDone` sets `_scanCompletionPublishing` before publishing
`sigScanDone` and retains it until `completeRequest`. During deferred release,
`_beginScanRun` therefore returns at its first guard before reaching
`reserveRun`, even after `_scanRunToken` is cleared.

**Requested resolution:** Provide a reproduction that bypasses this guard or
revise D-10 and its regression test to reflect the current code. Catching
`ScanBusyError` inside `_beginScanRun` may still be useful for other rejection
paths, but the stated contamination of a finishing successful run needs current
evidence before being treated as a verified defect.

### R-07 [P1] — Pre-flight before publishing lifecycle signals

**Applies to:** C-11, A-05 workflow dispatch, P-5, A-10.

`run_scan_from` does not implement the pre-flight described in A-05. It calls
`_dispatch_with_lifecycle`, which emits `sigScanStarting` before invoking
`runScanExternal`. That controller method then checks for refusal. When it
reports refusal, `_pair_unowned_scan_start` emits `sigScanEnded`. The earlier
pre-flight belongs to `run_scan_prepared`, a different service method. Moving
the controller's refusal method to a mixin does not move it ahead of the
service's signal emission.

**Verified:** With a source reporting an active-iteration refusal, the current
`run_scan_from` emitted one start and one end; `run_scan_prepared` emitted
neither. Routing a duplicate API scan through the proposed method would publish
an end while the original scan is still running, contrary to C-06. FocusLock
and Recording subscribe to that global lifecycle.

**Requested resolution:** Use a prepared dispatch that checks ownership before
any lifecycle signal while preserving the intended source. Extend scope to
`WorkflowServices` if necessary. Test a duplicate request during an active run
and assert no new global start/end signals and no change to its consumers.
A-10 should explicitly assert absence of `sigScanEnded` on refusal too.

### R-08 [P1] — Make pending dispatch observe Stop immediately

**Applies to:** A-01 `_Invocation.start` / `_invoke`, A-02 `REQUESTED`, P-4.

The invocation lock protects `inv.cancel()` against `inv.start()`, but Stop
only changes the run token. The worker calls `inv.cancel()` later, after its
50 ms poll wakes. In that interval the GUI can process the queued invocation:
`_invoke` sees an open gate, `start()` sees `PENDING`, and a scan or laser change
executes even though Stop was handled first. The state machine does not yet
provide the stated no-start-after-Stop guarantee.

**Requested resolution:** Couple dispatch authorization to the run's
cancellation state, with a synchronized decision at invocation start, or
synchronously cancel that run's registered pending invocations when requesting
Stop. Distinguish newly authorized cleanup calls from calls queued before Stop.
Test the adverse ordering: queue a call, handle Stop, dispatch on the GUI before
the worker polls, and verify the function never runs.

### R-09 [P1] — Make completion-handle waits cooperative and GUI-safe

**Applies to:** A-02 cooperative-wait list, A-05 `ScanRunHandle.wait` and
`runScanAndWait`, P-5, §8 items 3–4.

The new helper calls `handle.wait(timeout)` directly, while the existing
`ScanRequestCompletion.wait` delegates to `threading.Event.wait`. It does not
poll the cancellation token. The corrected example passes 600 seconds, so Stop
during a stalled scan could leave it blocked for ten minutes; the default
`None` can block indefinitely. Exception injection does not wake this wait.
A raw handle wait on the GUI thread can also prevent the completion callback
from executing, so checking only `runScanAndWait`'s thread is insufficient.

**Verified:** Injecting a cancellation exception into a worker blocked in the
real `ScanRequestCompletion.wait` did not finish the worker within 200 ms. The
worker caught the exception only after the completion was explicitly resolved.

**Requested resolution:** Implement a token-aware polling wait in the public
handle, respecting a monotonic timeout and cleanup deadline; reject blocking
GUI-thread use there too. Add Stop-during-unresolved-completion and direct
console-handle tests. Require the corrected script to reach recording cleanup
without waiting for scan completion or the 600-second timeout.

### R-10 [P1] — Do not treat the UI API gate as isolation from hardware

**Applies to:** A-01, A-03 shutdown timeout, A-08, §0.1 R-03.

A-08 continues hardware teardown when a script fails to stop, claiming the
gate guarantees it cannot reach controllers or hardware. The proposed gate is
in `_UIThreadExecWrapper`, and P-4 leaves `generateAPI` otherwise unchanged:
non-UI exports remain raw bound methods. Scripts can also retain a workflow
facade created by `buildWorkflowFacade`, whose operations call hardware through
an independent path. A script or operation still running after the shutdown
deadline is therefore not isolated by closing this gate.

The withdrawal of R-03's event-processing evidence is also incorrect:
`ImConMainController.closeEvent` calls
`closeAllCreatedControllers(waitTimeoutS=30.0)`, whose pending-controller loop
explicitly calls `FrameworkUtils.processPendingEventsCurrThread()` in
`imcommon/controller/basecontrollers.py:84`. Queued work can interleave with
teardown even after the main event loop returns.

**Requested resolution:** Define a shutdown barrier covering all supported
hardware entry points and outstanding operations, including retained facades
and non-UI exports. Do not finalize managers still reachable by an undrained
worker merely because a UI wrapper gate closed. Specify a failure policy when
the deadline expires and test it, plus event delivery during controller
shutdown. Restore the original event-processing evidence in §0.1/D-12/A-08.

### R-11 [P2] — An idle recording stop does not always emit a terminal

**Applies to:** C-12, A-09, Appendix A cleanup comments.

`endRecording()` calls `_signalRecordingEnded`, but that helper suppresses the
signal when the generation is zero or its end was already emitted. The public
`stopRecording()` takes another path: it sets the REC button to unchecked.
When the button is already unchecked, its `toggled` signal does not fire and
the manager is not called at all. Consequently an unconditional
`callAndWaitForSignal(recordingEnded, stopRecording)` can time out when idle or
after a failed/completed start. The guarded Appendix A example avoids the
simple idle case; the advertised unconditional alternative does not.

**Requested resolution:** Correct C-12 and the cleanup guidance. Define an
explicit idempotent stop/completion contract if unconditional cleanup is
desired. Test never-started, failed-start and already-ended recordings through
the public API, rather than inferring the contract from the manager docstring.

### R-12 [P2] — Define transport serialization for the new scan handle

**Applies to:** A-05 `ScanRunHandle`, Q-08, P-5, §8 item 7.

The plan promises JSON from REST, but a live handle wrapping
`ScanRequestCompletion` contains an event, locks and an owner reference.
`ImSwitchServer` currently returns the API result directly; no transport
adapter or serialized schema is included in this plan. A read-only Python
wrapper does not itself make that state JSON-serializable or Pyro-serializable.

**Verified:** FastAPI's `jsonable_encoder` raised `ValueError` for a minimal
wrapper exposing the proposed wait/successful/message interface over the real
completion object. This checks the proposed shape, not an implemented
`ScanRunHandle` (which does not exist yet).

**Requested resolution:** Specify a serializable status/identity representation
and the REST/Pyro adapters that return it, while keeping the local wait handle
for scripts. Add an endpoint serialization test for pending and completed
requests; a fake-API `getRecFolder` smoke test cannot validate this return type.

### R-13 [P1] — Export the scan dispatcher once per combined API

**Applies to:** A-05 shared-mixin API, A-10 discovery tests, P-5 (r2.1).

Defining `runScan` once in a mixin still exposes a bound method on every scanner
instance. `ImConMainController` passes all its controllers to `generateAPI`,
which rejects any duplicate exported name. Once multiple scanner controllers
inherit the newly decorated method, API construction raises before a script
can use `source=`. This breaks precisely the multi-scanner setups A-05 intends
to support. A-10's per-controller `generateAPI([controller])` test misses it.

**Verified:** Calling the real `generateAPI` on two distinct subclasses that
inherit one decorated `runScan` raised
`NameError: API method name "runScan" is already in use`.

**Requested resolution:** Export a single source-selecting dispatcher from an
API/service owner and leave per-controller hooks internal, or explicitly define
how API generation deduplicates this dispatcher without hiding unrelated name
collisions. Add a combined-API test with two capable scanner instances and
verify that both explicit source selection and ambiguity handling work.
