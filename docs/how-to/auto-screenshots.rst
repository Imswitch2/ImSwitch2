******************************************
Auto-screenshot widgets for the docs
******************************************

Every widget image under ``docs/images/auto/`` is regenerated by a
single script that drives Qt headlessly and grabs each widget in
isolation.  This keeps the GUI documentation in sync with the code
without anyone having to remember to take fresh screenshots.

Run it
======

.. code-block:: bash

   # All widgets, each in isolation (default; see "Crash isolation" below)
   python tools/screenshot_widgets.py

   # One widget only
   python tools/screenshot_widgets.py LaserWidget

   # ALSO capture the full UI with a mock setup loaded —
   # widgets are populated with mock lasers, detectors, positioners
   python tools/screenshot_widgets.py --mock-setup

   # Mock-setup pass only (skip the per-widget standalone captures)
   python tools/screenshot_widgets.py --mock-only

   # Use a different bundled setup
   python tools/screenshot_widgets.py --mock-setup example_sted.json

   # Faster but no crash isolation; one segfault stops the whole run
   python tools/screenshot_widgets.py --no-subprocess

   # Render on the real display (default is offscreen)
   python tools/screenshot_widgets.py --show

Output goes to ``docs/images/auto/<WidgetName>.png`` for standalone
captures and ``docs/images/auto/mock-<dock>.png`` for the populated
mock-setup pass (plus ``mock-main-window.png``).

Two capture modes
=================

**Standalone (default).**  Each ``Widget`` subclass is constructed in
isolation with a stub ``Options`` instance.  Fast and dependency-free
but the layout is "empty": controllers haven't run, so per-laser rows,
per-positioner axes, and live plots are absent.

**Mock-setup (``--mock-setup``).**  Boots the full Imswitch2 main view
with a chosen example setup from
``imswitch/_data/user_defaults/imcontrol_setups/`` (default:
``example_no_hardware.json``).  Every widget is built by the real
factory with its controller attached, so the screenshots show actual
mock laser rows, mock positioner axes, the populated scan widget, the
napari viewer, and so on.  Internally this uses the same
``prepareUI`` helper as the UI test suite
(``imswitch.imcontrol._test.ui``).

Run both for the docs build — standalone gives clean per-widget
layouts; mock-setup gives realistic populated views.

Crash isolation
---------------

By default each widget is rendered in its own short-lived Python
subprocess.  Some widgets (anything OpenGL-backed via vispy or napari)
can crash hard on the headless ``offscreen`` Qt platform — without
isolation, a single ``SIGSEGV`` would end the whole run.  In subprocess
mode the parent reports the signal and moves on::

   skip ImageWidget: child killed by signal 11

If you need to debug a particular widget interactively, run with
``--no-subprocess`` and ``IMSWITCH_SCREENSHOT_DEBUG=1`` to get a full
traceback in-process.

How it works
============

The script walks ``imswitch.imcontrol.view.widgets``, finds every
concrete subclass of
:class:`~imswitch.imcontrol.view.widgets.basewidgets.Widget`, and tries
to instantiate it with stub arguments.  Each widget is shown briefly,
``QWidget.grab()`` is called, and the resulting :class:`QPixmap` is
saved as PNG.

By default ``QT_QPA_PLATFORM=offscreen`` is set so the script runs in
CI without a display server.  Use ``--show`` if you need to capture a
tooltip, popup menu, or other transient UI element that only renders
on a real surface.

Populators
==========

A *populator* is a small function that calls the same public methods
on a widget that its controller would normally call on init —
``addLaser(...)``, ``addPositioner(...)``, ``initControls(...)``, etc.
Without one, a standalone screenshot of e.g. ``ScanWidgetBase`` is just
an empty frame, because the scan-parameter grid is constructed
lazily from the positioner list.

Populators live in ``tools/screenshot_widgets.py`` next to a
``POPULATORS`` dict that maps widget class names to populator
functions.  The full set covers every widget the docs display; a few
highlights:

* ``_populate_laser`` — adds 405 / 488 / 561 (modulation-capable) /
  640 nm rows.
* ``_populate_positioner`` — adds X / Y / Z axes.
* ``_populate_scan`` — calls ``initControls`` with the same
  positioners + a few TTL devices; covers all four concrete scan
  widget variants.
* ``_populate_fft`` — pushes a synthetic FFT magnitude image
  (Gaussian DC + two rings) into the FFT widget so it shows a real
  picture, not a black square.
* ``_populate_flim_hist`` — feeds a bimodal lifetime distribution
  (~1.2 ns and ~3.5 ns populations) into the FLIM histogram widget.
* ``_populate_beadrec`` — drops a synthetic field of gaussian beads
  into ``BeadRecWidget`` so the reconstruction viewport renders.
* ``_populate_settings`` — adds a fake Hamamatsu camera with five
  representative ``DetectorNumberParameter`` /
  ``DetectorListParameter`` entries.
* ``_populate_leicastand`` — populates a cube turret with five
  filter cube choices.

Populators that need extra constructor args (e.g. ``ULensesWidget``
needs a ``napariViewer``) plug into ``_widget_stub_kwargs(name)`` next
to the registry.  ``ULensesWidget`` gets a duck-typed ``MagicMock``
viewer, which is enough because ``addItemToViewer`` swallows
``AttributeError``.

To add a populator for another widget:

1. Open its controller in
   ``imswitch/imcontrol/controller/controllers/<Foo>Controller.py``
   and find what it calls on ``self._widget`` during ``__init__``.
2. Write a function ``_populate_foo(w)`` that calls those same
   methods with realistic-looking fake data.
3. Register it in the ``POPULATORS`` dict.

If a populator raises, the capture still proceeds with whatever was
rendered up to that point — empty layout always beats no screenshot.

Adding a new widget
===================

If your new widget takes mandatory constructor arguments beyond the
standard ``options`` dict, register a stub in ``WIDGET_STUBS`` near
the top of ``tools/screenshot_widgets.py``:

.. code-block:: python

   WIDGET_STUBS = {
       "MyWidget": {"someRequiredArg": <stub-value>},
   }

The screenshot will be a *layout-only* capture: controllers populate
runtime-driven elements (one row per laser, scan plots, …) which are
absent here.  The intent is to keep the *visual structure* of each
widget — its buttons, panels, labels — discoverable in the docs.

For a fully populated screenshot (controllers active, mock setup
loaded) launch Imswitch2 with ``example_no_hardware.json`` and use
the standard OS screenshot tools.  Those images go to
``docs/images/`` (not ``auto/``) so the automated regeneration
doesn't overwrite them.

CI integration
==============

Add ``python tools/screenshot_widgets.py`` to your docs build before
``sphinx-build``.  On a headless runner you also need a Qt platform
backend — the offscreen backend ships with PyQt5, no system packages
required.
