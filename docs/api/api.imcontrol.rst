   .. method:: buildWorkflowFacade(**kwargs: Any) -> Any

      Build a MicroscopeFacade from the current master controller.

      ImSwitch's ``generateAPI`` flattens every ``@APIExport``'d method to
      the top level of ``api.imcontrol`` — so this method is reachable as
      ``api.imcontrol.buildWorkflowFacade(...)`` (not via a sub-namespace).

      :param \*\*kwargs: Forwarded to ``build_facade_from_master``. Common arguments:

                         - ``laser_aliases`` (dict[str, str]): logical → setup laser names
                         - ``detector_name`` (str): name of detector/camera to expose
                         - ``xy_positioner_name`` (str): name of XY positioner
                         - ``z_positioner_name`` (str): name of Z positioner
                         - ``time_resolved_detector_name`` (str): detector implementing
                           the time-resolved contract
                         - ``hwp_name`` / ``qwp_name`` (str): rotator names
                         - ``hwp_presets`` / ``qwp_presets`` (RotatorPresets)
                         - ``scan_workflow`` / ``scan_done_signal``: optional overrides;
                           by default these are taken from the communication channel

      :returns: facade object with WFS-shaped sub-facades.
      :rtype: MicroscopeFacade

      .. rubric:: Example

      >>> facade = api.imcontrol.buildWorkflowFacade(
      ...     laser_aliases={'488': '488 (EXC) sn27311',
      ...                    '405': '405 (ACT) sn26647'},
      ...     detector_name='Kiralux',
      ...     xy_positioner_name='XY',
      ...     z_positioner_name='Z',
      ...     hwp_name='HWP', qwp_name='QWP',
      ... )
      >>> facade.laser_con.set_constant_power(['488'], [50.0])

      Always available.

   .. method:: recordFramesToMemory(detectorName: Union[List[str], str, int, NoneType], numFrames: int, timeout: float = 600.0, keep: bool = False, structured: bool = False) -> Union[numpy.ndarray, Dict[str, numpy.ndarray], imswitch.imcontrol.model.acquisition_result.AcquisitionResult]

      Records ``numFrames`` frames of a detector, as the Recording

      is as for recordScanToMemory: ``detectorName`` (a name, a list, -1,

   .. method:: recordScanToMemory(detectorName: Union[List[str], str, int, NoneType] = None, timeout: float = 600.0, keep: bool = False, structured: bool = False) -> Union[numpy.ndarray, Dict[str, numpy.ndarray], imswitch.imcontrol.model.acquisition_result.AcquisitionResult]

      Runs the scan the Scan widget holds once and returns the frames
      it triggers as a NumPy array ``(frames, rows, columns)``, without
      writing a file: the recording goes to memory, is read back, and is
      dropped. With several detectors the result is a dict that maps each
      detector's name to its array.

      ``detectorName`` is a detector's name, a list of names, ``-1`` for
      the current detector, ``-2`` for all of them, or None for what the
      Recording widget has selected. The call blocks until the scan and
      the recording are over, at most ``timeout`` seconds; it raises
      ``RuntimeError`` when the recording is refused or fails and
      ``TimeoutError`` when it does not finish (the recording is stopped).
      The Recording widget's settings are put back afterwards. With
      ``keep=True`` the recording also stays listed in ImProcess, as a
      recording to RAM does. It runs on the caller's thread, which must
      not be the GUI thread (a script's is not).

      ``structured=True`` returns an AcquisitionResult instead: the frames
      of every detector with their axes and pixel size, which scan
      position each frame was taken at (recorded by the scan, or
      reconstructed from its plan -- the result says which), the settings
      the recording wrote down, its start time and whether it is
      complete, with show() and save().

      Needs *Recording* in ``availableWidgets``.

   .. method:: runScan(source: Optional[str] = None) -> imswitch.imcontrol.model.scan_request.ScanRunHandle

      Starts one scan with the parameters set in the scan widget and
      returns a handle for its completion.

      The request is pre-flighted before any lifecycle signal is published;
      a refused start (a scan is already running, the previous one is still
      finishing, ...) raises ``ScanRequestRejectedError`` (a RuntimeError)
      whose message is the reason, and nothing else happens. A scan design
      the scan manager refuses (longer than ``scan.maxScanTimeMin``, a
      scanner driven outside its voltage range) raises the same way; it is
      found only after ``scanStarting`` went out, which is then paired with
      a ``scanEnded``. On rigs with several scanners ``source``
      selects one by its widget key (see getScanSourceNames); without it the
      canonical Scan controller or a lone capable controller is used, and
      ambiguity raises. Repeat is switched off for the scan.

      The returned handle resolves for exactly this scan whatever the order
      of any waiter: ``handle.wait(timeout)`` (from a script), ``handle.done``
      / ``handle.successful`` / ``handle.message``, or
      ``getScanRequestStatus(handle.requestId)`` (remote clients receive the
      handle as ``{requestId, source, state, message}``).

      Always available.

   .. method:: signals() -> Mapping[str, imswitch.imcommon.framework.qt.Signal]

      Returns signals that can be used with e.g. the getWaitForSignal
      action. Currently available signals are:

       - acquisitionStarted
       - acquisitionStopped
       - recordingStarted
       - recordingEnded
       - recordingFailed
       - scanStarting (the run-level start, before hardware arms)
       - scanStarted (the execution backend started the iteration)
       - scanDone (an iteration finished)
       - scanEnded (the run is over, on every terminal path)
       - scanRejected(reason) (a start request was refused and its scan
         never runs; reason says why)

      They can be accessed like this: api.imcontrol.signals().scanEnded

      Always available.
